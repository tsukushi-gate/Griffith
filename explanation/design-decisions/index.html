設計判断の記録

このページは、このライブラリの形を決めた 主要な設計判断 を公開 ADR (Architecture Decision Record)風にまとめたものである。各項目は 問題 / 決定 / 理由 の 3 行を骨格とし、必要なら帰結を添える。

「どういう構造か」は アーキテクチャ全体像 に、 「どう書くか」はリポジトリの CONTRIBUTING.md にある。ここに書くのは なぜそう決めたか だけである。

#決定一言でいうと
1IR を真実源に据える学習系と出力ターゲットを直交させる
2参照実装を ground truth にする素朴さそのものが検証価値
3周辺は実数のまま残す全部を論理ゲートにしない
4N=2 softmax を既定に既知の再現点を基準線にする
5Conv は residual init 既定 ON深いツリーに信号を通す
6uv + extras で依存を管理CPU/CUDA/GPU 環境を 1 つの定義で
7テストを L1〜L5 に分ける変更の種類とテストの種類を対応づける

ADR-1: IR を真実源に据える

Section titled “ADR-1: IR を真実源に据える”
  • 問題 — 学習フレームワーク(PyTorch)と出力ターゲット(Verilog / VHDL / エディタ / コード生成)を 直接つなぐと、片方を変えるたびにもう片方が壊れる。出力ターゲットが増えるほど組み合わせが爆発する。
  • 決定 — 学習後のモデルの意味を IR(JSON) に固定し、下流はすべて IR だけを見る。 IR は学習系にも下流系にも属さない共通契約とする。ノード粒度はレイヤ単位で、 ゲート単位には展開しない(ゲートビューは indices と truth_tables から導出する)。
  • 理由 — 学習フレームワークを差し替えても IR より下流は不変、HDL ターゲットを増やしても 学習側は不変でいられる。ゲート単位に展開しないのは、MNIST 級でも数万ノードになり ファイルサイズと編集性が破綻するため。
  • 帰結 — export/ もビジュアルエディタも griffith CLI も、同じ IR を読む単一の消費者になった。 エディタで組んだモデルと Python で書いたモデルが同じ形で保存されるのはこの決定の帰結である。

ADR-2: 参照実装を ground truth にし、高速化のために書き換えない

Section titled “ADR-2: 参照実装を ground truth にし、高速化のために書き換えない”
  • 問題 — LutLayer の backward はカスタム autograd + CUDA カーネルで最適化されており、 式変形の誤りが混入しても loss は「それらしく」下がってしまう。何を正解とみなすかが要る。
  • 決定 — core/reference.py に素朴な純 autograd 実装を置き、これを ground truth とする。 最適化版は float64 の gradcheck と参照照合 1e-10 で正しさを保証する(tests/l2_grad/)。 参照実装は高速化目的では書き換えない。
  • 理由 — 素朴さそのものが検証価値だからである。参照実装が最適化されるほど 「両方が同じ間違いをしている」可能性が上がり、照合が意味を失う。
  • 帰結 — 新しいカスタム autograd Function を足すときは、必ず参照実装との照合テストを先に書く (手順は CONTRIBUTING の「Test layers」節を参照)。

ADR-3: 論理ゲート化は範囲を切って行い、周辺は実数のまま残す

Section titled “ADR-3: 論理ゲート化は範囲を切って行い、周辺は実数のまま残す”
  • 問題 — 既存の PyTorch モデルを丸ごと論理ゲート化しようとすると、embedding・正規化・ attention など「連続値であることに意味がある」部分まで壊れ、学習が立たない。
  • 決定 — 論理ゲート化はブロック単位で行い、境界に encoder / decoder を挟む。 周辺の実数層は浮動小数点のまま残す。境界の選択肢は LogicSpec に集約する (encoder = sigmoid / binarize_ste / thermometer / identity、 decoder = groupsum_centered / groupsum / layernorm / identity)。
  • 理由 — ハードウェア化の利益は計算量が集中する中核部にあり、周辺を無理に 0/1 化しても 得るものが少なく失うものが多い。境界の作り方を 1 つの dataclass に集めておけば、 「どこまで論理ゲートにするか」を実験パラメータとして掃引できる。
  • 帰結 — Attention / Transformer はエディタ上では blackbox として扱われる (学習不可・HDL 生成不可・実行の正は Python モデル)。これは制限ではなく、 この方針を UI に反映した結果である。

ADR-4: N=2 の softmax を既定にし、16 ゲート表として持つ

Section titled “ADR-4: N=2 の softmax を既定にし、16 ゲート表として持つ”
  • 問題 — パラメータ化は 5 方式あり、どれを既定にするかで初見のユーザが最初に見る挙動が決まる。 N=2 は「2N=42^N=42N=4 エントリの softmax」でも「16 種ゲートの softmax」でも書ける。
  • 決定 — 既定を parameterization='softmax' とし、N=2 のときだけ内部表現を 16 ゲートのロジット (out_dim, 16) にする(_use_16gate)。N>2 は 2N2^N2N エントリ表を使う。
  • 理由 — N=2 の 16 ゲートは difflogic(NeurIPS 2022)と等価で、論文の数字を再現できる基準線になる。 加えて離散化が arg⁡max⁡\arg\maxargmax 一発で 16 種の Boolean 関数すべてを選べるため、N=2 では離散化ギャップが原理的に生じない。
  • 帰結 — 逆に N>2 の softmax は hard 表が「単一 minterm か FALSE」に縮退するという既知の弱点を抱える。 N=4/6 でハードウェア展開するなら independent / iwp / warp を選ぶこと (→ LutLayerの数理 §5、パラメータ化を選ぶ)。

ADR-5: LutConv2d では Residual Initialization を既定 ON にする

Section titled “ADR-5: LutConv2d では Residual Initialization を既定 ON にする”
  • 問題 — 論理ゲートツリーは深さ ddd で NdN^dNd リーフに広がる。ランダム初期化では初期のツリーが 入力を潰してしまい、勾配が奥まで届かない。
  • 決定 — LutConv2d は residual_init=True を既定とし、パススルー相当のエントリだけ ロジットを 5.0 に置く(softmax([5,0,0,0])≈[0.993,… ]\mathrm{softmax}([5,0,0,0]) \approx [0.993, \dots]softmax([5,0,0,0])≈[0.993,…])。 一方 LutLayer は既定 OFF で、必要なときだけ明示的に有効化する。
  • 理由 — 深さは Conv 側にしか構造的に現れないため。初期状態を「第 1 入力をそのまま通す」に 寄せておけばネットワークはほぼ恒等写像から始まり、信号と勾配が通る(CDDLGN §3.2)。 全結合の LutLayer に同じ既定を敷くと、必要のない初期バイアスを常時掛けることになる。
  • 帰結 — 既定値が層ごとに違うのは意図的である。iwp は構造上この初期化を持てないため、 指定しても警告付きで無視される。

ADR-6: 依存は uv + extras で管理し、PyTorch は extra に追い出す

Section titled “ADR-6: 依存は uv + extras で管理し、PyTorch は extra に追い出す”
  • 問題 — PyTorch は CPU 版・CUDA 版・MPS 版でホイールが異なり、単一の依存指定で Mac 開発機・CPU CI・GPU 機のすべてを満たせない。エディタや可視化の依存も、 全員に強制すると環境構築が重くなる。
  • 決定 — パッケージ管理を uv に統一し、PyTorch を含む重い依存はすべて extra に切り出す (cpu / cu128 / dev / editor / figures)。セットアップは uv sync --extra ... で行い、 uv pip install や .venv の直接 activate は使わない。Python は常に uv run 経由で起動する。
  • 理由 — extra の組み合わせで環境差を吸収でき、ロックファイルが 1 本で済む。 uv run を強制するのは、環境がずれたまま実験結果が出てしまう事故を構造的に防ぐため。
  • 帰結 — cpu と cu128 は同時に指定できない(排他)。 editor extra には FastAPI/uvicorn しか入っていないので、 エディタを使うときも --extra cpu(または cu128)が必要になる。

ADR-7: テストを L1〜L5 の 5 層に分ける

Section titled “ADR-7: テストを L1〜L5 の 5 層に分ける”

  • 問題 — 「数式が正しいか」「勾配が正しいか」「論文が再現できるか」「学習が収束するか」 「HDL と一致するか」は失敗の意味も実行コストもまったく違う。1 つのスイートに混ぜると、 遅いテストのせいで速いテストが回らなくなる。

  • 決定 — テストを 5 層に分け、変更の種類と書くべきテストを対応づける。 既定の高速スイートは L1/L2/L4/L5 に絞り、重い層はマーカーで隔離する。

    層場所内容実行
    L1tests/l1_math/数学的性質(分割単位性・真理値表・離散化仕様)既定
    L2tests/l2_grad/勾配(float64 gradcheck + 参照実装照合)既定
    L3tests/l3_paper/論文再現(実測較正した閾値)-m paper
    L4tests/l4_learning/学習収束(hard eval 100% が合格基準)既定
    L5 / HDLtests/l5_hybrid/, tests/hdl/ハイブリッド統合 / 3 段等価性既定 / -m hdl

  • 理由 — 高速スイートが常時グリーンでいられること(2 分以内)を最優先にしたため。 L4 の合格基準を soft ではなく hard eval 100% にしているのは、 「連続緩和では解けるが Boolean 回路にすると解けない」という本質的な失敗を素通りさせないためである。

  • 帰結 — L3 の閾値は推測で決めず必ず実測してから固定し、較正履歴を docstring に残す。 テスト閾値を実装に合わせて緩めるのは禁止事項として明記されている。

判断の背後にある一貫した姿勢

Section titled “判断の背後にある一貫した姿勢”

7 つの決定を貫いているのは、次の 2 つである。

  • 正しさの基準を、速いものの外側に置く — 参照実装(ADR-2)、hard eval 基準(ADR-7)、 3 段等価性チェーン。最適化されたコードは、最適化されていない何かと突き合わせて初めて正しいと言える。
  • 境界を 1 か所に集める — IR(ADR-1)、LogicSpec(ADR-3)、extras(ADR-6)。 組み合わせが爆発しうる場所には必ず 1 枚の契約を挟み、両側を独立に動かせるようにする。
