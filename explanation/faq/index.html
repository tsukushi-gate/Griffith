よくある質問

このページは 方針とスコープについての質問に答える。 「何ができて、何がまだできないのか」を、実測値と出典のある範囲で正直に書く。 操作でつまずいたときはトラブルシューティング、 言葉の定義は用語集を参照。

スコープと主張

Section titled “スコープと主張”

なぜ「GPU 不要」と言えるのか

Section titled “なぜ「GPU 不要」と言えるのか”

GPU が要らないのは推論側だけである。ここを取り違えると期待がずれる。

学習(訓練)推論(デプロイ)
何をしている連続緩和した LUT を PyTorch の実数演算で最適化argmax で固定した純ブール回路のビット演算
GPUあると速い。大規模構成では実質必須不要。乗算器もゼロ
実行先PyTorch(CUDA / MPS / CPU)CPU / FPGA / ASIC

学習中は「各ニューロンがどのゲートになるか」を微分可能に緩和して勾配を流しているので、 中身は普通の実数ニューラルネットと同じ計算負荷を持つ。GPU が不要になるのは model.eval() で真理値表を argmax 固定したあとの話である (soft と hard の二相)。

規模感の目安は次のとおり(学習を回す)。

  • スモーク(k=16・2層)—— 数秒、CPU
  • クイック(k=2000・3層・3エポック)—— 数分
  • 標準(k=16,000・6層・50エポック)—— 数分〜数十分(GPU)
  • 論文再現(k=64,000・6層・200エポック〜)—— 時間単位 → クラウド GPU

学習に CUDA は必須か

Section titled “学習に CUDA は必須か”

必須ではない。 CUDA カーネルは高速化のための任意実装で、非対応環境では自動的に Python フォールバックへ切り替わる(CPU / MPS で動く)。実際、本サイトのチュートリアルの 大半は「実行環境: CPU のみ(GPU 不要)」で完結する。

これは difflogic / BinaryBrain が CUDA を必須としているのとの明確な差でもある。 ただし フォールバックは遅い。MPS では CUDA カーネルが使われず、 fan-in を上げると基底数が 2N2^N2N で増えるため、N=6 の構成をローカル Mac で回すのは現実的でない (トラブルシューティング)。

difflogic(原論文の実装)と何が違うのか

Section titled “difflogic(原論文の実装)と何が違うのか”

原論文(Petersen et al., NeurIPS 2022)の実装は 2 入力ゲート固定・softmax・CUDA 必須で、 全結合の DLGN を学習するためのものである。本ライブラリはその一般化と、学習後の下流工程を持つ。

difflogicgriffith-logic
計算単位2 入力ゲート固定(16 種)N 入力 LUT(N = 2 / 4 / 6)
パラメータ化16 ゲート softmax のみ5 方式(softmax / independent / iwp / raw / warp)
CUDA必須不要(CPU / MPS 対応、Python フォールバックあり)
畳み込み非対応対応(N 入力 LUT 完全木による CDDLGN)
学習則backpropbackprop / AP / DFA / ES
学習後——IR(JSON)→ Verilog / VHDL、3段等価性検証
開発支援——ビジュアルエディタ、griffith 統一 CLI

「difflogic 互換」と言うときは N=2 + softmax パラメータ化のモードを指す。 この設定なら原論文と同じ土俵に立てる —— 実際、同一レシピ(6層・τ=10・200k イテレーション)で hard 精度 97.84% を得ており、論文の small 構成 97.69% を上回っている。

系譜の全体像は DLGN の分類と系譜、 方式ごとの違いは パラメータ化を選ぶ。

精度と限界

Section titled “精度と限界”

実数ニューラルネットの精度に勝てるのか

Section titled “実数ニューラルネットの精度に勝てるのか”

タスクによる。MNIST 級ではほぼ並ぶが、CIFAR-10 級ではまだ差が残る。 正直に数字で示す。

モデルMNISTCIFAR-10
DiffLogic(Petersen, NeurIPS 2022)98.47%62.14%
LogicTreeNet-L(NeurIPS 2024)99.35%84.99%
LogicTreeNet-G(NeurIPS 2024)——86.29%
通常の CNN(参考)約 99.5%約 93%

本ライブラリでの MNIST 実測は次のとおり(いずれも backprop、test の値)。

  • hard 97.84% —— DLGN 公式レシピ(6層・τ=10・200k イテレーション)
  • hard 97.74% / soft 98.30% —— softmax N=2・6層・τ=10・bs=128・lr=0.01・50 エポック
  • hard 98.02% —— Hard-ST(CAGE)・6層 × 64,000 ゲート

つまり MNIST では通常の CNN と 1〜2pt 差まで来ているが、CIFAR-10 では 6〜10pt の開きがある。 そして精度あたりのパラメータ効率は、密な実数 NN に劣る場面がある。

精度を引用するときのお願い

DLGN の精度は 学習則・soft/hard・train/test・アーキテクチャ・エポック数を書かないと意味が定まらない。 特に soft と hard は別物なので、「MNIST 98%」のような裸の数字は使わないこと。 学習則を変えると差は大きく、backprop を使わない AP 法(Akiho Propagation)では同じ MNIST 全結合構成で soft 約 0.90 / hard 約 0.85 にとどまる(学習則)。

LLM は動くのか

Section titled “LLM は動くのか”

現状は「文字レベル言語モデル」の段階であり、実用的な LLM ではない。

LogicGPT は attention も FFN も出力ヘッドも論理ゲートで組んだ decoder-only Transformer で、 実数の行列積を一切持たない。Tiny Shakespeare の文字 LM として学習すると、 チュートリアル構成(d_model=192・2層・context 32 文字・1500 step・パラメータ 48,640・CPU 106 秒)で val bpc が 4.954 → 3.134 まで下がる(一様分布のベースラインは log₂32 = 5.00)。 生成テキストには単語らしい綴り・改行・ROMEO: のような話者行までは現れる。

本格レシピ(Tiny Shakespeare・語彙 65・T=64・20k ステップ・A10G)での hard perplexity の梯子は、 論理化を進めるほど悪化する形で測れている。

構成hard ppl離散化ギャップ
L0(全て浮動小数点 = 天井)4.9〜5.0≈ 0
L0b(FFN のみ論理化)7.880.30
L1(+ 射影をゲート化)19.240.50
L3-C(+ MUX 選択器)15.5〜15.950.29
L3-C + Gumbel 較正13.310.107

生成品質も正直に書くと、L3-C + Gumbel の greedy デコードは 200 文字すべて改行というモード崩壊を起こし、 温度サンプリングでようやく単語断片レベルになる(浮動小数点の L0 ですら短い反復ループに陥る)。

ボトルネックは離散化ギャップである。系列 MNIST では 0.02〜0.05 で済むギャップが、 言語モデルでは 0.3〜0.5 nat と約 10 倍になる。Gumbel 較正はこれを 63% 削ったが、 浮動小数点の天井にはまだ届いていない。実際に動かすなら 論理ゲート GPT と 論理化の梯子 を参照。

事前学習済みモデルを論理ゲートに「変換」できないのか

Section titled “事前学習済みモデルを論理ゲートに「変換」できないのか”

変換はできるが、基本的にスクラッチ学習に負ける。 これは実測で確認された負の結果である。

理由は構造的なもので、算術演算を保持したまま回路化する系(LogicNets 系)と、 自由にブール論理を学ぶ系(difflogic 系)は最大限に異質だからである。 既存の重みを転写すると「自由にブール関数を選ぶ」という native DLGN の強みを縛ってしまう。

変換に価値があるのはハードウェア忠実な算術回路を作りたいときであって、 native DLGN の性能が目的ならスクラッチ学習が正解である(分類と系譜)。

どんなタスクに向く / 向かないか

Section titled “どんなタスクに向く / 向かないか”

向く

  • 推論を FPGA / ASIC で回したい(乗算器不要、LUT に直マップ、低消費電力)
  • レイテンシが厳しい(組合せ回路なので数クロックで答えが出る)
  • クラウドに出せないデータを手元のデバイスで処理したい
  • 入力がもともと二値・カテゴリ的(温度計符号化した特徴、ビットマップ、n-gram の有無など)

向かない / 注意が必要

  • 巨大な事前学習モデルからの流用が効きにくい(上記)
  • 精度あたりのパラメータ効率が密な実数 NN に劣る場面がある
  • 系列モデリング・言語は離散化に脆い(ギャップが画像タスクの約 10 倍)
  • 学習そのものは実数計算なので、学習コストは普通の NN と変わらない

実務上の落としどころは、範囲を切って論理化するハイブリッド化であることが多い。 「Attention は PyTorch のまま、MLP だけ LUT に置換」といった部分置換が nn.Module の途中にそのまま挟める(ハイブリッド NN を作る)。

使い方の前提

Section titled “使い方の前提”

FPGA が無くても使えるか

Section titled “FPGA が無くても使えるか”

使える。 FPGA は「最後まで行くと使える出口」であって、前提条件ではない。

  1. PyTorch だけで完結する —— model.eval() で離散回路と同じ hard 推論ができる。 本サイトのチュートリアルの大半はこれだけで成立している
  2. IR を numpy で実行できる —— simulate() がビット厳密に走る。 simulate_trace() を使えば層ごとの中間ビットも追える(IR を扱う)
  3. HDL の生成だけならシミュレータも不要 —— griffith export-hdl は変換のみを行う
  4. 等価性検証は任意 —— iverilog / ghdl が無い環境では該当テストが自動 skip される

なお実機 FPGA 向けの支援ツール群(mdl-fpga)はまだ本体に統合されていない先行ガイドの段階である (FPGA に焼く)。

「FPGA に焼けた」なら精度も保証されるのか

Section titled “「FPGA に焼けた」なら精度も保証されるのか”

されない。 ここは分けて考える必要がある。

等価性検証(3段等価性)が保証するのは IR と実機のビット一致であって、 学習時の連続値モデルと離散回路の精度が一致することではない。 真理値表がまだ 0/1 に決めきれていないモデルを丸めると精度は大きく落ちうる —— 短縮レシピの実例では、連続値では eval acc 0.803 だったモデルがエントリを丸めると 0.211 まで崩壊した。

焼く前に必ず hard eval の精度を確認する。 読み方は学習曲線の見方、 ギャップが構造的にゼロになる構成は DWN。

fan-in(N)はいくつを選べばよいか

Section titled “fan-in(N)はいくつを選べばよいか”

用途で決まる。FPGA の面積を最小化したいなら 6、CPU / GPU での推論速度なら 2、 訓練の安定性なら 2 が目安である。パラメータ化との組合せには確定知見があり、 N=2 は softmax、N≥4 は independent(または warp)+ 学習率を上げる。 N≥4 で softmax を使うと hard 表が構造的に縮退するので選んではいけない (パラメータ化を選ぶ)。

ライセンス / 商用利用はどうなっているか

Section titled “ライセンス / 商用利用はどうなっているか”

暫定で Apache-2.0(正式決定前)である。 リポジトリには LICENSE(Apache-2.0)と NOTICE / THIRD_PARTY_NOTICES.md が入っており、パッケージメタデータの license も Apache-2.0 を指している。ただしこれは正式決定前の暫定値で、 公開時に見直す可能性がある。

したがって、Apache-2.0 の条件での利用・再配布・商用利用を想定して差し支えないが、 確定版のライセンスはリポジトリ直下の LICENSE を常に正とすること。 第三者由来のコード・データの帰属は THIRD_PARTY_NOTICES.md に整理してある。 判断が必要な場合は CONTRIBUTING を参照のうえ個別に問い合わせてほしい。

開発に参加するには

Section titled “開発に参加するには”

テストは L1(数式性質)〜 L5(ハイブリッド / HDL 等価性)の層で構成されており、 新しい部品を足すときは「参照実装 → 勾配照合 → 性質テスト → 収束テスト」の順に テストを先に書くのが規約である(テスト体系)。 ドキュメントの書き方はドキュメントを書く。
