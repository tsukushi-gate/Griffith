ドキュメントは **書くより腐らせないほうが難しい**。このページは本プロジェクトで
ドキュメントをどう構成し、どう更新し、どう腐敗を機械的に検出するかの方針をまとめる。
新しいページを足す前に読んでほしい。

## 1. 4分類(Diátaxis)で置き場所を決める

すべてのページは [Diátaxis](https://diataxis.fr/) の 4 象限のどれか **1 つだけ** に属する。
「学習中か作業中か」×「実践か理論か」で決まる。

| 象限 | 読者の状態 | 書き方 | 本サイト |
|---|---|---|---|
| **Tutorial**(学習 × 実践) | 何も知らない。手を動かして体験したい | 手順を順に。選択肢を出さない。必ず動く | `tutorials/` |
| **How-to**(仕事 × 実践) | 目的が決まっている。最短で達成したい | 目的別。前提を明示。分岐を許す | `guides/` |
| **Reference**(仕事 × 理論) | 正確な仕様を引きたい | 網羅・一貫・淡々と。説明しない | `reference/` |
| **Explanation**(学習 × 理論) | 「なぜ」を理解したい | 背景・設計判断・比較。手順を書かない | `explanation/` |

**混ぜないことが最大の規律** である。チュートリアルの途中で設計判断を語り始めた瞬間に、
そのページは初心者にとって長すぎ、経験者にとって薄すぎる文書になる。
語りたくなったら **explanation に切り出してリンクする**。

判断に迷ったときの目安。

- 「まず何をすればいい?」に答える → tutorial
- 「X をするにはどうする?」に答える → guide
- 「X の引数は?」に答える → reference
- 「なぜ X なのか?」に答える → explanation

## 2. 生成する領域と、手で書く領域

**同じ事実を 2 か所に書かない**。ドキュメントが腐る原因のほぼすべては「コードと文章に同じ情報が
別々に書かれ、片方だけ更新される」ことにある。したがって、コードから機械的に導ける領域は
**生成物** とし、手編集を禁止する。

| 領域 | 真実源 | 生成方法 | 手編集 |
|---|---|---|---|
| API リファレンス | パッケージの公開シンボル定義と docstring | `npm run gen:api`(griffe による静的解析) | **禁止**(docstring を直す) |
| チュートリアル | `examples/*.py`(実行可能な最小サンプル) | `scripts/build_tutorials.py`(実行して出力と図を埋め込む) | **禁止**(元の `.py` を直す) |
| ガイド / 解説 | 人の判断・設計意図 | 手書き | 可 |

生成系は **ビルドの前段に組み込む**(`prebuild` で API 生成が走る)。
「生成を忘れて古い API 表が出る」という失敗を、手順書ではなく仕組みで潰すのが要点である。

:::caution[生成物を手で直さない]
生成先のファイル冒頭には「このファイルは自動生成される」旨を必ず書く。手で直しても次回の生成で
消えるうえ、真実源との差が誰にも気づかれないまま残る。
:::

## 3. 更新のワークフロー

### 実装したら、同じブランチでドキュメントも直す

「あとでまとめて直す」は必ず腐る。**実装 PR とドキュメント修正を同じブランチに載せる** のを基本とする。
コミット規約(`種別: [タスクID] 要約`)に従い、ドキュメントだけの変更は `docs:` を使う。

### docs-sync(ドキュメント同期)の運用

リポジトリ内の `docs/`(開発者向けの内部ドキュメント)と、この公開サイトの二重管理を避けるため、
次の役割分担を守る。

| | リポジトリ `docs/` | 公開サイト |
|---|---|---|
| 読者 | 開発者・AI エージェント | 利用者・外部の読者 |
| 内容 | 進捗・実験台帳・内部設計メモ・運用手順 | 使い方・概念・API |
| 内部 ID や実験 ID | あってよい | **除去する**(意味が伝わらないため) |

公開サイトへ持ち込むときの清書ルールは 3 つ。

1. **内部の実験 ID・タスク ID を落とす**(「D5 の結果」→「社内実験の結果」)
2. **未確定の計画・未公開の数値を落とす**
3. **リンクを公開サイト内のパスへ張り替える**(リポジトリ相対パスのまま持ち込まない)

この清書を毎回手作業でやると必ずブレるので、**手順を skill(定型作業の手順書)として固定** し、
「内部ドキュメントを公開サイトへ反映する」作業は常に同じ手順で行う。
skill 化の判断基準は「事実ではなく手順に育ったら」である。

## 4. 腐敗を機械で検出する

レビューの目視は必ず漏れる。次の 4 つを **CI で落ちるようにする** のが目標。

| 対象 | 手段 | 効果 |
|---|---|---|
| リンク切れ | リンク検証プラグイン(サイト内リンクを実在検証) | 移動・改名でリンクが死んだらビルドが落ちる |
| ビルドの警告 | strict なビルド設定(警告をエラー扱い) | frontmatter 欠落・不正な参照を検出 |
| API の網羅性 | `npm run check:api`(生成せず差分検査のみ) | 公開シンボルを足して docs を忘れると落ちる |
| docstring の欠落 | `interrogate` などの docstring カバレッジ計測 | 「公開 API に説明が無い」状態を数値で監視し、閾値を下げない |

:::tip[閾値は下げない]
カバレッジや検証の閾値は **上げる方向にのみ動かす**(ratchet)。落ちたときに閾値を下げるのは、
検証を無効化するのと同じである。
:::

さらに、リンクは **相対パスよりサイト内絶対パス**(`/explanation/dlgn/` の形)で書くと、
ページ移動時の壊れ方が単純になり検証で確実に捕まる。

## 5. 書き方の約束

- **日本語で書く**。英語版は `/en/` に置き、未翻訳ページは日本語へフォールバックする
- **1 ページ 1 目的**。目的が 2 つあるなら 2 ページに割る
- **薄いリンクを置かない**。「詳細は X を参照」だけでなく、**なぜそこを読むのか** の 1 行を添える
- **数式は KaTeX、図は Mermaid** を使う(どちらもビルド時 / クライアント側で描画される)
- **色の約束を守る** — 橙 = 実数の世界、緑 = 論理の世界。図でこの規約から外れない
- **画面キャプチャは最後の手段**。UI は変わるので、変わらない概念を文章と図で説明する

## 6. 出口戦略(将来の移行に備える)

ドキュメントサイトのフレームワークは数年で世代交代する。**移行コストを最小に保つ設計** を
最初から取っておく。

- **中身は素の Markdown に寄せる** — フレームワーク固有のコンポーネントは
  注記・タブなど「無くても意味が通る」用途に留める。フレームワーク固有記法で
  本文の構造を作らない
- **frontmatter は最小限**(`title` / `description`)に保つ
- **ディレクトリ構成 = URL 構成 = Diátaxis の 4 分類** を保つ。この 3 つが一致していれば、
  移行先が何であれディレクトリを丸ごと移すだけで済む
- **生成スクリプトは出力先パスだけを差し替えれば動く** ようにしておく

この条件を満たしていれば、移行先の候補
(例: [Zensical](https://zensical.org/)、MkDocs Material、VitePress など)へ切り替える判断は、
**中身ではなくビルド設定の問題** に縮む。逆に、フレームワーク固有記法で本文を書き始めた瞬間に
移行は数百ページの書き直しになる ── これが「素の Markdown に寄せる」ことの実利である。

## 7. 新しいページを足すときのチェックリスト

1. 4 分類のどれか **1 つ** に決めたか
2. 同じ事実を他のページに書いていないか(あるならリンクに置き換える)
3. 生成で埋められる内容ではないか(なら生成側を直す)
4. 内部 ID・未公開の数値が混ざっていないか
5. リンクはサイト内絶対パスか。リンク先は実在するか
6. ローカルでビルドが通るか(警告も含めて)
