griffith-logic manages its dependencies with [uv](https://docs.astral.sh/uv/).
Don't invoke `.venv` directly and don't use `pip install` / `uv pip install` — always go through
`uv run` and `uv sync`.

## Requirements

| Item | Requirement |
|---|---|
| Python | 3.11 or newer |
| uv | Latest release recommended |
| OS | macOS (Apple Silicon) / Linux / Windows |

If you don't have uv yet, install it one of these ways.

<Tabs>
  <TabItem label="macOS / Linux">

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

  </TabItem>
  <TabItem label="Homebrew">

```bash
brew install uv
```

  </TabItem>
  <TabItem label="Windows (PowerShell)">

```powershell
powershell -c "irm https://astral.sh/uv/install.ps1 | iex"
```

  </TabItem>
</Tabs>

## Setup

<Steps>

1. Clone the repository.

   ```bash
   git clone https://github.com/tsukushi-gate/Griffith.git
   cd Griffith
   ```

2. Sync with the extras that match your machine.

   <Tabs syncKey="platform">
     <TabItem label="Mac / Linux CPU">

   ```bash
   uv sync --extra dev --extra cpu
   ```

     </TabItem>
     <TabItem label="Linux CUDA (GPU)">

   ```bash
   uv sync --extra dev --extra cu128
   ```

     </TabItem>
   </Tabs>

3. Verify the install (see "Verifying the install" below).

</Steps>

<Aside type="caution" title="cpu and cu128 are mutually exclusive">
`torch` and `torchvision` resolve from **either** the `cpu` extra **or** the `cu128` extra, never
both. They are declared as
[conflicting extras](https://docs.astral.sh/uv/concepts/projects/dependencies/#conflicting-dependencies)
under `[tool.uv] conflicts` in `pyproject.toml`, so passing both makes `uv sync` fail to resolve.
When in doubt: `cpu` for Mac / CPU development, `cu128` for GPU training.
</Aside>

## Available extras

The extras are declared in `[project.optional-dependencies]` of `pyproject.toml`. The first four
are the ones you'll reach for most.

| extra | What it pulls in | When to use it |
|---|---|---|
| `cpu` | torch, torchvision, timm (CPU / MPS builds) | Everyday development and CI. Always this on Mac |
| `cu128` | torch, torchvision, timm (CUDA 12.8 builds) | GPU machines, training on Modal / RunPod |
| `dev` | pytest, hypothesis, pytest-cov, httpx, mypy | Tests and type checking (required for development) |
| `editor` | fastapi, uvicorn, python-multipart | Backend of the [visual editor](/en/guides/editor/) |
| `visualizer` | websockets | Per-gate WebGL viewer (`tools/visualizer/`) |
| `cloud` | modal, runpod, wandb-workspaces | [Cloud GPU](/en/guides/cloud-gpu/) runs and report generation |
| `figures` | matplotlib, pillow | Plotting experiment results |
| `teachers` / `text` | onnxruntime, huggingface-hub / transformers, datasets | Converting and distilling pretrained models |
| `sat` | python-sat | SAT-based capacity checks (representability proofs) |
| `wmt` / `sentiment` | datasets, sacrebleu / fugashi and friends | Translation and Japanese sentiment datasets |

Extras can be combined freely (except `cpu` together with `cu128`).

```bash
uv sync --extra dev --extra cpu --extra editor   # dev environment including the editor
```

:::note[The editor and the viewer are available once you clone the repository]
The visual editor and the WebGL viewer backed by the `editor` / `visualizer` extras **are part of
this repository** (`tools/editor/` and `tools/visualizer/`). They are not shipped inside the PyPI
package, so to use them, clone the repository, run `uv sync --extra editor` (or
`--extra visualizer` for the viewer), and start them with `make editor`.
:::

## How torch resolves per platform

`sys_platform` markers under `[tool.uv.sources]` make the same `--extra cpu` / `--extra cu128`
resolve from different indexes depending on the platform. You never have to think about it.

| Environment | Extra to pick | Resolved from |
|---|---|---|
| Mac | `cpu` | PyPI (Apple Silicon build with MPS support) |
| Linux (CPU) | `cpu` | dedicated `pytorch-cpu` index (small, used in CI) |
| Linux (CUDA) | `cu128` | dedicated `pytorch-cu128` index (CUDA 12.8 build) |

## Using pip instead

You can also consume the package as a plain library without uv, but then **you must install torch
yourself**. As explained above, `torch` and `torchvision` resolve from different places per
platform, so they are not part of the package's core dependencies.

```bash
# 1. Install torch for your platform first (https://pytorch.org/get-started/locally/)
pip install torch torchvision

# 2. Clone the repository and install it in editable mode
pip install -e .
```

<Aside type="caution" title="Caveats when using pip">
- `pip install -e .` alone does not bring in torch, so importing the package raises
  `ModuleNotFoundError: No module named 'torch'`. Install torch first.
- Everything you do inside the repository (running tests, experiment scripts, the editor) assumes
  uv. Use `uv sync` if you plan to develop.
- CUDA builds of torch do not come from the default PyPI wheels — install them from the
  [official index](https://pytorch.org/get-started/locally/).
</Aside>

## Environment variables

Copy `.env.example` to `.env` and fill in what you need. At the moment only wandb-related
variables are used.

```bash
cp .env.example .env
```

## Verifying the install

```bash
uv run python -c "import griffith_logic as gl, torch; print(gl.__name__, torch.__version__)"
uv run python examples/01_xor.py   # trains XOR → accuracy 1.00 under hard eval
make test                          # fast test suite (under 2 minutes, always green)
```

If `examples/01_xor.py` prints `XOR: soft acc=1.00, hard acc=1.00`, you're done.
The [XOR appendix tutorial](/en/tutorials/xor/) walks through what just happened, one cell at a time.
To see it on real data, go to [1. Train on MNIST](/en/tutorials/mnist/).

## HDL verification tools (optional)

You only need an external simulator if you want to check Verilog / VHDL equivalence.
HDL generation itself works without them — the comparison step is simply skipped.

```bash
brew install icarus-verilog   # Verilog comparison (iverilog)
```

We **do not recommend installing the VHDL side (ghdl) locally on macOS**. The Homebrew Cask build
of ghdl has been measured to be broken and fails to build, so the supported way to run VHDL
equivalence checks is inside CI or a cloud (Modal) container. On machines without ghdl the tests
marked `hdl_vhdl` are simply skipped automatically; nothing else is affected.
See [HDL export](/en/guides/hdl-export/) for details.

## Datasets and their licenses

The tutorials and the scripts under `examples/` **download the datasets they need at run time**
(by default into directories such as `data-mnist/` at the repository root, overridable with each
loader's `root=` argument). This repository neither bundles nor redistributes the data itself.

| Dataset | Where it is used | Distributed by |
|---|---|---|
| MNIST / Fashion-MNIST | Nearly every tutorial except XOR | via torchvision |
| CIFAR-10 / CIFAR-100 | CNN, ResNet, and Mixer families | via torchvision |
| Tiny Shakespeare | Logic GPT and the RNN family (character LM) | the original author's public text |
| SST-2 | TextCNN and sentiment distillation | Hugging Face Datasets |
| WRIME | Japanese sentiment analysis | Hugging Face Datasets |
| Oxford-IIIT Pet / WIDER FACE, etc. | Segmentation and object detection | their respective distributors |

**Use of each dataset is governed by the license and terms of its distributor.** Some are restricted
to research use, and some forbid redistribution. Downloading them means accepting those terms, so
check the dataset's own primary source before any commercial use. The library's own license
(griffith-logic) does not extend to the datasets.
