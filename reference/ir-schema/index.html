IRスキーマ

IR(中間表現)は、このライブラリの真実源である。 PyTorch のモデルも、numpy の ゴールデンシミュレータも、生成される Verilog / VHDL も、すべて同じ 1 個の JSON から派生する。 だから「PyTorch の出力 = シミュレータの出力 = 実際の回路の出力」を機械的に照合できる。

このページは IR の仕様書 である。読み方・生成の手順は IRを扱う を、なぜ IR を挟むのかは アーキテクチャ全体像 を参照してほしい。

真実源のコードは griffith_logic/ir/schema.py(dataclass 定義とビット規約の docstring)、 検証規則は griffith_logic/ir/validate.py にある。

1. ドキュメントの全体構造

Section titled “1. ドキュメントの全体構造”

IR は 1 個の JSON オブジェクトである。中身は「ヘッダ」「境界(ポート)」「本体(グラフ)」の 3 ブロックに分かれる。

グラフ構造は ノード集合 + エッジ集合 で表され、ノードの中に子ノードを持つ入れ子は無い。 ポートとノードは同じ id 空間を共有し、エッジの src / dst はノード id と ポート id のどちらでもよい(だから入力ポートから直接ノードへ、ノードから直接出力ポートへ張れる)。

トップレベルのフィールド

Section titled “トップレベルのフィールド”
フィールド型意味
formatstring常に "magicdelta-ir"。読み込み時に検査され、違えば拒否される
versionstringスキーマ版(現行 "0.2.0")。→ 下の「7. バージョニング方針」
metadataobject自由記述。name / created_at などが入る。意味論には一切影響しない
inputsIRPort[]グラフの入力ポート
outputsIRPort[]グラフの出力ポート
nodesIRNode[]レイヤ本体。順序に意味はない(実行順はエッジから導く)
edgesIREdge[]ノード間・ポート間の配線

IRPort(境界)

Section titled “IRPort(境界)”
フィールド型必須意味
idstring✓ポート識別子。エッジの端点になる(例 "x" / "y")
widthint✓ビット幅。接続先の幅と一致しないと検証エラー
shapeint[] | null元テンソルの形状(例 [1,28,28])。幅規約は常に flatten 後の width が正
encodingstring | null入力の符号化(例 "binary_threshold_0.5" = 0.5 で二値化して入れる)
semanticsstring | null出力の意味(例 "class_scores" = クラススコア、argmax で予測ラベル)

encoding / semantics は 人間と外部ツールへの申し送りで、シミュレータや HDL 生成は参照しない。 「この回路にどんなビット列を入れれば正しいのか」を IR 単体で判るようにするために置いている。

IRNode(レイヤ)

Section titled “IRNode(レイヤ)”
フィールド型意味
idstringノード識別子。グラフ内で一意(重複は検証エラー)
typestringノード種別。→ 下の「2. ノード種別一覧」
paramsobject種別ごとの必須パラメータ。ここだけが回路の意味を決める
train_infoobject学習時の参考情報(パラメータ化方式など)。トランスパイラは読まない
metaobjectビジュアルエディタ専用の自由 namespace(座標・表示名等)。完全に無視される

この 3 分割が設計の要である。params を書き換えれば回路が変わり、 train_info と meta はいくら書き換えても回路は 1 ビットも変わらない。 エディタが自由にノードを動かしても HDL 出力が揺れないのはこのためである。

IREdge(配線)

Section titled “IREdge(配線)”
フィールド型既定意味
srcstring—出力側。ノード id または入力ポート id
dststring—入力側。ノード id または出力ポート id
dst_slotint0多入力ノードの入力スロット番号(v0.2 で追加)
  • dst_slot が 0 のときは JSON からキーごと省略する(v0.1 とバイト列レベルで同じ表現になり、差分が安定する)
  • fanout(同じ src から複数のエッジ)は許容される。分岐用の専用ノードは不要
  • 多入力ノードでは slot 0..N-1 が 欠番なく 1 本ずつ 埋まっている必要がある

2. ノード種別一覧

Section titled “2. ノード種別一覧”

現行 v0.2 のノードは 11 種類(うち lut_flat は配備専用)。「1 ノード = 1 レイヤ」の粒度で、ゲート単位には展開しない (ゲートビューは indices と truth_tables から導出できるので、IR に持たせると二重管理になる)。

type追加版主な params出力幅役割
lut_layerv0.1in_width, out_width, n_inputs, indices, truth_tablesout_width中核。N 入力ルックアップテーブル層
group_sumv0.1in_width, k, tau, bias(任意)kビット列を k グループへ集計しクラススコアへ。bias はクラスごとの整数の判定バイアス(省略 = 全 0)
binarizev0.1width, thresholdwidth実数を閾値で二値化(実数世界 → 論理世界の境界)

blackboxv0.1torch_class, config, in_width, out_widthout_width非論理層(ハイブリッドモデルの実数部)。HDL 生成不可
concatv0.2in_widths(slot 順)sum(in_widths)複数入力のビット連結
addv0.2width, mode(or/xor/sum)widthビット合流

binarize が実数側から論理側への入口、group_sum が論理側から実数側(スコア)への出口になる。 この 2 つに挟まれた区間だけが HDL へ落ちる、と覚えておくと構造が読みやすい。

2.1 lut_layer — 中核ノード

Section titled “2.1 lut_layer — 中核ノード”

out_width 個のゲートが並び、ゲート j は入力ビット indices[0][j] … indices[n_inputs-1][j] を 読んで、真理値表 truth_tables[j] に従って 1 ビットを出す。

params型制約(検証で強制)
in_widthint入力ビット幅
out_widthint出力ビット幅 = ゲート数
n_inputsint1 ゲートあたりの入力数 N
indicesint[N][out_width]形状は厳密に (n_inputs, out_width)。値は 0 ≤ v < in_width
truth_tablesstring[out_width]hex 文字列。値域 0 ≤ t < 2^(2^N)

真理値表のビット規約(全ノードで統一):

真理値表は「2N2^N2N ビットの整数」。その bit k が、butterfly 基底順の入力パターン kkk (パターン kkk の bit j = 入力スロット jjj の値)に対する出力である。

例として N=2 のとき、0x6 は 2 進で 0110。

入力パターン kスロット1スロット0真理値表の bit k出力
000bit0 = 00
101bit1 = 11
210bit2 = 11
311bit3 = 00

つまり 0x6 は XOR ゲートである。同様に 0x8 = AND、0xe = OR、0x9 = XNOR。 下の実物 JSON に出てくる 16 進はすべてこの規則で読める。

なぜ hex 文字列なのか

N=6 のとき真理値表は 64 ビット整数になり、JSON の数値(JavaScript の安全整数 2532^{53}253)を超える。 言語をまたいで無損失に往復させるため、真理値表だけは常に hex 文字列として書く。 N は 6 より大きくてもよい(例: ThermometerEncoder(input_bits=8) の 8 入力 LUT は 256 ビット)。 simulate は N ≤ 6 を 64 ビット整数のシフトで、N > 6 は表を (out_width,2N)(\text{out\_width}, 2^N)(out_width,2N) の ビット行列に展開して引く。

2.2 group_sum — 論理領域の終端

Section titled “2.2 group_sum — 論理領域の終端”

in_width ビットを k 個のグループへ等分し、各グループの 1 の個数を数えて tau で割る。 制約は in_width % k == 0。出力は ビット列ではなく実数スコアなので、 このノードから先は HDL の対象外になる(tau は学習時のロジット温度)。

任意の bias(長さ k の整数リスト)があれば、各グループの個数に足してからスコアにする (2 クラス判定則 s1>s0+ts_1 > s_0 + ts1​>s0​+t は bias = [t, 0])。省略時は全 0 で、simulate と build_torch が対応する。HDL 生成と C ランタイムは bias が非零だと明示的に拒否する(比較器 + 定数は回路側の 終端部品で付ける)。

2.3 concat / add — 多入力ノード(v0.2)

Section titled “2.3 concat / add — 多入力ノード(v0.2)”

DAG 構造(直列でないグラフ)を表すために追加された 2 つ。どちらも dst_slot で 入力の順番を区別する。

  • concat: in_widths(2 要素以上の正整数リスト)の順にビットを連結する
  • add: 同じ幅の入力をビット演算で合流させる。mode は 3 種
mode硬い(離散)意味柔らかい(学習時)意味HDL
orビット OR1−(1−a)(1−b)1-(1-a)(1-b)1−(1−a)(1−b)生成可
xorビット XORa+b−2aba+b-2aba+b−2ab生成可
sum整数和a+ba+ba+b生成不可(値が {0,1}\{0,1\}{0,1} を超えるため)

mode='sum' は group_sum の直前など論理領域の終端専用で、validate(..., target='hdl') が拒否する。

concat のビット順は 3 実装で完全統一

slot 0 が出力ビット列の先頭(インデックス 0 側)= 整数パック時の下位ビット。

実装書き方
numpy / torchconcatenate([slot0, slot1, ...], axis=-1)
Verilogassign w = {slotN-1, ..., slot1, slot0};({} は左が MSB)
VHDLw <= slotN-1 & ... & slot1 & slot0;(& は左が MSB)

HDL 側で左右が逆に見えるのは、Verilog / VHDL の連結が 左を MSB と定めているため。 逆順に書いているのではなく、同じ規約を各言語の記法で表現している。

2.4 constant — 定数線

Section titled “2.4 constant — 定数線”

bits(長さ = width の 0/1 リスト)を出すだけの、入力エッジを持たないノード。 bits[j] が出力ビット j(concat と同じく index 0 が下位)。 シミュレータでは定数行、torch ではバッチ方向へ expand、HDL ではハードワイヤ定数になる。

2.5 conv2d / or_pool2d — 畳み込み(v0.2)

Section titled “2.5 conv2d / or_pool2d — 畳み込み(v0.2)”

幅規約: 入出力とも width = C × H × W の NCHW flatten。 つまり入力幅 = prod(in_shape)、出力幅 = out_channels × H_out × W_out で、 出力形状は通常の畳み込みと同じ式で決まる。

Hout=⌊H+2pH−kHsH⌋+1H_{\text{out}} = \left\lfloor \frac{H + 2p_H - k_H}{s_H} \right\rfloor + 1Hout​=⌊sH​H+2pH​−kH​​⌋+1
  • indices_flat: 形状 (out_channels, n_inputs^tree_depth)。受容野内のフラット位置を指す
  • truth_tables: 長さ = out_channels × 木の内部ノード数。**oc 優先(oc-major)**で木のレベル順

HDL 生成の前に export/lowering.lower_to_primitives で lut_layer の列へ展開する。 conv をネイティブノードとして持つのは、エディタとシミュレータが「畳み込みである」ことを 見失わないため。展開後の巨大な lut_layer 列だけを IR に持つと、この情報が復元できなくなる。

2.6 lut_flat — 縮約済み dense 平坦ネットリスト(配備専用)

Section titled “2.6 lut_flat — 縮約済み dense 平坦ネットリスト(配備専用)”

2 入力 lut_layer の直列鎖を export/netlist_reduce.py で lossless に縮約 (定数・パススルー・NOT・CSE・未参照の除去)した 1 枚の平坦 DAG。 griffith deploy bundle --dense-flat(実体は deploy/flatten_dense.py)が lut_layer 列を置換して作る。学習側から作るノードではなく、torch へも戻せない (build_torch は NotImplementedError)。HDL 生成の対象外で、C ランタイムだけが実行する。

lut_flat は置換した最終 lut_layer と同じ out_width 本のビット列を返す。 後段の group_sum は無改造で、整数スコア(グループ内 popcount)の意味論も変わらない。 縮約で定数・パススルー・反転に解決した最終層ゲートは、outputs の参照として lut_flat の中で最終出力ビット列に再構成される。

params意味
in_width入力ビット数(前段の出力幅)
out_width出力ビット数(= 置換した最終層の幅 = group_sum.in_width)
gates[tt, a, b] のリスト。tt は 0..15 の真理値表(lut_layer と同じ規約: bit index = (b<<1)|a)、a / b は信号番号
outputs長さ out_width。出力ビット i の参照 = 2*信号番号 + 極性(極性 1 = 反転)

信号番号(a / b / outputs が指す添字):

信号意味
0定数 0(定数 1 は信号 0 の反転 = outputs の値 1)
1 … in_width入力ビット k → 信号 1+k
in_width+1 …ゲート g の出力 → 信号 in_width+1+g

ゲート g の a / b は自分より前の信号(< in_width+1+g)のみを指せる(トポロジカル順)。 極性(NOT)はゲート入力側に持たない — 縮約器が下流ゲートの真理値表へ吸収済みで、 極性が残るのは outputs だけ。

3. 実物を見る — XOR 回路の IR

Section titled “3. 実物を見る — XOR 回路の IR”

チュートリアル 1 と同じ 2 層 LUT + GroupSum の XOR モデルを学習し、 export_ir で抽出した 実際の JSON である(examples/04_export_hdl.py の生成物)。 長い indices は省略記号で畳んであるが、それ以外は生成されたそのままの形。

読みどころを 4 つ。

  1. 幅が鎖のようにつながっている — x(2)→ n0(in 2 / out 16)→ n1(in 16 / out 16) → n2(in 16 / k=2)→ y(2)。ここが 1 か所でもずれると validate が幅不整合で落ちる
  2. 2 段目の indices は最大 15 — 入力幅 16 なので 0 ≤ v < 16。1 段目は入力幅 2 なので 0/1 しか出ない
  3. 真理値表が学習の成果物 — 2 段目に 0x6(XOR)と 0x9(XNOR)が並んでいる。 学習後の eval() で各ゲートが 1 個の論理関数に確定した結果である
  4. dst_slot がどのエッジにも無い — すべて単入力ノードで slot 0 だから、規約どおりキーが省略されている

パラメータ化は IR に残らない

train_info.parameterization は "softmax" と記録されているが、これは参考情報である。 independent でも iwp でも、学習方式が何であれ抽出後の IR は真理値表の集まりに統一される。 下流(シミュレータ・HDL)を学習方式から完全に切り離すための正規化であり、 パラメータ化を選ぶ の選択がここから先へ漏れることはない。

大配列のサイドカー退避

Section titled “大配列のサイドカー退避”

MNIST 級のモデルでは indices が数十万要素になる。save_ir は要素数が inline_threshold(既定 65536)を超える配列を .npz サイドカーへ退避し、 JSON 側には参照だけを残す。

load_ir は同じディレクトリの .npz を自動で解決する。truth_tables は常に JSON 内にインライン (hex 文字列なので大きくならない)。 なお、エディタが HTTP でやり取りする経路(ir_to_dict / ir_from_dict)は 一括送受信のため常にインライン展開で、$data 参照には対応しない。

4. 検証ルール(validate)

Section titled “4. 検証ルール(validate)”

validate(ir, target=...) はエラーを例外で送出し、警告をリストで返す。 HDL を書き出す前に必ず通す。ここで落とせば、合成ツールで初めて気づく事故を防げる。

#検査落ちる条件
1ノード型NODE_TYPES に無い type
2id の一意性ノード id の重複
3エッジ端点src / dst が未定義の id を指す
4ノード固有 params形状・値域違反(indices 形状、真理値表の値域、in_width % k、bits が 0/1 以外 …)
5slot 整合多入力ノードで slot が欠番・重複、単入力ノードに 2 本目のエッジ
6幅整合src の出力幅 ≠ dst の当該 slot の入力幅(出力ポートへの接続も含む)
7DAG 性循環、または到達不能な依存
8未使用ノード出力がどこにも繋がっていない → 警告(エラーではない)
9HDL 追加制約target='hdl' のとき blackbox ノード、add(mode='sum')、lut_flat

lut_flat の params は 4 で検査される(gates の tt が 0..15、a / b が前方参照でない、 outputs の長さ = out_width と信号数の範囲内)。 9 のうち blackbox と add(mode='sum') は「原理的に回路にできないもの」である。blackbox は実数の非論理層なので ハイブリッドモデルは論理部分だけを切り出してエクスポートする。

5. 実行順序の決め方

Section titled “5. 実行順序の決め方”

nodes 配列の並びは実行順ではない。実行順は エッジからトポロジカルソートして決める (IRGraph.topological_order())。循環していれば検査 7 で落ちる。

「最終出力はどのノードか」も推測しない。IRGraph.output_source() が 最初の出力ポートへ繋がっている src を返し、シミュレータ・torch ビルド・HDL 生成の 3 者がこの同一のヘルパーを使う。直列グラフではトポロジ末尾ノードと一致するが、 fanout や未使用ノードがある DAG では「末尾 = 出力」が成り立たないため、規則を 1 か所に固定している。

7. バージョニング方針

Section titled “7. バージョニング方針”
  • IR_FORMAT は "magicdelta-ir" 固定、IR_VERSION は現在 "0.2.0"
  • v0.2 は v0.1 を完全に読める。 dst_slot の無い v0.1 の JSON は読み込み時に 0 として扱われ、 出力時も dst_slot=0 はキーごと省略されるので、v0.1 相当のグラフは v0.1 と同じ JSON に戻る
  • 後方互換の原則: 新しいフィールドは既定値つきの任意フィールドとして足し、 既定値のときは JSON に書かない。これで「新機能を使っていない IR」は表現が変化せず、 差分レビューもゴールデンデータも壊れない
  • format が一致しないドキュメントは読み込み時に拒否される。 一方 version は読み込みを止めない(前方互換は保証しないが、検査 1〜9 が実質のゲートになる)
  • ノード種別の追加は加算的に行う。既存ノードの params の意味を変えるような破壊的変更は マイナー版を上げ、設計判断の記録 に理由を残す
