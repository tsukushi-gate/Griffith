圧縮と最適化の一覧

griffith deploy は、あなたのモデルを配るまでの途中で、いくつもの圧縮と最適化を行う。 このページはそれを 1 か所に全部並べた一覧 である。「勝手に何をされているのか」「切りたいときはどうするか」「本当に効くのか」がここで分かる。 使い方そのものは デプロイキット クイックスタート、モデルを用意する手順は デモモデルを用意する、 GPU は GPU へデプロイする、ブラウザは ブラウザへデプロイする を参照。コマンドの全オプションは CLI リファレンス、バンドルの形式は 配布バンドル仕様 にある。

まず安心してよいこと

ここに載っているものは、出力の整数値を変えない ように作られている(学習済みモデルの精度は落ちない)。 変換のたびに、元の IR の ir/simulate.py と整数で突き合わせて確かめ、1 つでも違えば止まるか、その最適化だけを捨てる。 遅くなる実測が見つかったものは、既定では OFF にして「条件を満たしたときだけ自動 ON」か「自分で明示したときだけ ON」にしてある。

Section titled “一目でわかる表”

まず全体の流れを 1 枚で示す(上から下へ進む)。箱の中の数字は、実在する 3 つのモデル(XOR / HAR k6000 / 顔検出)のゲート数が各段でどう減るかの実測である。

自分のモデルにどれが効くか

Section titled “自分のモデルにどれが効くか”

上の表を「自分のモデルとターゲット」から逆引きするための図である。dense は 2 入力 lut_layer の列、削減率は平坦化したときの実効ゲートの削減率を指す。上から順に答えていけば、既定で自動的に入る最適化と、自分で選ぶもの(C の入口の呼び分け)が分かる。

バンドル段(griffith deploy bundle)

Section titled “バンドル段(griffith deploy bundle)”

bundle は、モデルの JSON から 配布バンドル を作る。バンドルは全ターゲット(C / CUDA / Metal / Web)が共通で読むので、ここで行う圧縮は 全ターゲットに効く。 レベルは --compress {none,fast,max}(既定 fast)で選ぶ。モデルが dense でも conv2d でも同じ意味になる。

レベル意味
noneIR を書き換える圧縮をしない(圧縮導入前と 1 バイトも変わらない出力)
fast(既定)秒で終わる lossless 削減をすべて行う。dense は sweep、conv2d は再合成(探索上限 4)
maxfast に加えて、探索上限 5 と ir/simulate による追加検証を行う(実モデルで分オーダー)

個別フラグ(--sweep / --no-sweep / --resynth lossless)は 指定すれば --compress より優先 される。 適用の順番は 再合成 → sweep(→ 平坦化を焼き込むなら最後)である。

conv2d の命令列化(常時)

Section titled “conv2d の命令列化(常時)”

conv2d の重み共有ゲート木は、ゲート数をそのまま持たず、自明なゲート(定数・パススルーなど)を畳んだ 命令列 にしてバンドルの programs 節に焼く。 ターゲット側はこの命令列をそのまま実行するだけでよく、縮約を自分で実装しなくて済む。IR は変えない。 どのレベルでも行われ、結果は about.compress.always に記録される。

  • 効果: 実モデルでゲート数が 59.7〜95.1% 減る(モデル依存)。顔検出では 14,784 → 1,077 ゲート(-92.7%)
  • 検証: 書き出す前に、全木の真理値表を全数で照合する。--no-verify で省けるが、デバッグ用で通常は使わない

sweep(dense のみ)

Section titled “sweep(dense のみ)”

dense(lut_layer の列)から、定数に決まるゲート・同じ働きの重複ゲート(CSE)・誰にも使われないゲートを取り除く。 conv2d を含むモデルには掛けず、スキップした理由を about.compress.skipped に残す。

  • 効果(gates_before → gates_after): XOR 32 → 22、HAR k6000 36,000 → 28,636、k600 2,400 → 1,989、MNIST 4,000 → 3,615(-10〜20%)
  • 検証: 書き出す前に、ランダム入力(既定 8 件)と、あれば実データ(demo_samples)で元の IR と整数一致を確かめる。1 件でも違えば中止する
  • 効かないもの: パススルー / NOT ゲートは層から除けない(平坦化の段で畳まれる)

下の図は、デプロイキット クイックスタートの examples/06_deploy_c/export_model.py と同じ手順で学習した XOR 回路に、実際に sweep を掛けた前後である。 左の灰色(定数)と黄色(重複)の 10 ゲートが第 1 層から消え、32 → 22 になる。右の点線の箱は「1 入力のゲート」で、層の形を保つために sweep では残り、後段の平坦化で配線に畳まれる。両側で class 0 / class 1 のスコアが同じことも確かめられる。

conv2d の再合成(conv2d のみ)

Section titled “conv2d の再合成(conv2d のみ)”

conv2d の木を、同じ関数を より少ないゲートで 作り直す。ゲート数が下限に達している木は探索しない(厳密な下限スキップ)ので速い。

  • 効果: 顔検出 1,279 → 1,077 ゲート(-15.8%)を 1.2 秒で(Apple M3。ブラウザデモ用の公開モデル tools/webbench/public/models/det_face_lut_k256.json での値。デモモデルを用意する の顔検出は wandb の別チェックポイントから作るので、命令列化後 2,686 → 再合成後 2,319 と数が違う)。コードサイズ(model.c)-4〜7%、バイナリ -9〜10%、配信サイズはほぼ不変(-0.6〜1.7%)
  • 速度(レイテンシ)は変わらない。効くのはフラッシュが小さい環境
  • 検証: fast は木ごとの真理値表の全数一致と、ランダム入力・実サンプルの前向き計算。max と --resynth lossless は ir/simulate による照合も加える

下の図は、顔検出モデル(det_face_lut_k256)の conv2d ノード n6_lutconv2d、出力チャネル 13 の木 1 本を追ったものである。 (a) 学習したままの深さ 3 の木は 7 ゲートだが、パススルーと未使用のゲートを畳むと (b) の 5 命令になり(命令列化)、再合成で (c) の 3 ゲートになる。(d) で 16 通りの入力すべてで 3 つの出力が一致すること、(e) で「入力 4 本に本当に依存する関数は 3 ゲート未満にできない」という下限により、多くの木は探索せずに飛ばせることが分かる。

平坦化を IR に焼く(任意)

Section titled “平坦化を IR に焼く(任意)”

bundle --dense-flat は、次節の平坦化を バンドルの IR に焼き込む 互換経路である。焼いた lut_flat ノードは C / Web / CUDA / Metal のすべてで実行できる(Web と GPU は現在対応)。 通常は不要で、codegen-c / codegen-web の自動判定に任せればよい(バンドルは全ターゲット共通のまま保たれる)。

前処理の整数化(画像入力のみ)

Section titled “前処理の整数化(画像入力のみ)”

画像入力モデルでは、入力の符号化(preproc)を 整数だけの記述子(preproc_desc)にしてバンドルに焼く。 端末側は浮動小数点を使わずに前処理でき、C ランタイムはこの記述子をそのまま実行する。バンドルを読むときに、preproc から再構築した記述子との一致も確かめられる(griffith deploy info --strict)。

失敗したときの扱い(fail-safe)

Section titled “失敗したときの扱い(fail-safe)”

自動で掛けた圧縮の途中で変換や検証が失敗した場合は、その圧縮だけを捨てて続行 する(圧縮なしの IR は元から正しい)。 理由は about.compress.skipped に残り、警告が標準エラーに出る。--sweep や --resynth lossless のように 自分で明示したフラグの失敗は、そのままエラー になる。

C 生成段(codegen-c / verify-c)

Section titled “C 生成段(codegen-c / verify-c)”

C ランタイムは依存ゼロの C99 で、実行時のヒープ確保もない。ここでは、C のコードを作るときに入る最適化を挙げる。

平坦化 --dense-flat(自動)

Section titled “平坦化 --dense-flat(自動)”

dense を、パススルー・定数・NOT・重複を畳んだ 平坦ネットリスト(lut_flat)にして、1 ゲート 1 回の表引きで実行する C を出す。 変換は C を作るときに メモリ上だけ で行い、バンドルのファイルは変わらない。

  • 既定は auto。試しに平坦化して、実効ゲートの削減率が 25% 以上 なら採用し、未満なら従来のカーネルにする。閾値はホスト実測の損益分岐(約 26%)に余裕を見た値
  • 対象は 2 入力の lut_layer が並ぶ dense。この節は C の話で、Web(codegen-web)も既定で平坦化する(閾値なし、下の「Web」節)。CUDA / Metal も lut_flat を実行できるが、既定では平坦化しない(opt-in、下の「GPU での平坦化」節)
  • 検証: 変換の前後の simulate を、ランダム入力 16 本と実データで整数比較してから使う。verify-c は元バンドルの simulate を基準にするので、この変換が lossless であることの実証にもなる
  • 効果: ESP32 の実機で HAR k6000 は 26.60 ms → sweep で 21.17 ms → sweep と平坦化で 12.69 ms(全件スコア一致)。ホストでは、削減率 36.5% で 1.23 倍、55.0% で 1.66 倍、75.0% で 2.52 倍
  • 代償: 作業 RAM(MDL_CTX_BYTES)が増える(信号表のぶん。HAR 相当の合成で 12,000 B → 26,800 B)。RAM が厳しいマイコンでは --dense-flat off

下の図は、sweep 後の XOR 回路(22 ゲート、左)を平坦ネットリストにした結果(右)である。 左の青い点線(パススルー / NOT)と黄色(重複)はすべて右の信号表への参照になり、実際に計算するゲートは s3〜s5 の 3 つだけが残る。NOT はゲートを使わず、出力参照の極性ビット(赤い線と丸)で表す。

ESP32 実機での効き目は次のとおり。モデルごとに縦軸が違うので、棒の高さは各パネルの中で比べること。どのモデルでも、既定(sweep + 平坦化)が最も速く、整数のスコアは 3 通りとも一致した。

バッチ軸パック入口 mdl_infer_batch_packed(自動)

Section titled “バッチ軸パック入口 mdl_infer_batch_packed(自動)”

平坦化を採用したときは、32 枚を 1 ワードに詰めて同時に評価する入口 mdl_infer_batch_packed も既定で生成される(MDL_DENSE_BATCH=32)。 ホスト(Apple M3)での 32 枚あたりのスループットは、1 枚ずつ流す lut_flat の HAR k600 で 1.7 倍、k2400 で 4.1 倍、k6000 で 5.9 倍、MNIST で 5.4 倍だった。 追加の flash は約 0.7KB、作業バッファは呼び出し側が MDL_DENSE_WORK_BYTES ぶん用意する。 verify-c はこの入口も、1 枚ずつの mdl_infer とは別に 33 枚で simulate と整数照合する。

下の図は、何をしているかを XOR の平坦ネットリスト(3 ゲート)で示したものである。 32 枚の入力を転置して「1 ワード = 1 つの信号の 32 枚ぶん」にすると、信号表の各ゲートは 32 ビットのワード演算 1 回で 32 枚を同時に計算する。橙の枠はサンプル 5 の列で、上から下まで追うとそのサンプルのスコアになる。

ホスト(Apple M3)で 32 枚を流したときの 1 枚あたりの時間は次のとおり。モデルが大きいほど(信号表が長いほど)効く。

1 枚だけ流す用途には使わない。 1 枚で呼ぶと mdl_infer より 5〜12 倍遅い。遅延を重視するなら mdl_infer を使う。 --dense-batch 0 で生成を止め、--dense-batch N で最大枚数を変えられる。平坦化しない dense でも --dense-batch N を明示すれば、層パックの入口が生成される。

GPU(codegen-cuda / codegen-metal)

Section titled “GPU(codegen-cuda / codegen-metal)”

GPU の最適化は「効くかどうかがモデルと batch で逆転する」ので、実測で勝てた条件のときだけ自動で ON にしてある(auto='measured')。 上書きの方法は、明示フラグを付けるか、--no-auto で自動選択ごと切る(--no-auto では、指定しなかった項目が自動選択の導入前の値、つまり split・dense_fuse OFF・dense_packed OFF に戻る)。

GPU での平坦化(lut_flat、opt-in)

Section titled “GPU での平坦化(lut_flat、opt-in)”

平坦ネットリストのゲートは「自分より前の信号」を参照するだけなので、そのままでは GPU の 1 スレッド = 1 ゲートで並べられない。 そこで生成時に、各ゲートへ ASAP の段番号(入力 = 0、ゲート = 1 + 入力の段の最大)を振り、段ごとにまとめ直す。同じ段のゲートは互いに依存しないので、段ごとに 1 回の起動(または 1 回のバリア)で全ゲートを同時に評価できる。 段数は元の lut_layer の層数を超えない。下の図は、HAR の実モデルで元の層・sweep 後の層・平坦化後の段のゲート数を並べたものである。

GPU の既定は平坦化しない(--dense-flat off)。使うときは codegen-cuda / codegen-metal / verify-metal に --dense-flat auto(削減率 25% 以上で採用)か on を付ける。bundle --dense-flat で焼いた lut_flat は既定にかかわらずこの方式で実行される。

実行方式は 3 通りある(Python API の lut_flat_mode)。既定の auto は、信号表が共有メモリ(Metal 32KB / CUDA 48KB)に収まれば fused を選ぶ。

方式中身
fused1 スレッドグループ = 1 枚。信号表を共有メモリに置き、段の間だけバリアを張る。起動は 1 回
levels段ごとに 1 回起動する。信号表はデバイスメモリ
packed段ごとの起動で、32 枚を 1 語に詰めて評価する(batch 32 以上)

ゲートは約半分になるが、GPU では速くなるとは限らない。Apple M3 の Metal で測ると、k600 はわずかに速く、k2400 は勝ち負けが混ざり、k6000 は平坦化しない最良(dense_packed / dense_fuse)より遅かった。 GPU は 1 回の推論でゲート数より起動・転送の固定費が大きく、batch=1 ではどの方式も 0.32〜0.40 ms である。 遅くなる条件: 数万ゲート級の大きいモデル(k6000 = 平坦化後 15,124 ゲート)を batch 128 以上で流すと、平坦化で 0.47〜0.71 倍に落ちた。小さいモデル(k600)や batch 32 前後ではほぼ同じか少し速い。CUDA の lut_flat は NVIDIA 実機で実行・計測していない(生成コードの構文検査まで)。平坦化を試すなら、自分のモデルと batch で既定(off)と比べてから選ぶこと(scripts/bench_dense_gpu.py --dense-flat fused)。

Web の実測

Section titled “Web の実測”

--slim は圧縮ではない
