4. デプロイする

学習した回路を、PyTorch なしで、手元の C コンパイラだけで動かす。 MNIST の「論理ゲート4000個」を、IR → 配布バンドル → C99 ソースの順に 書き出し、cc でビルドして、テスト画像1000枚を C だけで推論する。

このページの核心は C が返す整数スコアが PyTorch の hard eval と1要素も違わないこと。 学習した回路が、書き出し・コード生成・コンパイルを経ても「同じ回路のまま」であることを assert で固定してから、配信サイズ(約58KB、gzip で約19KB)・実行時メモリ(4KB)を数える。 1枚あたりの推論時間は著者環境(Apple M1 Max・1コア・cc -O2)で約3マイクロ秒だった (機種で変わる値なのでページの出力には載せず、latency.json へ書き出す)。最後はゲート数を 変えた回路を並べて、配信サイズがゲート数にほぼ比例することを確かめる。

この回路を ESP32 や iPhone に載せる手順は ESP32 に載せる・ iPhone に載せる で続き、デプロイキットの全体像は デプロイキット クイックスタート にある。

このページで学ぶこと

  1. 学習済みモデル → IR → 配布バンドル → C ソース → 実行ファイル、という出口の全段
  2. C の整数スコアが PyTorch hard eval・IR simulate と完全一致することの確かめ方
  3. 配信サイズ・実行時メモリの測り方と、ゲート数に対するサイズの伸び方(µs/枚は機種依存なので latency.json に記録する)

前提

  • 1. MNISTを学習する — ここで運ぶ回路そのもの
  • 3. HDLへエクスポート — IR と3段等価性の考え方
  • デプロイキット クイックスタート — 先に XOR で出口の全体を軽く通したいとき(任意)

▶ Colabで開く(リポジトリ公開後に有効化)

MNISTを学習し、そのまま依存ゼロの C99 で動かす(デプロイキット)例。

MNIST で学習した「論理ゲート4000個の回路」は、PyTorch の中でしか 動かせない。ここではその回路を PyTorch なしで、手元の C コンパイラだけで動く形に 包んで届けるところまでを、1本のスクリプトで通す。

道のりは次の6段で、すべてこのファイルの中で実行する。

橙が PyTorch の世界、緑が論理回路として扱う世界、青が整数のスコアである。 最後の「完全一致」が主役で、C が返す整数が PyTorch の hard eval と1個も違わないことを 確かめてから、配信サイズと速さを測る。

実行: uv run python examples/29_deploy_mnist.py 期待結果: hard accuracy 0.85前後 / C推論とPyTorchが1000枚×10クラスで完全一致 (Cコンパイラ cc / clang / gcc が必要。成果物は out_examples/deploy_mnist/ に出る)

準備: import・乱数種・出力先

Section titled “準備: import・乱数種・出力先”

学習側は MNIST とまったく同じ道具立てで、デプロイ側に使うのは griffith_logic.deploy の4つの部品である。

  • build_bundle / save_bundle / load_bundle … 学習済みモデルを 配布バンドル (回路の IR とクラス名を1ファイルにしたもの)へ包み、書き出し、読み戻す
  • generate_c … バンドルから自己完結した C ソース(model.c / model.h)を生成する
  • verify_c_matches_simulate … 生成した C を実際にビルドして、IR の参照実装 (simulate)と整数で突き合わせる「出荷前ゲート」

乱数種を固定しているので、毎回同じバイト列のバンドルができる (ESP32 や iPhone のデモが読むファイルとして使えるように)。

出力先とハイパーパラメータ

Section titled “出力先とハイパーパラメータ”

成果物はすべて out_examples/deploy_mnist/ に出す。mnist.bundle.json という ファイル名は固定してあり、他のデモ(組み込み・スマホ)がそのまま読む。 学習レシピは MNIST と同じ縮小版(2層×2000ゲート・4000 iter)で、 CPU で1〜2分に収まる。

データセット: 画像を 8bit のまま持つ

Section titled “データセット: 画像を 8bit のまま持つ”

MNIST の 20x20 を読む。MNIST と違うのは、画像を 0〜255 の 整数(u8)でも持っておく点である。デバイスに届くのは「カメラやファイルから来た 8bit の画素」で、0.37 のような実数ではないからだ。

PyTorch 側の hard eval は x.round() で二値化していた(0.5 を超えたら 1)。 画素値 k/255 > 0.5 は k >= 128 と同じなので、C 側は u8 の画素を閾値 128 で 比べるだけで同じビット列が得られる。この1行の二値化を、後で書く C のドライバに 持たせる。

学習: MNIST ページと同じ回路を作る

Section titled “学習: MNIST ページと同じ回路を作る”

モデルも学習ループも MNIST と同一で、LutLayer 2段 + GroupSum を普通の PyTorch で回すだけである。ここで見るべきは精度ではなく、学習が終わった 時点の model.eval()(= 離散化された回路)が、この先の出口すべての基準になること。

IR とバンドル: 学習済みモデルを1つのファイルに包む

Section titled “IR とバンドル: 学習済みモデルを1つのファイルに包む”

出口の最初の一歩は HDLエクスポート と同じで、 export_ir が学習済みモデルを IR(真理値表の集まり) へ確定させる。 IR は PyTorch にも C にも依存しない、全ターゲット共通の真実源である。

validate(ir, target='hdl') は IR が回路として成立するか(ビット幅・配線の整合)を 検査する。ここで落ちるなら、C を作る前に直す。

入力の約束と、モデルJSONの中身

Section titled “入力の約束と、モデルJSONの中身”

バンドルに載せるのは IR と、クラス名(labels)である。入力は 400 ビットの 0/1 列(20×20 の画素を行優先に並べ、画素 >= 128 なら 1)と決めておく。 画像の前処理(閾値・正規化)をバンドルに載せる道もあるが、それが使えるのは 畳み込み(LutConv2d)から始まる画像モデルで、全結合の回路は C には ビット列そのものを渡すのが作法になる。ビット列にするのは Python か C のドライバの 仕事で、ここでは後者に1行で持たせる。

「{'ir': ...} だけを持つ辞書」が griffith deploy bundle の入力(モデルJSON)になる。

export_ir は IR のメタデータに書き出した時刻(created_at)を入れる。このままだと 実行のたびにバンドルのバイト列が変わる(gzip サイズも ±1B 揺れる)ので、下では 固定の時刻(FIXED_TIME)で上書きして、同じ学習結果なら同じバイト列にしている。

バンドルを作って書き出す

Section titled “バンドルを作って書き出す”

build_bundle が IR とラベルを束ね、save_bundle が1ファイルへ書く。 CLI なら griffith deploy bundle mnist_model.json -o mnist.bundle.json と同じ操作である。 配信サイズ(圧縮後)は gzip で測る。gzip.compress は既定だとヘッダに現在時刻を 入れるので、mtime=0 で固定して同じバンドルなら毎回同じバイト数にする。

C コード生成とビルド: model.c を作って cc に渡す

Section titled “C コード生成とビルド: model.c を作って cc に渡す”

バンドルを読み戻し(読み込み時に構造を検証する)、generate_c で C ソースを作る。 生成物は model.h(公開 API とサイズ定数)と model.c(static const の真理値表と、 それを順に評価する直線コード)の2本だけで、実行時のヒープ確保も浮動小数点もゼロ。 公開 API は mdl_infer(input_bits, scores) で、400 個の 0/1 を渡すと 10 個の整数 スコアが返る。

論理ゲートの評価そのものは、ランタイム(mdl_kernels.c、ソースで約60KB)が32ゲートずつ まとめてビット演算で行う。CLI なら griffith deploy codegen-c が同じことをする。

ホスト用のドライバを書いてビルドする

Section titled “ホスト用のドライバを書いてビルドする”

生成された mdl_infer(bits, scores) を呼ぶだけの小さな main を用意する。 u8 の画像 N 枚をファイルから読み、画素を 128 と比べて 400 ビットにしてから推論する。 これを N 枚×reps 回まわしてループ全体の時間を測り(二値化の時間も含む)、 最後の周回のスコアをファイルへ書く。時間は clock()(C 標準)で測るので 追加の依存はない。ドライバだけは malloc を使うが、それはホスト用の都合で、 モデル自身は作業領域をコンテキストの中に持つ。

C で推論し、PyTorch と整数で突き合わせる

Section titled “C で推論し、PyTorch と整数で突き合わせる”

テスト画像の先頭1000枚を u8 のまま書き出し、C の実行ファイルに食わせる (二値化は C のドライバがやる)。 返ってくるのは 1000枚×10クラスの 整数スコア(各クラスに割り当てた 200 ゲートのうち 1 を出した本数)である。

比べる相手は3つ。PyTorch hard eval(model.eval() の出力に tau を掛け戻した もの)、IR の参照実装 simulate(numpy の整数ビット演算)、そして C。 3者が1要素も違わないことを assert で固定する ── 学習した回路が、書き出しと コード生成と C コンパイルを経ても同じ回路のままであることの証明である。

出荷前ゲート: verify-c

Section titled “出荷前ゲート: verify-c”

上は「いま学習したモデル」を相手にした確認だった。verify_c_matches_simulate は もっと機械的で、ランダムなビット列を何本か作り、バンドルから C を生成・ビルドして IR の参照実装と突き合わせる(CLI の griffith deploy verify-c)。 手元のモデルや画像に依らず、回路そのものが C で正しく再現されることを見る関門で、 CI や出荷前のスクリプトにそのまま組み込める。

配信サイズと速さ: 何バイトで、1枚あたり何マイクロ秒か

Section titled “配信サイズと速さ: 何バイトで、1枚あたり何マイクロ秒か”

ここまでで「正しく動く」ことが分かったので、次は「どれだけ軽いか」を数える。 数字は3種類で、運ぶもの(バンドルのバイト数)、ビルドするもの(C ソース)、 走らせるのに要るもの(作業 RAM MDL_CTX_BYTES)と速さである。

速さ(µs/枚)は機種・実行ごとに揺れる数字なので、このページの出力には焼き込まない (計測は上でしていて、out_examples/deploy_mnist/latency.json に書き出す)。 著者環境(Apple M1 Max、1コア、cc -O2)での実測は 約 3 µs/枚(二値化込み、 約 33万枚/秒)で、手元で再実行すると桁は同じだが値は少し変わる。 バイト数のほうは回路が同じなら毎回同じ値である。

可視化: C が読んだ数字と、ゲート数に対するコスト

Section titled “可視化: C が読んだ数字と、ゲート数に対するコスト”

最初の図は、C の実行ファイルが返した予測をテスト画像に重ねたもの。 緑が正解、赤が誤答で、PyTorch と完全に一致している以上、赤はそのまま PyTorch hard eval の誤答でもある。

図1: C の予測をテスト画像に重ねる

Section titled “図1: C の予測をテスト画像に重ねる”

24枚を並べる。画像は回路が受け取った 20×20 の画素(u8)そのものである。

読み取り: 外れるのは 4 と 9、3 と 5 のような紛らわしい数字が中心で、 MNIST の誤分類と同じ傾向である。C は新しい誤りを一つも作っていない。

図2: ゲート数に対する配信サイズと速さ

Section titled “図2: ゲート数に対する配信サイズと速さ”

学習済みの回路は1つしか無いので、幅 K を変えた回路を作って並べる。サイズと速さは 回路の「形」だけで決まり、どの論理関数に学習されたかにはほとんど依らないので、 学習していない(乱数初期化の)回路で測ってよい。確かめるために、本当に学習した K=2000 の回路を星印で重ねる ── 乱数の回路の線の上に載っていれば仮定は正しい。

各点は「export_ir → バンドル → C 生成 → ビルド → 1000枚で計時」を丸ごとやり直したものである。 計時の結果(µs/枚)は機種で変わるので図にも出力にも載せず、latency.json へ書き出す。 図はサイズだけの決定的な図にしてある。

読み取り: サイズは3本とも傾き1(ゲート数が2倍なら大きさも約2倍)で、 星印(学習済み)は乱数の回路の線にそのまま載る。速さも同じ向きに伸び、著者環境 (Apple M1 Max、1コア、cc -O2)では 500 ゲートで約 0.4 µs/枚、8,000 ゲートで約 6 µs/枚 だった(傾きの細部は機種で変わるので latency.json を見て各自で確かめる)。 サイズと速さは回路の形で決まるので、運ぶ前に見積もれる ── 8,000ゲートでも配信は約110KB、gzip で約37KBである。
