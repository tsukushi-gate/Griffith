5. CNNをHDLへエクスポート

論理ゲート畳み込み(LutConv2d)+ OR プーリング + LUT 全結合の CNN を学習し、 丸ごと Verilog / VHDL へ変換する。畳み込みは IR 化の際に木レベルごとの lut_layer へ unroll され、padding の境界処理は真理値表の特殊化に畳み込まれる。

このページで学ぶこと

  1. LutConv2d + OR プーリング + LUT 全結合という論理ゲート CNN の組み方
  2. 畳み込みが IR 化で木レベルごとの lut_layer へ unroll される様子
  3. padding の境界処理が真理値表の特殊化へ畳み込まれること

前提

  • 3. HDLへエクスポート — まず全結合の回路で出口を通す
  • 1. MNISTを学習する

このページについて

所要時間の目安: 約10分 / 実行環境: CPU のみ(GPU 不要) 元スクリプト: examples/05_cnn_export_hdl.py 手元で試す: notebooks/05_cnn_export_hdl.ipynb(このページと同じ内容の未実行ノートブック。uv run --group docs jupyter lab notebooks/ で開ける) コード出力はすべて 実際に実行した結果をそのまま埋め込んでいます。

▶ Colabで開く(リポジトリ公開後に有効化)

CNN(論理ゲート畳み込み)のHDLエクスポート例。

LutConv2d(木構造)+ ORプーリング + LUT全結合 + GroupSum のCNN分類器を 小タスクで学習し、丸ごとVerilog/VHDLへ変換する。paddingの境界処理は 真理値表特殊化で自動的に畳み込まれる。

04_export_hdl.py の全結合版に対して、こちらは畳み込みを含むモデルでも 同じ手順がそのまま通ることを示す。畳み込みは「同じ重みを位置ごとに使い回す」 構造だが、回路には重みの共有という概念が無いため、IR化の際に全位置へ展開(unroll) される。ゲート数がどれだけ膨らむかを実際に数えるのもこのスクリプトの目的。

このモデルの形(実測値つき)

緑が「ビット(0か1)しか流れない論理の世界」、橙が「実数」。 実数が現れるのは最後の GroupSum だけで、それより手前は全部ゲートの網である。

LutConv2d の中身(1画素ぶんの木)

リーフ数は n_inputs ** tree_depth = 2 ** 2 = 4、内部ゲート数は 3。 この木を4チャネルぶん持ち、それを画像の全64画素に当てるので 4ch x 64画素 x 3ゲート = 768ゲートになる。

どうやって実現しているか(専門用語はその場で言い換える)

  • 画像を最初から0/1にしている — 論理ゲートに入るのは電圧のHigh/Lowだけなので、 回路が読めるのは「ビット」だけ。実画像を使うときも、閾値処理や thermometer encoding(明るさを何段階かの目盛りビットに開く方法)で二値化してから入れる
  • 畳み込み = 小さな窓を画像の上でずらしながら、同じ回路を当てること。 ここでは 3x3 の窓(受容野)を1画素ずつずらして、どの位置でも同じ木を評価する
  • 木(tree) = ゲートを段重ねした小さな回路。1段目で 4ビット→2ビット、 2段目で 2ビット→1ビット。tree_depth はこの段数で、表現力のつまみになる
  • リーフの配線はランダムに固定される — 9ビットのうちどの4本を見るかは 層を作った瞬間に決まり、学習では動かない。学習で変わるのは各ゲートが 「16種の2入力論理関数のどれになるか」だけ
  • プーリング = 近くの4ビットをまとめて1ビットに縮める操作。実数NNの max pooling は ビットの世界では OR(どれか1つでも1なら1)そのもので、ORゲート1個で済む
  • padding = 画像の外側を0で埋めること。境界では窓が画像からはみ出すが、 はみ出した先は定数0なので、回路にするときは真理値表へそのまま畳み込まれて消える
  • unroll(展開) = 回路には重みの使い回しが無いので、位置の数だけ回路を複製すること。 PyTorch では 12ゲートぶんの重みでも、ハードウェアには 768ゲートが並ぶ
  • GroupSum = ゲートの出力ビットをクラスごとに足し算して点数にする出口。 ここで初めて実数になり、argmax でクラスを決める

図では、まずモデル全体を実データ付きのアーキテクチャ図で俯瞰し、次に回路が見ている ビットの特徴マップ、全結合ヘッドの実回路、unroll後にどのIRノードでゲート数が膨らむか、 焼かれた回路の「部品表」(16種の2入力論理関数の内訳)、そして PyTorch の hard eval と IR simulate がスコアまで完全一致することを順に見ていく。

実行: uv run python examples/05_cnn_export_hdl.py 期待結果: IR simulate予測がPyTorchと一致、(iverilogがあれば)照合ALLPASS

準備: 畳み込み版の出口に必要なAPI

Section titled “準備: 畳み込み版の出口に必要なAPI”

3. HDLへエクスポートの全結合版に、畳み込み用の部品が加わる。

  • LutConv2d … 論理ゲート版の畳み込み。3x3 の窓の中から数ビットを選び、 2入力ゲートの木で1ビットを出す層
  • OrPooling2d … ビットの世界での max pooling。近くの4ビットの OR を取るだけ
  • write_verilog / write_vhdl … 同じ IR から2種類の HDL を書き出す
  • truth_tables_from_conv / gate_id_from_tt_n2 … 学習後のゲートを真理値表として 取り出し、16種の2入力論理関数のどれかへ対応付ける(図の中でゲート名を出すのに使う)

データセット: 左右どちらが明るいかを当てる

Section titled “データセット: 左右どちらが明るいかを当てる”

8x8 の二値画像を作り、「左4列の1の個数 > 右4列の1の個数」をラベルにする。

なぜこのタスクか ── 局所的な窓を画像全体でずらしながら数を集める課題なので、 畳み込み + プーリングという構造がそのまま効く。しかも 8x8 と小さいので、 後段の IR 化・Verilog 生成・照合まで数秒で通せる。

入力を最初から 0/1 にしているのがポイント。論理ゲートに入れられるのは 電圧の High/Low だけなので、実画像を扱うときも閾値処理や thermometer encoding (明るさを何段階かの目盛りビットに開く方法)で二値化してから入れる。

モデル定義: 論理ゲートCNN

Section titled “モデル定義: 論理ゲートCNN”

4つの層を積むだけだが、実数 CNN の各部品がビットの世界で何に置き換わるかが すべてここに現れている。

  • LutConv2d(1, 4, kernel_size=3, tree_depth=2, padding=1) … 3x3 の窓(受容野)の9ビットから4本を選び、2入力ゲートを2段積んだ木で 1ビットを出す。tree_depth が木の段数=表現力のつまみ。 どの4本を見るかは層を作った瞬間にランダムに決まり、学習では動かない
  • OrPooling2d(kernel_size=2) … 実数 CNN の max pooling に対応する。 ビットの世界では「どれか1つでも1なら1」= OR そのものなので、ORゲート1個で済む (平均プーリングは加算器が要るので使わない)
  • LutLayer(64, 32) … 平坦化した64ビットを受ける全結合の LUT 層
  • GroupSum(k=2, tau=4.0) … 32ゲートを2クラスへ集計する出口。実数が現れるのはここだけ

学習と hard 評価

Section titled “学習と hard 評価”

学習は普通の PyTorch ループで300ステップ回すだけ。train() モードでは各ゲートが 「16種の論理関数の重み付き和」として連続的に振る舞うので勾配が流れる。

回路として固定されるのは eval() 以降で、そこで測る正解率が hard accuracy (= 焼いた回路としての正解率)である。ここが下がるようなら soft → hard の ギャップが大きい、という判断になる。

可視化: 実データが流れるアーキテクチャ図

Section titled “可視化: 実データが流れるアーキテクチャ図”

読み取り: hard accuracy は 0.76 前後。総ゲート数1000未満・学習300ステップの 極小レシピで、「左右どちらが明るいか」という広域の集計が偶然(0.5)を大きく超えて解けている。

ここからが本ページの中心で、まず実データを流し込んだアーキテクチャ図を1枚作る。 以下の数セルはその図のための下ごしらえ(配色・ヘルパー関数・中間ビットの取り出し)である。

図1: ビットが最後の層まで流れていく様子

Section titled “図1: ビットが最後の層まで流れていく様子”

上段は1枚の画像が層を通っていく実際のビット(入力8x8 → conv 4ch → プーリング → 平坦化 → 全結合 → 最後にGroupSumの実数スコア)。下段左は受容野のどの位置を 木のリーフ L0〜L3 が見ているか、下段中央は1画素ぶんの木の中身 (実際に学習で確定したゲート名入り)、下段右はunroll 後のゲート数の内訳である。

unroll(展開) とは、回路には重みの使い回しが無いので、畳み込みを全出力位置ぶん 複製することを指す。PyTorch 側では 12 ゲート分の重みでも、ハードウェアには 768 ゲートが並ぶ ── その計算がこの図の右下に書き出されている。

読み取り: 上段を左から右へ追うと、値が最後まで 0/1 のままであることが分かる (橙で描かれた右端の GroupSum スコアだけが実数)。下段右の内訳では、 共有された 12 ゲートが unroll で 768 ゲートへ、プーリングと全結合を足して 全体 864 ゲートに膨らむ。 PyTorch のパラメータ数ではなく、この unroll 後のゲート数が FPGA の面積である。

図2: 回路が見ている入力と、畳み込み層が出したビット

Section titled “図2: 回路が見ている入力と、畳み込み層が出したビット”

上段が入力の 8x8 二値画像(=回路の入力線64本)、下段が LutConv2d の4チャネル出力。 実数 CNN の特徴マップは実数だが、ここでは eval() なので純粋な 0/1 である。

読み取り: 4つのチャネルはそれぞれ違う模様を出しており、同じ入力に対して 別々の論理関数の木が働いていることが分かる。入力も出力もビットなので、 このまま次の層(OR プーリング)へ配線として繋がる。

図3: 全結合ヘッドを実際の回路図として見る

Section titled “図3: 全結合ヘッドを実際の回路図として見る”

モデル後半の全結合ヘッド(LutLayer(64→32) + GroupSum(k=2))だけを取り出し、 実際の回路図として描く。灰の箱64個がプーリング後のビット、 緑の箱32個が確定したゲート、橙が2クラスの実数スコアである。

読み取り: ノードに XOR や NAND といった具体的な論理関数の名前が入っている。 このゲート名は export/discretize(IR と Verilog が使う唯一の離散化経路)から 取っているので、この図に描かれたゲートがそのまま生成される Verilog のゲートになる。

IR化とHDL生成

Section titled “IR化とHDL生成”

全結合版と手順は同じで、違いは export_ir に input_shape=(1, 8, 8) を渡すこと だけである(展開に画像サイズが必要なため。全結合なら input_width で足りる)。

ここで畳み込みが木のレベルごとの lut_layer へ unroll される。 padding=1 の境界処理も、はみ出した先が定数0であることを利用して 真理値表の特殊化として畳み込まれ、回路からは消える。 VHDL も同じ IR から生成できる ── ツールチェーンに合わせて選べばよい。

図4: unrollでゲート数がどこで膨らむか

Section titled “図4: unrollでゲート数がどこで膨らむか”

IR ノードごとのゲート数(out_width)を横棒で並べる。木の段(tree_depth)ごとに lut_layer ノードが並ぶので、どの段が面積を支配しているかが一目で分かる。 これが FPGA 実装面積の見積もりそのものになる。

読み取り: 畳み込みの level 0(1画素あたり2ゲート × 4ch × 64画素 = 512)が 最も大きく、全結合ヘッドの32ゲートは誤差の範囲でしかない。 面積を決めているのは層の「幅」ではなく、畳み込みを何画素ぶん展開するかである。

図5: 焼かれた回路はどんなゲートで出来ているか

Section titled “図5: 焼かれた回路はどんなゲートで出来ているか”

IR の各ゲートは真理値表を持つ。2入力なら16種の論理関数のどれか1つなので、 名前を付けて数えれば回路の部品表になる。生成 Verilog の 4'h8 >> {a, b} のような行と1対1に対応する情報である (ORプーリングは4入力LUTなので、この集計からは外してある)。

読み取り: 16種のうち AND が突出し、次いで A>B(= A かつ not B)が多い ── 「その位置のビットが立っているか」を数える方向の関数が選ばれている。 一方で定数 FALSE やパススルーも1割前後残る。これらは実質的に無効ノードか配線なので、 後段の論理合成ツールが削れる余地であり、実際に載るゲート数はこの集計より小さくなる。

golden model と照合する

Section titled “golden model と照合する”

全結合版と同じく、PyTorch hard eval と IR simulate を突き合わせる。 畳み込み版で1つだけ注意が要るのはスケール合わせで、GroupSum は tau で割った ロジットを返すのに対し IR のスコアは生の合計値なので、tau=4.0 を掛け戻してから比べる。

判定は「だいたい合っている」ではなくスコアがビット単位で一致することを要求する。 ここがズレるなら IR 変換のバグなので、閾値を緩めてはいけない。

図6: PyTorch(hard eval)と IR simulate が同じ回路であること

Section titled “図6: PyTorch(hard eval)と IR simulate が同じ回路であること”

同じ一致を2通りの見せ方で確かめる。左は64サンプル×2クラスのスコアの散布図 (横軸 PyTorch・縦軸 IR)、右はクラス0のスコアをサンプル順に並べた折れ線である。

読み取り(この図が最後なので先に書く): 左では全点が破線の y=xy=xy=x 上に乗り (整数値なので点が重なる)、右では PyTorch の太線の上に IR simulate の破線が 完全に重なる。これが3段等価性の1段目と2段目 ── ズレた点が1つでもあれば IR 変換のバグである。最後のセルで iverilog による3段目の照合結果も出力する。
