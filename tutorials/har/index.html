行動認識(UCI-HAR、スマホ加速度)

スマホの加速度から「歩く・座る・階段を上る」を当てる。腰につけたスマートフォンの 9 チャネル × 128 サンプル(2.56 秒)の生信号を、4 閾値の温度計符号化で 4,608 ビットにして、 9,000 ゲートの論理回路へ入れる。画像ではなくセンサの時系列を論理ゲートが受け取る最小の例である。

実測は hard accuracy 0.885(テスト 2,947 窓・訓練に居ない 9 人)。後半は デプロイする と同じ出口を通し、学習した回路を C99 に書き出して テスト窓すべてを C だけで推論 → PyTorch の hard eval と整数で完全一致を確かめ、 配信サイズ(約140KB)と実行時メモリ(6KB)を数える。1窓あたりの推論時間は著者環境 (Apple M1 Max・1コア・cc -O2)で約6.7マイクロ秒だった(機種で変わる値なのでページの出力には 載せず、latency.json へ書き出す)。

この回路を ESP32 や iPhone に載せる手順は ESP32 に載せる・ iPhone に載せる で続く。

このページで学ぶこと

  1. 実数のセンサ信号を温度計符号化(閾値は訓練データの分位点)で 0/1 の入力線にする方法
  2. 9ch × 128 点 × 4 閾値 = 4,608 ビットを受ける論理回路で、未知の被験者の行動を分類する流れ
  3. 同じ回路を C99 へ運び、テスト窓すべてで PyTorch hard eval と整数一致させる確かめ方

前提

  • 4. デプロイする — 後半の出口と同じ手順
  • 1. MNISTを学習する — LutLayer + GroupSum の基本

スマホの加速度から行動を当てる ── UCI-HAR を論理ゲートで学習して C へ運ぶ例。

腰につけたスマートフォンの加速度・ジャイロ(9 チャネル × 128 サンプル = 2.56 秒の窓)から、 歩く・階段を上る・階段を下りる・座る・立つ・横になるの 6 行動を当てる。 画像ではなくセンサの時系列を、論理ゲート網がどう受け取るかを見るページである。

論理ゲートが受け取れるのは 0/1 だけなので、実数の信号は入口で温度計符号化する。 各チャネルの値を 4 つの閾値(訓練データの 20/40/60/80 パーセンタイル)と比べ、 超えたかどうかの 4 ビットに置き換える。9ch × 128 点 × 4 閾値 = 4,608 ビットが、 そのまま回路の入力線になる。

後半は デプロイする と同じ出口を通す。 学習した回路を IR → 配布バンドル → C99 ソースへ書き出し、cc でビルドして、 テスト窓 2,947 本すべてを C だけで推論し、PyTorch の hard eval と 整数で完全一致することを確かめる。

橙が実数のセンサ信号、青が 0/1 のビット列とクラススコア、緑が論理回路である。

実行: uv run python examples/27_har.py 期待結果: hard accuracy 0.80 以上 / C 推論と PyTorch が 2,947 窓 × 6 クラスで完全一致 (初回は UCI の zip(約 60MB)を data-uci-har/ へダウンロードする。Cコンパイラ cc が必要)

準備: import・乱数種・出力先

Section titled “準備: import・乱数種・出力先”

学習側で使うのは load_uci_har(生信号の読み込み)と thermometer_encode (温度計符号化)の 2 つの新しい部品で、残りは MNIST と同じ LutLayer + GroupSum である。出口側は デプロイする と同じ griffith_logic.deploy の部品を使う。

出力先とハイパーパラメータ

Section titled “出力先とハイパーパラメータ”

成果物は out_examples/har/ に出す(har.bundle.json はファイル名固定)。 回路は LutLayer を DEPTH 段重ねて、最後に 6 クラスへ集計する。入力が 4,608 ビットと 広いので、MNIST(400 ビット)より 1 段目のゲートを多めに取る。 CPU で 3 分以内に収まる規模である。

データセット: 生の加速度・ジャイロ信号

Section titled “データセット: 生の加速度・ジャイロ信号”

load_uci_har は生の Inertial Signals を (N, 9, 128) の float32 で返す (初回だけダウンロードして data-uci-har/har_raw.npz にキャッシュする)。 9 つのチャネルは、体の加速度(body_acc、重力を除いた動き)・ジャイロ(body_gyro)・ 全加速度(total_acc、重力込み)の x/y/z である。ラベルは 0〜5 の行動番号。

被験者で分かれている点が大事で、訓練とテストに同じ人の窓は混ざらない (初見の人でも当てられるかを測る設定)。

データの出典: Jorge Reyes-Ortiz, Davide Anguita, Alessandro Ghio, Luca Oneto, Xavier Parra, “Human Activity Recognition Using Smartphones”, UCI Machine Learning Repository, 2013 (doi:10.24432/C54S4K)。ライセンスは CC BY 4.0。 データはリポジトリに同梱せず、UCI から取得する。

温度計符号化: 実数の信号を 4,608 ビットにする

Section titled “温度計符号化: 実数の信号を 4,608 ビットにする”

閾値は訓練データだけから、チャネルごとに 20/40/60/80 パーセンタイルで決める (fit_thermometer_thresholds)。テストの分布を使うと評価が楽観的になるので、 テスト側にも同じ閾値を当てる。分位点で切るので、どのビットも訓練データの 約 80/60/40/20% で 1 になり、偏りなく情報を使える。

thermometer_encode は (N, 9, 128) を (N, 9, 128, 4) の 0/1 に変える。reshape で 一列に並べたものが回路の入力線(チャネル → 時刻 → 閾値の順)で、4,608 本になる。

温度計になっているかの確認

Section titled “温度計になっているかの確認”

閾値は昇順なので、ある点で「高い閾値を超えた」なら必ず「低い閾値も超えている」。 この単調性(0001 のような並びが出ない)を全データで確かめる。

モデルと学習: 普通の PyTorch ループ

Section titled “モデルと学習: 普通の PyTorch ループ”

モデルは LutLayer を DEPTH 段と GroupSum(k=6) で、MNIST のときと形は同じである。 GroupSum は最終段のゲートを 6 組に分け、各組で 1 が立っている本数を数えて 6 クラスのスコアにする。学習ループも cross_entropy + Adam の普通の PyTorch で、 500 ステップごとに soft(学習中の姿)と hard(離散化した回路)の精度を並べて測る。

IR とバンドル: 学習済みモデルを1つのファイルに包む

Section titled “IR とバンドル: 学習済みモデルを1つのファイルに包む”

手順は デプロイする と同じ。export_ir が回路を IR へ確定させ、build_bundle / save_bundle が IR とクラス名を har.bundle.json へ包む。 入力は 4,608 ビットの 0/1 列(温度計符号化した結果)で、この符号化(閾値)は Python 側の仕事になる。閾値の表も har_thresholds.json に一緒に出しておく。

配信サイズ(圧縮後)は gzip で測る。gzip.compress は既定だとヘッダに現在時刻を入れるので、 mtime=0 で固定する。さらに export_ir は IR のメタデータに書き出した時刻(created_at) を入れるので、これも固定の時刻で上書きして、 同じ学習結果なら毎回同じバイト列・同じバイト数にする。

C コード生成とビルド

Section titled “C コード生成とビルド”

バンドルを読み戻して generate_c で model.c / model.h を作り、ランタイムと一緒に cc に渡す。ドライバは「ビット列のファイルを読んで mdl_infer を回し、 ループ全体の時間を測る」だけの小さな main である。

C で全テスト窓を推論し、PyTorch と整数で突き合わせる

Section titled “C で全テスト窓を推論し、PyTorch と整数で突き合わせる”

テスト窓すべて(2,947 本)の 4,608 ビットをファイルに書き、C の実行ファイルに食わせる。 返ってくる 6 クラスの整数スコアを、PyTorch hard eval・IR の参照実装 simulate・ C の 3 者で比べ、1 要素も違わないことを assert で固定する。

配信サイズと速さ: 2.56 秒の窓を何マイクロ秒で判定できるか

Section titled “配信サイズと速さ: 2.56 秒の窓を何マイクロ秒で判定できるか”

センサの 1 窓は 2.56 秒ぶんの記録なので、判定に使える時間は 2.56 秒ある。 それに対して C の推論はどれだけ速いか、運ぶものは何バイトか、を数える。

速さ(µs/窓)は機種・実行ごとに揺れる数字なので、このページの出力には焼き込まない (計測は上でしていて、out_examples/har/latency.json に書き出す)。 著者環境(Apple M1 Max、1コア、cc -O2)での実測は 約 6.7 µs/窓で、 判定に使える 2.56 秒の約 38 万分の 1(およそ 1e-6 倍)の時間である。 バイト数のほうは回路が同じなら毎回同じ値になる。

可視化: 波形と温度計ビット、そして混同行列

Section titled “可視化: 波形と温度計ビット、そして混同行列”

最初の図は、1 つの窓(テスト窓の先頭)の 9 チャネルの波形である。破線が 訓練データから決めた 4 本の閾値で、波形がどの線を超えているかが、そのまま 入力ビットになる。

図1: 9 チャネルの波形と閾値

Section titled “図1: 9 チャネルの波形と閾値”

行は体の加速度(上)・ジャイロ(中)・全加速度(下)、列は x/y/z。 この窓は「立っている」(STANDING)で、動きのチャネルは小さく揺れるだけである。 閾値の線が値域を 5 つの帯に切っている。

読み取り: 波形が破線を何本またぐかで、各時刻の符号(0000 / 0001 / … / 1111)が決まる。 閾値は分位点なので、よく動くチャネルほど線の間隔が広く、静かなチャネルでは 値が小さな範囲にぎっしり集まる ── 同じ「4 ビット」でも、信号の大きさに合わせて目盛りが 付いている。

図2: 混同行列と、行動ごとの正解率

Section titled “図2: 混同行列と、行動ごとの正解率”

C の予測と正解ラベルの対応表。行が正解、列が予測で、数字は窓の数。 PyTorch と完全に一致しているので、これは PyTorch hard eval の混同行列でもある。

読み取り: 間違いは「座る ↔ 立つ」と「歩く / 階段を上る / 階段を下りる」の 2つの仲間内に集中し、仲間をまたぐ取り違えはほとんど無い。腰につけたスマホでは座るも 立つも体がほぼ静止し、重力の向きがわずかに違うだけだからで、一方「横になる」は 重力の向きが大きく変わるので全窓を当てている。つまり回路の誤りは センサから見て本当に紛らわしい行動に偏っている。
