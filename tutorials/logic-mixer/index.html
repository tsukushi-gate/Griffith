LogicMixer(MLP-Mixer)— attentionなしで画像を混ぜる

attention を使わずに画像を混ぜる MLP-Mixer の論理ゲート版。画像を16トークンに刻み、 **token-mixing(転置して LutStack に通す)**と channel-mixing を soft-XOR 残差で 交互に積む。MNIST で hard acc 0.658。

見どころは「情報がどう混ざるか」の実測。1つのパッチだけを潰した入力との差分を追うと、 パッチ埋め込み直後は変化がそのトークンの行に閉じているのに、1ブロック通すと 隣のトークンへ漏れ出す(1ブロックあたり 1→2 token)。混ぜているのは誰かが絵で分かる。

このページで学ぶこと

  1. attention を使わずに画像を混ぜる MLP-Mixer を論理ゲートで組む方法
  2. token-mixing(転置して LutStack に通す)と channel-mixing の役割分担
  3. 1パッチだけを潰した差分で「情報がどこまで漏れ出すか」を実測する読み方

前提

  • ResNet(残差接続)の論理化 — soft-XOR 残差の素性
  • 1. MNISTを学習する

このページについて

所要時間の目安: 約8分 / 実行環境: CPU のみ(GPU 不要) 元スクリプト: examples/15_logic_mixer.py 手元で試す: notebooks/15_logic_mixer.ipynb(このページと同じ内容の未実行ノートブック。uv run --group docs jupyter lab notebooks/ で開ける) コード出力はすべて 実際に実行した結果をそのまま埋め込んでいます。

LogicMixer(MLP-Mixerの論理ゲート版)でMNISTを解く例。

MLP-Mixer(Tolstikhin et al., 2021)は「attentionを使わずMLPだけで画像を解く」 アーキテクチャで、2種類の混合を交互に積むだけの構成をしている:

LogicMixer はこの2つのMLPを LutLayerのスタック に置き換えた論理ゲート版 (griffith_logic/models/mlp_mixer.py)。

用語(NNが初めてでも読めるように)

  • token(トークン) … 画像を7x7のタイルに切ったときの1枚。28x28を7x7で刻むと 4x4=16枚になるので、このモデルにとって画像は「16個のtoken」でしかない
  • channel(チャネル) … 1枚のtokenを表すビットの並び。ここでは128ビット。 「そのタイルが持つ128個の○×質問への答え」だと思えばよい
  • LutLayer … 2入力の論理ゲートを out_dim 個並べた層。1ゲート=1出力ビット。 学習中は16種の論理関数(AND/OR/XOR…)の連続的な混合、確定させると本物の回路になる
  • LutStack … 同じ幅のLutLayerを depth 段だけ積んだもの。MLPの「隠れ層」に当たる
  • 転置(transpose) … 行列の行と列を入れ替える操作。行列の中身は1ビットも変えず、 「どの軸に沿ってゲートをかけるか」だけを切り替えられるのがMixerの肝

全体像(このサンプルの実設定の数字を入れたもの)

1ブロックの中身(転置で何が起きるか)

同じ (16 tokens x 128 channels) のビット表を、行と列を入れ替えて2回 LutStackに通すだけ。行列の向きが変わると「1回のLutStack適用で混ざる相手」が token同士 ⇄ チャネル同士 に切り替わる、というのがMixerの全アイデアである。

どう実現しているか

  1. パッチ埋め込みも論理ゲート: 7x7パッチを温度計符号化(値の大きさを 「棒グラフの長さ」としてビット列にする符号化)でビットに直し、全パッチ共有の 1枚のLutLayerで128ビットへ潰す。実数NNの Conv2d(stride=patch_size) に当たる。
  2. token-mixing は転置で実現: (B, tokens, channels) を転置してチャネル軸を バッチ側へ畳み込み、token軸に沿ったLutStackを1回かける。こうすると 「全チャネルで重みを共有した token 方向の混合」になり、たった32ゲートで 16枚のタイル全部を混ぜられる。
  3. 残差は加算でなく soft-XOR a + b - 2ab。{0,1}入力に対して厳密に bitwise XOR と一致するので、eval時も中間表現が {0,1} のまま保たれる。 soft-OR だと段を重ねるたび1へ飽和して情報が潰れるため採用しない (XORは a XOR b XOR b = a で情報を壊さない)。
  4. 最後だけ実数: 160本のビットを10組に分けて1の本数を数える(GroupSum)。 ここで初めて float が現れ、その値がそのまま logits になる。

このサンプルでは、まず実データを流したアーキテクチャ図で上の流れを目で追い、 次に「1パッチの変化が全パッチへ伝播している」ことを確かめてから、MNISTを学習する。

実行: uv run python examples/15_logic_mixer.py 期待結果: hard accuracy 0.65前後(CPUで2分弱の縮小レシピ。 d_channels / n_blocks / STEPS を増やせばさらに伸びる)

準備: import と乱数種

Section titled “準備: import と乱数種”

使うのは PyTorch と matplotlib、そして本ライブラリの load_mnist と LogicMixer / LogicMixerConfig だけ。MLP-Mixer(attention を使わず 2種類の混合MLPを交互に積むだけの画像アーキテクチャ)の論理ゲート版が LogicMixer で、 実装は griffith_logic/models/mlp_mixer.py にある。

ハイパーパラメータ: モデルの形を決める数字

Section titled “ハイパーパラメータ: モデルの形を決める数字”

このモデルの形はほぼ下の8行で決まる。先に語を定義しておく。

  • token(トークン) … 画像を刻んだパッチ1個。PATCH=7 なら 28x28 が 4x4 = 16 token になる
  • channel(チャネル) … 1トークンを表す論理チャネルのビット。D_CHANNELS=128 なので 1トークン = 128ビット
  • (tokens, d_channels) のビット表 … 以降ずっと混ぜ続ける主役。 行 = token・列 = channel の 16 x 128 の 0/1 の表である

ENCODE_BITS=4 は ThermometerEncoder(温度計符号化 = 実数の大きさを「棒グラフの 長さ」としてビット列に直す符号化) で1画素を何ビットに開くかの指定。

データセット: MNISTを28x28のまま読む

Section titled “データセット: MNISTを28x28のまま読む”

他の例と違い、画像を縮小も二値化もしない。パッチサイズ 7 で割り切れる必要があるので 28x28 のまま使い(20x20 だと 7 で割り切れない)、値も [0,1] の実数のまま渡す。 ビットへの変換はモデル内部の ThermometerEncoder が引き受けるため、データ側は何もしない。

モデル定義: LutLayerだけでMixerを組む

Section titled “モデル定義: LutLayerだけでMixerを組む”

上の数字を LogicMixerConfig に渡すだけで、patch_embed → LogicMixerBlock x3 → head → GroupSum までが組み上がる。部品の名前を先に押さえておく。

  • LutStack … 同じ幅の LutLayer(2入力の論理ゲートを並べた層)を depth 段だけ 積んだもの。MLP-Mixer の「MLP」の位置に入る部品
  • token-mixing / channel-mixing … 前者は token をまたいでビットを混ぜる (= 「どこを見るか」)、後者は1トークン内の128チャネルを混ぜる(= 「何を見るか」)
  • 残差接続 … 混ぜる前の値を混ぜた後に足し戻す配線。ここでは加算ではなく soft-XOR
  • GroupSum … 最終ビットをクラスごとに数え上げて logits にする出口。 このモデルで実数が現れるのはここだけ

表示される model の構造と、次の節で print されるゲート数の内訳が、この構成の全コストである。

アーキテクチャ: 転置で同じ道具を2回使う

Section titled “アーキテクチャ: 転置で同じ道具を2回使う”

なぜ転置するのか。 LutStack は常に「行列の各行」にかかる道具である。 (tokens, d_channels) のビット表をそのまま渡せば1行 = 1トークンの128チャネルなので channel-mixing になり、転置して渡せば1行 = 1チャネルの16トークン分になるので token-mixing になる。転置はビットを1つも書き換えない純粋な配線替えで、 同じ部品を向きだけ変えて2回使うためだけに入っている。 「行列の向きを変えて同じ道具を2回使う」── これが Mixer のアイデアのすべてである。

以下では実データを1枚だけ流し、その断面をそのまま図にして確かめる。

ブロック断面の採取

Section titled “ブロック断面の採取”

学習前のモデルに1枚流して、(1)パッチ埋め込み直後 (2)それを転置した行列 (3)token-mixing後 (4)channel-mixing後 の4つのビット表を取り出す。

図1: 1ブロックの断面(実データが流れている)

Section titled “図1: 1ブロックの断面(実データが流れている)”

左から順に、入力画像 → パッチ埋め込み後のビット表 → それを転置した行列 → token-mixing後 → channel-mixing後、の5枚。見るべきは2枚目と3枚目の関係で、 同じ 2,048 ビットを縦横入れ替えて眺めているだけ(ゲートは1個も通っていない)。 各パネルの下にはその時点の shape と、そこまでに使ったゲート数を書いてある。 破線は soft-XOR 残差の迂回路で、混ぜる前のビットを丸ごと持ち越す配線を表す。 配色はプロジェクト共通で、緑=論理(ビット)/ 橙=実数 / 灰=入力・配線。

3枚目だけ縦横が入れ替わっていること、そして4枚目・5枚目が2枚目と同じ向き・同じ形 (16 x 128)に戻っていることを確かめてほしい。ブロックを何段積んでも表の大きさは変わらず、 中身も 0/1 のままである。矢印に添えたゲート数(token-mix 32・channel-mix 256)が 混合1回分のコストで、16トークン全部を混ぜるのにたった32ゲートしか要らない。

図2: 画像をパッチ(token)に刻む

Section titled “図2: 画像をパッチ(token)に刻む”

同じことを、今度は入力側だけ拡大して見る。左は刻み方(数字が token 番号)、 右がパッチ埋め込み直後の (tokens, d_channels) ビット表 = 行が token・列が channel。 Mixerにとって画像は「16個のtoken」でしかなく、以降はこの表だけが混ぜられていく。

右の表は学習前なので模様に意味は無い。読み取るべきは、行ごとに立っているビットの 並びが違うこと ── つまり token ごとに別々の128ビットが割り当てられており、 この時点ではまだ token 同士が一切混ざっていないことである。

図3: token-mixing が情報を全パッチへ運ぶ

Section titled “図3: token-mixing が情報を全パッチへ運ぶ”

なぜ attention 無しで大域が見えるのかを実測で確かめる。1パッチだけを黒く潰した 入力を作り、元の入力との差分(明るい = 変化したビット)を2枚並べる。 左はパッチ埋め込み直後で、パッチ埋め込みは token ごとに独立なので変化は潰した token の 1行だけに閉じるはず。右は1ブロック(token-mix → channel-mix)通過後で、token-mixing が token 軸を跨いで配線されているぶん、変化が他の token へ漏れ出すはずである。 LutLayerの配線は疎(1ゲート2入力)なので1ブロックで届くのは数token分だけだが、 ブロックを重ねるほど画像全体へ広がる。これが attention を持たないMixerが 大域を見る仕組みで、その1段目の実測がこの図になる。

左は1行だけが光り、右は複数行が光る。潰した1パッチの情報が、たった1ブロックで 他のtokenへ届いたということで、上の print と assert が変化した token 数を数値でも示している。

学習: 普通のPyTorchループ

Section titled “学習: 普通のPyTorchループ”

学習則は特別なものを使わない。Adam + cross entropy の完全に普通の PyTorch である。 500ステップごとに精度を2通りで測る。

  • soft eval(train())… 各ゲートが16種の論理関数の連続混合のままの状態。勾配は流れるが まだ回路ではない
  • hard eval(eval())… 各ゲートを argmax で1つの論理関数に確定させた、 そのままハードウェアに焼ける純粋なBoolean回路

hard が本番の数字で、soft だけ高い状態は「回路として決めきれていない」サインである。

評価: 学習曲線と誤分類

Section titled “評価: 学習曲線と誤分類”

図4: soft と hard の学習曲線

Section titled “図4: soft と hard の学習曲線”

橙が soft、緑が hard。見どころは値そのものより2本が離れないことである。

なぜ soft-XOR 残差なのか。 残差を a + b - 2ab(0/1 なら厳密に XOR)で取っているのは、 XOR が自己逆元(a XOR b XOR b = a)で、片方の入力を反転すれば出力も必ず反転するから。 つまり情報を潰さない。soft-OR のように段を重ねるたび1へ飽和する演算だと深いところで 勾配が消えるが、XOR ならそれが起きず、中間表現も {0,1} のまま保たれる。 おかげで hard が soft から離れにくい。差が大きく開くようなら、 ゲートの混合が中間状態に居座っていることを疑う。

実際、緑(hard)は橙(soft)にわずかに遅れて追随し、最後はほぼ重なる。 離散回路のまま同じ精度が出ているということで、これが LogicMixer の主張である。 値が 0.65 前後で頭打ちなのは CPU 2分の縮小レシピだからで、 D_CHANNELS / N_BLOCKS / STEPS を増やせばそのまま伸びる。

図5: 誤分類例

Section titled “図5: 誤分類例”

締めくくりに、確定した回路(hard eval)が間違えた10枚を並べる。似た字形どうしの 取り違えが多いはずで、7x7 のタイルに刻んでしまうと局所の情報だけでは判別しづらい ケースが残る。16トークン x 3ブロックという小さな混合では拾いきれなかった 大域的な差であり、ブロックを増やすことが効く余地がここにある。
