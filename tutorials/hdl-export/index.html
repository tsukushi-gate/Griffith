3. HDLへエクスポート

学習済みモデルを IR(中間表現・真実源) へ抽出し、Verilog を生成して golden model と照合する。「PyTorch で学習 → IR → HDL」という本ライブラリの 出口をひととおり通す。

このページで学ぶこと

  1. 学習済みモデル → IR(中間表現・真実源)→ Verilog という出口の3手順
  2. validate(ir, target='hdl') が合成前にどんな事故を落としてくれるのか
  3. PyTorch hard eval ⇔ IR simulate ⇔ HDL シミュレーションの3段等価性の確かめ方

前提

  • 付録: XORで仕組みを最小で覗く — ここで焼く回路そのもの
  • IRガイド — IR が真実源である理由

このページについて

所要時間の目安: 約10分 / 実行環境: CPU のみ(GPU 不要) 元スクリプト: examples/04_export_hdl.py 手元で試す: notebooks/04_export_hdl.ipynb(このページと同じ内容の未実行ノートブック。uv run --group docs jupyter lab notebooks/ で開ける) コード出力はすべて 実際に実行した結果をそのまま埋め込んでいます。

▶ Colabで開く(リポジトリ公開後に有効化)

学習済みモデル → IR → Verilog エクスポートの例。

XORを学習し、IR(中間表現)JSONとVerilogを生成する。 iverilogがあればgolden modelとの一致検証も行う。

このライブラリの出口——「PyTorchで学習した重みを、GPUの要らない論理回路に変換する」 ——を最短で通すスクリプト。要は3段階で、(1) 学習、(2) IRへ万能離散化、 (3) IRからVerilog生成。IRが真実源で、シミュレータもHDLもすべてIRから派生するため、 「PyTorchの出力 = IRの出力 = 実際の回路の出力」を機械的に照合できる。

実行: uv run python examples/04_export_hdl.py 期待結果: out_examples/xor.json と xor.v が生成され、照合ALLPASS

準備: 出口までに使う4つのAPI

Section titled “準備: 出口までに使う4つのAPI”

このページで通す道は「学習 → IR → Verilog → 照合」の4段で、それぞれに対応する API を最初に import しておく。用語は初出でここに定義しておく。

  • export_ir … 学習済みモデルを IR(中間表現) へ変換する。IR は 「真理値表の集まり」として正規化された JSON で、ハードウェア側の真実源
  • validate … IR が HDL 生成の制約(ビット幅・トポロジ順序など)を満たすか検査する
  • write_verilog … IR から合成可能な Verilog(RTL)を書き出す
  • simulate … IR を numpy の整数ビット演算で解釈実行する参照実装(golden model)

学習: 焼く対象のXOR回路を作る

Section titled “学習: 焼く対象のXOR回路を作る”

エクスポートの手順を見せるのが主題なので、対象は最小の XOR に絞る (付録: XOR とまったく同じ構成の 32 ゲート)。 学習ループも普通の PyTorch なので、ここは黙って 500 ステップ回すだけでよい。

エクスポート前に、これから焼く回路を見る

Section titled “エクスポート前に、これから焼く回路を見る”

図1: 確定したゲートの網

Section titled “図1: 確定したゲートの網”

model.eval() を呼んだ時点で、各ゲートは16種の論理関数の混合ではなく 1つに確定したゲートになっている。その状態を回路図として描く。 緑のノードが確定した論理ゲート、橙が GroupSum(ここから先は実数)。

読み取り: 各ノードに XOR / NAND / A>=B のような具体的な論理関数の名前が 入っている。この名前は export_ir が Verilog を吐くときに使う真理値表と 同じ経路(export/discretize)から来ているので、 この図のゲート = 生成される回路のゲートである。

回路の「部品表」を数える

Section titled “回路の「部品表」を数える”

同じ回路を別の角度から見る。各ゲートの真理値表(2入力なので4ビット=16通り)を ゲートIDとみなし、16種の論理関数それぞれが何個使われたかを数える。 truth_tables_from_lut_layer は export_ir が内部で使うのと同じ離散化経路なので、 ここで数えた内訳は生成される Verilog の中身の内訳と一致する。

図2: どの論理関数が何個使われたか

Section titled “図2: どの論理関数が何個使われたか”

横軸に16種すべてを並べる(0個のものも空欄として残し、何が使われなかったかも見せる)。

読み取り: 16種のうち一部しか使われず、XOR / XNOR に大きく偏っている ── 誰も「XOR を使え」とは教えていないのに、勾配だけでタスクに必要な論理関数が選ばれた。 一方で定数(FALSE)や入力の素通し(A / !B)も残る。これらは実質的に配線か 無効ノードで、人間なら書かない冗長さである。学習は「32ゲートを使い切れ」とは 言われていないので、余ったゲートが何もしない形に落ち着いた結果であり、 後段の論理合成ツールが削れる余地でもある。

IRへ抽出する

Section titled “IRへ抽出する”

IR が真実源であるというのが本ライブラリの設計の要である。Verilog も VHDL も シミュレータも、すべて IR から派生する ── だから「PyTorch の出力 = IR の出力 = 実際の回路の出力」を機械的に照合できる。

手順で外せないのは2点。

  • eval() にしてから抽出する。train() のままだと連続混合の状態を見ることになり、 回路として確定していない
  • validate(ir, target='hdl') を通す。ビット幅・トポロジ順序・未対応ノードの不在を ここで検査しておけば、Verilog を書き出してから合成ツールで初めて気づく事故を防げる

Verilogを生成する

Section titled “Verilogを生成する”

write_verilog は IR から合成可能な RTL(レジスタ転送レベル記述)を書き出す。 できあがった .v は Vivado / Quartus といったベンダーツールへそのまま投げられる。 VHDL が要るなら write_vhdl に差し替えるだけでよい ── 下流を差し替えられるのは、 上流の IR が正規化された真実源だからである。

3段等価性で照合する

Section titled “3段等価性で照合する”

出口の正しさは「3つの独立な実装が同じ答えを出すこと」で担保する。

  1. PyTorch hard eval … 同じ真理値表を浮動小数のテンソル演算で通した結果
  2. IR simulate … 浮動小数を一切使わない整数ビット演算の参照実装(golden model)
  3. HDL シミュレーション … 生成した Verilog を iverilog で実際に走らせた結果

1と2が一致すれば「離散化に取りこぼしが無い」、さらに3が一致すれば 「学習した重みが実際のハードウェアの挙動と一致する」と言い切れる。

図3: 3段等価性を1枚の真理値表にする

Section titled “図3: 3段等価性を1枚の真理値表にする”

最後に、上の3経路の答えを1枚の表にまとめる。行が4つの入力パターン、 列が答え合わせの経路(教師ラベル / PyTorch hard / IR simulate)。 セルの数字が出力クラスで、緑=expected と一致、赤=不一致である。

読み取り(この図が最後なので先に書く): 3列が同じ値で埋まり緑一色になる。 これが「学習の世界(PyTorch)」と「回路の世界(IR / HDL)」が同じ関数を 表していることの確認であり、赤が1つでも出たらエクスポートのバグである。 図のタイトルには iverilog による HDL 照合の結果も併記してある。
