論理ゲート版TextCNNで「n-gram検出器」を育てる

単語を数えるだけでは絶対に解けない問題を用意して、畳み込みが n-gram 検出器として 働くことを反証不能な形で示す。肯定語 × 良い語 / 否定語 × 悪い語 の XNOR でラベルを 決めるバイグラム XOR 分類では、どの単語も両クラスに等頻度で現れる ── つまりユニグラムの情報量がゼロ(単語頻度による規則の上限 0.535 = ほぼ偶然)。

論理ゲート版 TextCNN はこれを soft/hard ともに 1.000 で解く。しかも学習後の フィルタを覗くと、filter 6 は “really good”、filter 4 は “never awful” ── 特定の2語の検出器へ育っている。付録: XOR の自然な続き。

このページで学ぶこと

  1. 単語頻度では原理的に解けない課題(バイグラム XOR 分類)の作り方と、その意味
  2. 論理ゲート版 TextCNN の構成と、soft/hard ともに 1.000 で解けること
  3. 学習後のフィルタを覗いて「特定の2語の検出器」へ育っていることを確かめる方法

前提

  • 付録: XORで仕組みを最小で覗く — 同じ XOR 構造の最小版
  • 1. MNISTを学習する

このページについて

所要時間の目安: 約5分 / 実行環境: CPU のみ(GPU 不要) 元スクリプト: examples/23_textcnn.py 手元で試す: notebooks/23_textcnn.ipynb(このページと同じ内容の未実行ノートブック。uv run --group docs jupyter lab notebooks/ で開ける) コード出力はすべて 実際に実行した結果をそのまま埋め込んでいます。

▶ Colabで開く(リポジトリ公開後に有効化)

TextCNN(論理ゲート版)でテキスト分類を学習し、畳み込みがn-gram検出器として 働く様子を可視化する例。

TextCNN(Kim 2014)は「埋め込み列の上を幅kの窓で畳み込み、Global Max Poolで 最も強く反応した位置だけを拾う」というモデルで、各フィルタは事実上 「特定のn-gramが文中のどこかに出たか」を検出する回路になる。 本サンプルはその畳み込みを LutConv2d(微分可能論理ゲートの木)で置き換えたもので、 埋め込みも LogicEmbedding によって {0,1} のビットベクトルへ落ちる。 つまり文全体が、乗算を1つも使わない論理回路で分類される。

モデルはパッケージ内ではなく experiments/train_textcnn.py にある

TextCNNModel は実験スクリプト側(パッケージ外)に置かれているため、 from griffith_logic import ... では取れない。ここでは tests/test_textcnn.py と 同じやり方で sys.path に experiments/ を足して import する。 (実験スクリプトの読み込み時に .env の読み込みと wandb ユーティリティの import が走るが、init_wandb を呼ばない限りログ送信は発生しない。)

題材: バイグラムXOR

本家は日本語感情分析データセット WRIME を使うが、ダウンロードと学習に時間がかかる。 ここでは数分で回るよう、ユニグラムだけでは絶対に解けない合成タスクを用意した:

肯定語(really / truly)と否定語(not / never)、良い語(good / nice)と 悪い語(bad / awful)の組み合わせで、ラベルは2語のXORで決まる。 どの単語も両クラスに等頻度で現れるので、単語の出現頻度(=ユニグラム)を いくら数えても精度50%より上には行かない。隣り合う2語をセットで見るしか 解く方法がなく、これはまさに幅2の畳み込みが得意とする形になっている。 例01のXORが、単語の世界へ引っ越してきたと思えばよい。

回路の全体像(1文12語・埋め込み32ビットの実寸)

具体例が図としてどこに出るか: 上の EX の流れは、このページ2枚目の図 「k=2 conv activations before Global Max Pool」で実物が見られる。 横軸が窓の位置、縦軸がフィルタ番号で、決定的なバイグラムがある位置の列だけが光る。 3枚目の図はそれを全テスト文で平均したもので、 「really good」「not bad」といった組み合わせごとに反応するフィルタが分かれていることが分かる。

どう実現しているか

  • 埋め込みもビットにする。LogicEmbedding は1語を32本のビット線に割り当てる。 学習中は [0,1] の実数だが、正則化で 0/1 の両端へ押しやるので、最終的には 「単語 = 32ビットの符号」になる
  • 窓が埋め込み次元を丸ごと覆う。kernel=(k, 32) と幅を埋め込み次元に一致させるので 横方向の出力幅が1になり、2次元畳み込みがそのまま1次元の n-gram 走査になる
  • 1フィルタ = 1つの n-gram 検出回路。k=2 なら 2語×32ビット = 64本を見て 0/1 を返す LUT の木。「really の符号かつ good の符号なら1」といった論理を、表として学習する
  • Global Max Pool は OR。ビットの世界では max = OR なので、 「文中のどこかでその n-gram が出たか」を、位置を捨てて1ビットに畳み込める。 これが TextCNN が語順に強く位置に鈍い理由でもある
  • ユニグラムでは50%が上限。どの単語も両クラスに等頻度で出るので、 単語の出現を数えるだけの回路は原理的に解けない。隣り合う2語をセットで見る = 幅2の窓が必要、という構造がこのタスクの本質である

実行: uv run python examples/23_textcnn.py 期待結果: hard accuracy 1.00(CPUで約1分)

準備: import と乱数種

Section titled “準備: import と乱数種”

モデル本体 TextCNNModel は experiments/train_textcnn.py にあり、パッケージ外なので sys.path を通してから読み込む。ゲートの初期接続も埋め込みもランダム初期化なので、 再現性のために PyTorch と Python 標準の乱数の両方を固定する。

ハイパーパラメータ

Section titled “ハイパーパラメータ”

n-gram とは「連続する n 語のまとまり」のこと(2語ならバイグラム)。 KERNELS = [2, 3] は「幅2の窓と幅3の窓を並べて走らせる」という意味で、 答えがバイグラムにあるこのタスクでは k=2 のブランチが主役になる。 D_EMB は1語を何本のビット線で表すかで、ここでは1語 = 32 ビットの符号になる。

データ: ユニグラムでは絶対に解けない題材を作る

Section titled “データ: ユニグラムでは絶対に解けない題材を作る”

ラベルは「修飾語 × 意味語」の XOR で決まる ── really good と not bad がポジティブ、 not good と really bad がネガティブ。どの単語も両クラスに等頻度で現れるように 作ってあるので、単語の出現頻度(= ユニグラム、1語だけを見る特徴)をいくら数えても 精度は 50% を超えられない。

なぜこの題材を選ぶのか: 「隣り合う2語をセットで見る」以外に解法が存在しない状況を 人工的に作ることで、学習後に精度が上がっていれば畳み込みが本当に n-gram を 捉えた証拠になるからである。例01の XOR が、単語の世界へ引っ越してきたと思えばよい。

語彙とID化

Section titled “語彙とID化”

単語を整数 ID へ写す辞書を作る。埋め込み層はこの ID を引いてビット列を返すので、 ここが「文字列の世界」と「回路の世界」の境目になる。

ユニグラムの上限を先に測っておく

Section titled “ユニグラムの上限を先に測っておく”

「良い語を含むならポジ」という最良のユニグラム規則を実際に走らせ、その精度を控えておく。 あとで学習曲線にこの値を破線で引き、そこからの伸びぶんが n-gram の寄与だと読めるようにする。 主張を先に測っておくと、結果を「たまたま上がった」と混同せずに済む。

モデル: 論理ゲート版 TextCNN

Section titled “モデル: 論理ゲート版 TextCNN”

構成は LogicEmbedding → 各 k の LutConv2d ブランチ → Global Max Pool → 連結 → LutLayer スタック → GroupSum。要点は3つある。

  • 埋め込みもビットにする。LogicEmbedding は1語を32本のビット線へ割り当てる。 学習中は [0,1] の実数だが、正則化で 0/1 の両端へ押しやるので、最終的には 「単語 = 32ビットの符号」になる
  • 窓が埋め込み次元を丸ごと覆う。kernel_size=(k, d_emb) と幅を埋め込み次元に 一致させるので横方向の出力幅が1になり、2次元畳み込みがそのまま1次元の n-gram 走査になる。 1フィルタ = 「2語×32ビット = 64本を見て 0/1 を返す LUT の木」= 1つの n-gram 検出回路である
  • Global Max Pool は OR。ビットの世界では max は「どれか1つでも1なら1」= OR に一致する。 なぜ max pooling が OR なのかが効いてくるのはここで、位置を捨てて 「文中のどこかでその n-gram が出たか」を1ビットに畳み込める。比較器も加算器も要らない

学習: 分類の損失に埋め込みの二値化正則化を足す

Section titled “学習: 分類の損失に埋め込みの二値化正則化を足す”

損失は cross entropy に emb_reg(埋め込みを 0/1 へ寄せる正則化)を少し混ぜたもの。 なぜ必要か: 推論時に LogicEmbedding は Heaviside(閾値で 0/1 に切る階段関数)で 二値化されるので、学習中の実数値が中途半端なままだと、離散化した瞬間に符号が変わって hard accuracy だけ崩れる。正則化で先に両端へ寄せておくことで、soft と hard が一致する。 精度も soft(連続緩和のまま)と hard(離散化した回路)の両方で測る。

畳み込みの中を覗く

Section titled “畳み込みの中を覗く”

ここからは「解けた」で終わらせず、回路が何を見て解いたのかを確かめる。 TextCNNModel.forward は Global Max Pool 済みの値しか返さないので、プール前の活性 (窓の位置ごとの 0/1)を自分で取り出す。やっていることは forward の前半と同じである。

可視化: 学習曲線とフィルタの中身

Section titled “可視化: 学習曲線とフィルタの中身”

図1: 学習曲線

Section titled “図1: 学習曲線”

この図で何を見るか: 橙が soft(連続緩和のまま)、緑が hard(離散化した論理回路)、 灰の破線が先ほど測ったユニグラム規則の上限。見どころは 緑が灰の破線をはっきり超えることで、超えた分がそのまま n-gram の寄与になる。

読み取り: soft と hard がほぼ重なったまま伸び、ユニグラム上限(灰の破線)を大きく 超える。離散化しても壊れない回路のまま、単語を数えるだけでは届かない領域へ 到達したということ。soft だけ高く hard が置いていかれる場合は、 埋め込みかゲートが中間状態に居座っているサインになる(ここではそうなっていない)。

図2: フィルタが文のどこで発火しているか

Section titled “図2: フィルタが文のどこで発火しているか”

この図で何を見るか: 縦がフィルタ番号、横が窓の位置(その窓が覆う2語をラベルにしてある)。 ポジ1文・ネガ1文について、プール前の活性をそのまま並べた。見どころは 決め手のバイグラムがある位置の列だけが光ること ── それが「畳み込みがその2語を 検出器として捉えた」証拠になる。なお Global Max Pool は各行の最大値だけを後段へ渡すので、 分類に効くのは「どこで光ったか」ではなく「どこかで光ったか」だけである。

読み取り: 光っている列が、その文の決め手のバイグラム(タイトルの key bigram)の 位置と一致していることを確かめる。位置がばらばらの2文で同じフィルタが反応していれば、 そのフィルタは位置ではなく語の組み合わせを見ているということ。 全く光らない行があるのも普通で、それは次の図で「死んだフィルタ」として数える。

図3: どのフィルタがどのバイグラムに反応するか

Section titled “図3: どのフィルタがどのバイグラムに反応するか”

この図で何を見るか: 決め手の組み合わせ(really good / not good / really bad / not bad の系統)ごとに、そのバイグラムが置かれた位置での活性をテストセット全体で平均した表。 縦がフィルタ、横がバイグラム。見どころは行ごとに光る列が分かれることで、 分かれていれば各フィルタが特定の n-gram の検出器へ育ったことになる。 逆に全列が同じ明るさの行は、何も見分けていない「死んだフィルタ」である。

読み取り: 上の表を行ごとに読み下すと、フィルタが「どのバイグラムの検出器になったか」が 言葉で出てくる。「最大 − 最小」の差が大きいフィルタほど選択的で、差がほぼ 0 の行は どのバイグラムでも同じ値を返す死んだフィルタである。冗長に用意したフィルタの一部が こうなるのは普通のことで、Global Max Pool の後段は生きているフィルタだけを使えばよい。
