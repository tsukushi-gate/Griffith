Training an FPGA-oriented LUT network with the BinaryBrain-compatible API

Train MNIST with the same component layout as the FPGA-oriented OSS project BinaryBrain (RealToBinary → DifferentiableLutBlock → BinaryToReal). A real-valued image is stochastically modulated into seven binary frames, 430 LUT6s are lined up, and a majority vote turns the result back into reals — the lineage that trains FPGA LUTs directly.

The subject of this page is quantifying “not yet burnable”. With continuous truth tables (BinaryBrain’s native inference path) eval acc is 0.803, but rounding the entries to 0/1 collapses it to 0.211. Recalibrating the BatchNorm statistics only brings it back to 0.632 — the main cause is not a statistics mismatch but that the truth-table entries are still clustered around 0.5 (std 0.048) and have not committed. We measure this discretization gap, honestly exposed by the shortened recipe, right down to the histogram.

What you’ll learn

  1. The BinaryBrain-style layout RealToBinary → DifferentiableLutBlock → BinaryToReal
  2. The mechanism that stochastically modulates a real-valued image into binary frames and turns it back into reals by majority vote at the end
  3. How to quantify not yet burnable — the collapse that happens when the truth tables are rounded to 0/1, and its main cause

Prerequisites

  • DWN — solving MNIST with thermometer encoding and n-input LUTs — an example where the gap goes to 0 instead
  • Choosing a Parameterization

About this page

▶ Open in Colab (enabled once the repository is public)

An example of training MNIST with the BinaryBrain-compatible API (Binarize / RealToBinary / BinaryToReal / DifferentiableLutBlock).

BinaryBrain (https://github.com/ryuz/BinaryBrain) is a Japanese OSS project designed on the premise of burning LUT networks directly onto FPGAs, and it implemented the idea of the “differentiable LUT” early on. This library reimplements its core components in PyTorch so they can be used from griffith_logic as plain nn.Modules.

Why compatibility matters

  1. You can bring proven recipes over as they are. We match BinaryBrain’s MNIST notebook down to the layer configuration, the initial values (BatchNorm gamma=0.3 / beta=0.5), and Unbinarize bias=0.25, so when accuracy is poor you can separate “is the implementation different or is the configuration different?”.
  2. You can connect to assets on the FPGA side. BinaryBrain’s LUTs map one-to-one onto an FPGA’s LUT6. Weights trained with the same configuration can be interpreted directly as FPGA truth tables.
  3. It gives a comparison point for parameterization. This library’s LutLayer has five parameterizations, and the BinaryBrain approach corresponds to parameterization='raw' (see below).

Relationship to LutLayer

So a BinaryBrain block is “a sandwich with a LutLayer in it”, not something different. The difference lies in how the truth table is parameterized:

  • The difflogic family (default parameterization='softmax') learns softmax weights over 16 logic gates and settles on one gate by argmax at inference time.
  • The BinaryBrain family (parameterization='raw') holds the 2^N truth-table entries directly as reals in [0,1], clamping them back into range every step. Since no sigmoid is interposed, the gradient does not carry a sigmoid Jacobian. Burning to an FPGA is then just a matter of rounding each entry to 0/1.

The whole circuit (binary modulation sandwiches the reals)

Where the concrete example shows up as a figure: the first figure on this page, “RealToBinary: one real image -> 7 binary frames -> mean”, is R2B and B2R above in the flesh. The darker a pixel, the more frames it is 1 in, and averaging the 7 frames nearly restores the original shading — that is exactly the trick of “carrying a real into the world of bits as a count”.

How it is done

  • Darkness becomes a number of 1s. RealToBinary duplicates one real-valued image into 7 binary images. Because the thresholds are evenly spaced, a pixel of value 0.7 is 1 in roughly 5 of the 7 frames. That is how probabilistic information turns into a bit string a circuit can handle
  • The layer sizes follow a design rule. With 6-input LUTs, unless “next layer’s node count × 6 ≥ previous layer’s node count” holds, some nodes end up read by nobody. 400 → 360 → 60 → 10 is the smallest configuration that satisfies it
  • BatchNorm corrects the bias of the bits. Feeding a LUT output straight into the next stage skews it toward 0 or 1, so it is normalized as a real and re-cut by Binarize. This BatchNorm is real arithmetic, so it has to be folded into the thresholds when burning (the orange block)
  • Binarize is a step function forward and a pass-through backward (STE). That is how gradients reach all the way back through a binarization that ought not to be differentiable
  • The truth table is held directly (raw). Where the difflogic family learns “weights over the 16 logic functions”, the BinaryBrain approach holds the 2⁶ = 64 entries as reals in [0,1] and clamps them every step. Burning is then just rounding each entry

Run: uv run python examples/22_binarybrain.py Expected result: eval accuracy around 0.80 (about 2 minutes on CPU)

Note that this example uses a short recipe, so the truth tables have not yet committed to 0/1. We finish by quantitatively examining that “training works, but it is not yet enough to burn” as a discretization gap (Figures 2 and 3).

Setup: imports and the random seed

Section titled “Setup: imports and the random seed”

All we use are the three BinaryBrain-compatible parts — RealToBinary (real values to bits), DifferentiableLutBlock (one LUT sandwich stage) and BinaryToReal (bits back to real values) — plus MNIST shrunk to 20×20. The LUT wiring (which input lines each table looks at) is chosen at random, so we fix the seed for reproducibility.

Hyperparameters

Section titled “Hyperparameters”

Let us pin down the symbols first. N_INPUTS (the number of LUT inputs) is how many wires a single truth table looks at; 6 is the headline value because it maps one-to-one onto an FPGA LUT6, giving 2⁶ = 64 entries. FRAME_M (the number of binary-modulation frames, written M in the text) is how many binary images one real-valued image is split into: larger means finer shading, at M times the computation.

Data: receiving 20×20 MNIST as real values

Section titled “Data: receiving 20×20 MNIST as real values”

This is where the page differs from the other examples. Most logic-gate NN examples binarize the image at the door, but the BinaryBrain style receives the real-valued shading itself and lets RealToBinary inside the model turn “darkness” into “the number of frames that are 1”. That is why we read the data with binarize_threshold=None.

Model: stacking three DifferentiableLutBlocks

Section titled “Model: stacking three DifferentiableLutBlocks”

One stage is the sandwich Unbinarize → LutLayer(raw) → BatchNorm1d → Binarize. Why BatchNorm is in there: feeding a LUT’s output straight into the next stage makes it lean hard towards 0 or 1, and the next LUT ends up returning the same answer whatever its inputs are. Normalizing back in the real domain and then re-cutting with Binarize evens out that bias at every stage. (This BatchNorm is real-valued arithmetic, so burning it to an FPGA means folding it in as a threshold.)

Binarize is a step function forwards and a pass-through backwards (STE = straight-through estimator, the approximation that passes gradients through a non-differentiable function unchanged). That is why gradients reach all the way back even with binarization in the middle.

Training: ordinary PyTorch plus one line of clamping

Section titled “Training: ordinary PyTorch plus one line of clamping”

The body is completely ordinary PyTorch, and the only BinaryBrain-specific part is the single line “call clamp_weights() after optimizer.step()”. Why the clamp is needed: the raw parameterization holds each truth-table entry directly as “the probability that this entry outputs 1”, so it becomes meaningless once a gradient pushes it outside [0,1]. Rather than squashing it with a sigmoid, upstream simply clips it back every step — and because no sigmoid Jacobian (a multiplication by the slope) rides on the gradient, learning stays more direct.

During training we measure two accuracies every time: eval (leaving the truth tables continuous = BinaryBrain’s native inference path) and rounded (a copy with the entries rounded to 0/1 = a naive burn to an FPGA). The gap between these two is the discretization gap, which is the subject of this whole page.

The discretization gap: why rounding breaks it

Section titled “The discretization gap: why rounding breaks it”

Rounding drops accuracy sharply. There are two candidate causes. (a) The truth tables have not yet committed to 0/1, and rounding destroys information. (b) The distribution of LUT outputs changes drastically, so the running statistics held by BatchNorm no longer fit. If (b), re-measuring the statistics should restore it, so we push training data through, recalibrate, and decide experimentally which cause dominates. Doing that identification is the point of this section.

Visualization: modulation, learning curve, truth-table distribution

Section titled “Visualization: modulation, learning curve, truth-table distribution”

Figure 1: what binary modulation (RealToBinary) is doing

Section titled “Figure 1: what binary modulation (RealToBinary) is doing”

What to look for: the original real-valued image on the far left, then seven binary frames made by shifting the threshold (f+0.5)/M, and on the far right their average turned back into a real image. The figure lets you follow, frame by frame, the correspondence that the darker a pixel is, the more frames it is 1 in.

Binary modulation means encoding magnitude as “the number of frames that are 1” (the same idea as pulse density modulation). The thresholds are evenly spaced, so a pixel with value 0.7 is 1 in about five of the seven frames. That is how continuous information turns into a bit string a circuit can handle.

What it says: the far right (the average of seven frames) looks almost the same as the far left (the original), which is the whole point — shading survives a round trip through nothing but a count of bits. Conversely, the smaller M is, the coarser that reconstruction becomes (with M = 7 only eight levels of darkness can be distinguished).

Figure 2: the learning curve and the discretization gap

Section titled “Figure 2: the learning curve and the discretization gap”

What to look for: green is BinaryBrain’s native inference path (continuous truth tables), orange is the accuracy of “what if we rounded and burned it right now”, and the red dashed line is the rounded model after recalibrating BatchNorm. The two things to watch are how wide the gap between green and orange is and how much of that gap the red dashed line fills.

What it says: with this reduced recipe the gap between green and orange stays wide open, and the red dashed line (BatchNorm recalibration) fills only part of it. So the dominant cause of the discretization gap is not the statistics mismatch (b) but the truth tables not yet having committed to 0/1 (a). The next figure shows that directly.

Figure 3: the distribution of truth-table entries

Section titled “Figure 3: the distribution of truth-table entries”

What to look for (this is the last figure, so here is how to read it in advance): the horizontal axis is the value of a LUT entry (= the probability that the entry outputs 1) and the vertical axis is the count (log scale); grey is before training and blue after. A burnable circuit is one whose distribution has pinned to both ends, 0 and 1, so that round() loses no information. Here, however, the distribution has only spread a little from its initial Normal(0.5, 0.01) and is still clustered around 0.5 — which is exactly why rounding breaks it (orange in Figure 2). It is also why BinaryBrain’s inference works with continuous weights, and the correct reading of this page is “training works, but this is not yet in a burnable state”. Pushing it to the ends requires training as long as upstream’s (or regularization that encourages binarization).
