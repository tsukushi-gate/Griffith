LogicMixer (MLP-Mixer) — mixing images without attention

The logic-gate version of MLP-Mixer, which mixes images without using attention. The image is chopped into 16 tokens, and token-mixing (transpose, then run through a LutStack) and channel-mixing are stacked alternately with soft-XOR residuals. Reaches hard acc 0.658 on MNIST.

The highlight is measuring how information gets mixed. Track the difference against an input where a single patch has been erased: right after patch embedding the change stays confined to that token’s row, but after one block it leaks into neighbouring tokens (1→2 tokens per block). Who is doing the mixing becomes visible in a picture.

What you’ll learn

  1. How to build an MLP-Mixer out of logic gates, mixing images without using attention
  2. The division of labour between token-mixing (transpose, then run through a LutStack) and channel-mixing
  3. How to read the difference from erasing a single patch to measure “how far information leaks”

Prerequisites

  • Residual connections in logic NNs — the character of the soft-XOR residual
  • 1. Train on MNIST

▶ Open in Colab (enabled once the repository is public)

An example of solving MNIST with LogicMixer (the logic-gate version of MLP-Mixer).

MLP-Mixer (Tolstikhin et al., 2021) is an architecture that “solves images with MLPs alone, without attention”; it is built by simply alternating two kinds of mixing:

LogicMixer replaces these two MLPs with stacks of LutLayers to get a logic-gate version (griffith_logic/models/mlp_mixer.py).

Terminology (so the page reads even if neural networks are new to you)

  • token … one tile of the image once it is cut into 7x7 tiles. Chopping 28x28 into 7x7 gives 4x4 = 16 tiles, so as far as this model is concerned an image is nothing but “16 tokens”
  • channel … the string of bits that represents one token; 128 bits here. Think of it as “the answers to 128 yes/no questions that this tile holds”
  • LutLayer … a layer of out_dim two-input logic gates. One gate = one output bit. During training each gate is a continuous mixture of the 16 logic functions (AND/OR/XOR…); once fixed it becomes a genuine circuit
  • LutStack … depth LutLayers of the same width stacked up. It plays the role of an MLP’s “hidden layers”
  • transpose … swapping the rows and columns of a matrix. It changes not a single bit of the contents, yet it switches “which axis the gates act along” — that is the crux of Mixer

The whole picture (with the numbers of this example’s actual settings)

Inside one block (what transposition actually does)

The very same (16 tokens x 128 channels) bit table is run through a LutStack twice, with rows and columns swapped in between. Turning the matrix around switches “who gets mixed with whom in one application of a LutStack” between token-with-token and channel-with-channel — and that is the entire idea of Mixer.

How it is realised

  1. Patch embedding is logic gates too: a 7x7 patch is turned into bits by thermometer encoding (an encoding that writes the magnitude of a value as “the length of a bar”), and a single LutLayer shared across all patches collapses it into 128 bits. It corresponds to Conv2d(stride=patch_size) in a real-valued NN.
  2. token-mixing is realised by transposition: transpose (B, tokens, channels) so that the channel axis folds into the batch side, then apply one LutStack along the token axis. This gives “mixing along the token direction with weights shared across all channels”, so a mere 32 gates suffice to mix all 16 tiles.
  3. The residual is soft-XOR a + b - 2ab, not addition. For {0,1} inputs it matches bitwise XOR exactly, so intermediate representations stay in {0,1} at eval time too. soft-OR is not used because it saturates towards 1 as layers stack and destroys information (XOR keeps information intact since a XOR b XOR b = a).
  4. Only the last step is real-valued: the 160 bits are split into 10 groups and the ones are counted (GroupSum). This is where float first appears, and that value is the logits itself.

In this example we first follow the flow above with an architecture figure that has real data flowing through it, then confirm that “a change in one patch propagates to all patches”, and finally train on MNIST.

Run: uv run python examples/15_logic_mixer.py Expected result: hard accuracy around 0.65 (a reduced recipe that takes just under 2 minutes on CPU. Increasing d_channels / n_blocks / STEPS pushes it higher.)

Setup: imports and the random seed

Section titled “Setup: imports and the random seed”

All we need is PyTorch, matplotlib and this library’s load_mnist plus LogicMixer / LogicMixerConfig. LogicMixer is the logic-gate version of MLP-Mixer (the image architecture that simply alternates two kinds of mixing MLPs without any attention); the implementation lives in griffith_logic/models/mlp_mixer.py.

Hyperparameters: the numbers that fix the shape of the model

Section titled “Hyperparameters: the numbers that fix the shape of the model”

The shape of this model is decided almost entirely by the eight lines below. Let us define the words first.

  • token … one patch the image is chopped into. With PATCH=7, a 28x28 image becomes 4x4 = 16 tokens
  • channel … the bits of the logic channels that represent one token. D_CHANNELS=128, so one token = 128 bits
  • the (tokens, d_channels) bit table … the protagonist that gets mixed from here on. It is a 16 x 128 table of 0/1 with rows = tokens, columns = channels

ENCODE_BITS=4 says how many bits one pixel is expanded into by the ThermometerEncoder (thermometer encoding = writing the magnitude of a real value as “the length of a bar” in bits).

Dataset: MNIST read at its original 28x28

Section titled “Dataset: MNIST read at its original 28x28”

Unlike the other examples, the image is neither downscaled nor binarized. The image size has to be divisible by the patch size 7, so we keep 28x28 as is (20x20 is not divisible by 7) and pass the values through as reals in [0,1]. The conversion to bits is handled by the ThermometerEncoder inside the model, so the data side does nothing.

Defining the model: building a Mixer out of LutLayers alone

Section titled “Defining the model: building a Mixer out of LutLayers alone”

Just handing the numbers above to LogicMixerConfig assembles everything from patch_embed → LogicMixerBlock x3 → head → GroupSum. Let us pin down the names of the parts first.

  • LutStack … depth LutLayers (layers of two-input logic gates) of the same width stacked up. It is the part that sits where MLP-Mixer’s “MLP” goes
  • token-mixing / channel-mixing … the former mixes bits across tokens (= “where to look”), the latter mixes the 128 channels within one token (= “what to look at”)
  • residual connection … the wiring that adds the value before mixing back after mixing. Here it is soft-XOR rather than addition
  • GroupSum … the exit that counts the final bits per class to make logits. This is the only place in the model where real numbers appear

The structure of model that gets printed, together with the gate breakdown printed in the next section, is the entire cost of this configuration.

The architecture: using the same tool twice via transposition

Section titled “The architecture: using the same tool twice via transposition”

Why transpose? A LutStack is always a tool that acts on each row of a matrix. Hand it the (tokens, d_channels) bit table as is and one row = the 128 channels of one token, so you get channel-mixing; hand it the transpose and one row = the 16 tokens of one channel, so you get token-mixing. Transposition is pure rewiring that rewrites not a single bit, and it is there solely so that the same part can be used twice, only turned around. “Turn the matrix around and use the same tool twice” — that is the whole idea of Mixer.

Below we push a single real image through and check the cross-sections as pictures.

Taking the block cross-sections

Section titled “Taking the block cross-sections”

Feed one image to the untrained model and pull out four bit tables: (1) right after patch embedding (2) that matrix transposed (3) after token-mixing (4) after channel-mixing.

Figure 1: the cross-section of one block (with real data flowing through)

Section titled “Figure 1: the cross-section of one block (with real data flowing through)”

From the left: the input image → the bit table after patch embedding → that matrix transposed → after token-mixing → after channel-mixing, five panels in all. What to look at is the relation between the second and third panels: the very same 2,048 bits, merely viewed with the axes swapped (not a single gate has been passed). Under each panel are the shape at that point and the number of gates used up to there. The dashed lines are the detour of the soft-XOR residual, the wiring that carries the bits before mixing over whole. Colours follow the project convention: green = logic (bits) / orange = real numbers / grey = input and wiring.

Check that only the third panel has its axes swapped, and that the fourth and fifth are back to the same orientation and the same shape (16 x 128) as the second. However many blocks you stack, the size of the table never changes and its contents stay 0/1. The gate counts written beside the arrows (token-mix 32, channel-mix 256) are the cost of one mixing step: mixing all 16 tokens takes a mere 32 gates.

Figure 2: chopping the image into patches (tokens)

Section titled “Figure 2: chopping the image into patches (tokens)”

The same thing again, this time zoomed in on the input side only. On the left is how it is chopped (the numbers are token indices); on the right is the (tokens, d_channels) bit table right after patch embedding = rows are tokens, columns are channels. In the Mixer’s world an image is nothing more than “16 tokens”, and from here on only this table gets mixed.

The table on the right is from an untrained model, so its pattern carries no meaning. What to read off it is that the arrangement of raised bits differs from row to row — that is, each token has its own separate 128 bits, and at this point no token has mixed with any other at all.

Figure 3: token-mixing carries information to every patch

Section titled “Figure 3: token-mixing carries information to every patch”

Here we confirm by measurement why a global view is possible without attention. We build an input with a single patch blacked out and put the difference against the original input (bright = a changed bit) side by side in two panels. On the left is right after patch embedding: patch embedding is independent per token, so the change should stay confined to the single row of the erased token. On the right is after one block (token-mix → channel-mix): because token-mixing is wired across the token axis, the change should leak out to other tokens. LutLayer wiring is sparse (2 inputs per gate) so one block only reaches a few tokens, but it spreads across the whole image as blocks stack. This is the mechanism by which a Mixer with no attention sees globally, and this figure is the measurement of its first stage.

On the left only one row lights up; on the right several rows do. The information from the single erased patch reached other tokens in just one block, and the print and the asserts above put a number on how many tokens changed.

Training: an ordinary PyTorch loop

Section titled “Training: an ordinary PyTorch loop”

No special learning rule is used. This is completely ordinary PyTorch with Adam and cross entropy. Every 500 steps accuracy is measured in two ways.

  • soft eval (train()) … the state where each gate is still a continuous mixture of the 16 logic functions. Gradients flow, but it is not a circuit yet
  • hard eval (eval()) … each gate fixed to a single logic function by argmax: a pure Boolean circuit that can be burned into hardware as is

hard is the number that counts, and a state where only soft is high is a sign that “the circuit has not been made up its mind”.

Evaluation: learning curves and misclassifications

Section titled “Evaluation: learning curves and misclassifications”

Figure 4: the soft and hard learning curves

Section titled “Figure 4: the soft and hard learning curves”

Orange is soft, green is hard. The highlight is not the values themselves but that the two lines do not drift apart.

Why a soft-XOR residual? The residual is taken as a + b - 2ab (exactly XOR for 0/1) because XOR is its own inverse (a XOR b XOR b = a): flip one input and the output necessarily flips too. In other words, it does not destroy information. An operation like soft-OR, which saturates towards 1 as layers stack, makes gradients vanish deep in the network, whereas XOR does not, and intermediate representations stay in {0,1}. That is why hard has a hard time drifting away from soft. If the gap does open up wide, suspect that the gate mixtures are sitting in an intermediate state.

Indeed, green (hard) trails orange (soft) by a little and the two almost coincide at the end. That means the same accuracy is obtained while staying a discrete circuit, which is exactly LogicMixer’s claim. The values plateau around 0.65 only because this is a reduced 2-minute CPU recipe; raising D_CHANNELS / N_BLOCKS / STEPS pushes it straight up.

Figure 5: misclassified examples

Section titled “Figure 5: misclassified examples”

To close, here are ten images the fixed circuit (hard eval) got wrong. Mix-ups between similar shapes should dominate: once the image is chopped into 7x7 tiles, some cases remain hard to tell apart from local information alone. These are the global differences that a small mixing of 16 tokens x 3 blocks could not pick up — which is exactly where adding more blocks has room to help.
