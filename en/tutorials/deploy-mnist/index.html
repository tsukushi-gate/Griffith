4. Deploy

Run the trained circuit with nothing but a C compiler on your machine, without PyTorch. The “4000 logic gates” of MNIST are exported in the order IR -> distribution bundle -> C99 source, built with cc, and 1000 test images are inferred by C alone.

The core of this page is that the integer scores returned by C do not differ from PyTorch’s hard eval in a single element. After pinning down with assert that the trained circuit stays “the same circuit” through export, code generation and C compilation, we count the delivery size (about 58 KB, about 19 KB gzipped) and the runtime memory (4 KB). The inference time per image was about 3 microseconds on the author’s machine (Apple M1 Max, 1 core, cc -O2) (a value that changes with the machine, so it is not put in the page’s output but written to latency.json). Finally, circuits with different gate counts are lined up to confirm that the delivery size is roughly proportional to the number of gates.

The steps for putting this circuit on an ESP32 or an iPhone continue in Run on ESP32 and Run on iPhone, and the overall picture of the deploy kit is in Deploy Kit Quickstart.

What you’ll learn

  1. Every stage of the exit: trained model -> IR -> distribution bundle -> C source -> executable
  2. How to confirm that C’s integer scores match exactly PyTorch hard eval and IR simulate
  3. How to measure delivery size and runtime memory, and how the size grows with the number of gates (us/image depends on the machine, so it is recorded in latency.json)

Prerequisites

  • 1. Train on MNIST — the very circuit we carry here
  • 3. Export to HDL — the IR and the idea of three-stage equivalence
  • Deploy Kit Quickstart — if you first want to run through the whole exit lightly with XOR (optional)

About this page

Estimated time: about 10 minutes / Environment: CPU only (no GPU required) Source script: examples/29_deploy_mnist.py Try it locally: notebooks/29_deploy_mnist.ipynb (an unexecuted notebook with the same content as this page; open it with uv run --group docs jupyter lab notebooks/) Every code output below is the result of an actual run, embedded verbatim.

▶ Open in Colab (enabled once the repository is public)

An example that trains MNIST and runs it as-is in zero-dependency C99 (the deploy kit).

The “circuit of 4000 logic gates” trained in MNIST can only run inside PyTorch. Here we carry it all the way to wrapping it into a form that runs with nothing but a C compiler on your machine, without PyTorch, in a single script.

The road has the following 6 stages, and all of them are executed inside this file.

Orange is the PyTorch world, green is the world treated as a logic circuit, and blue is the integer scores. The final “exact match” is the star: after confirming that the integers C returns do not differ from PyTorch’s hard eval in a single element, we measure the delivery size and the speed.

Run: uv run python examples/29_deploy_mnist.py Expected: hard accuracy around 0.85 / C inference and PyTorch match exactly on 1000 images x 10 classes (a C compiler cc / clang / gcc is required. Artifacts go to out_examples/deploy_mnist/)

Setup: imports, random seed, output directory

Section titled “Setup: imports, random seed, output directory”

The training side uses exactly the same toolkit as MNIST, and the deploy side uses four parts of griffith_logic.deploy.

  • build_bundle / save_bundle / load_bundle … wrap a trained model into a distribution bundle (the circuit’s IR and the class names in a single file), write it out, and read it back
  • generate_c … generate self-contained C source (model.c / model.h) from the bundle
  • verify_c_matches_simulate … actually build the generated C and compare it in integers against the IR reference implementation (simulate), a “pre-shipment gate”

The random seed is fixed, so you get a bundle with the same bytes every time (so it can be used as the file that ESP32 or iPhone demos read).

Output directory and hyperparameters

Section titled “Output directory and hyperparameters”

All artifacts go to out_examples/deploy_mnist/. The file name mnist.bundle.json is fixed, and other demos (embedded, smartphone) read it as it is. The training recipe is the same shrunken one as MNIST (2 layers x 2000 gates, 4000 iters), and it finishes in 1-2 minutes on CPU.

Dataset: keep the images as 8-bit

Section titled “Dataset: keep the images as 8-bit”

We read the 20x20 MNIST. What differs from MNIST is that the images are also kept as integers 0-255 (u8). What reaches a device is “8-bit pixels from a camera or a file”, not real numbers like 0.37.

PyTorch’s hard eval binarized with x.round() (1 if above 0.5). A pixel value k/255 > 0.5 is the same as k >= 128, so the C side gets the same bit string just by comparing the u8 pixel with the threshold 128. We let the C driver we write later carry this one-line binarization.

Training: build the same circuit as the MNIST page

Section titled “Training: build the same circuit as the MNIST page”

The model and the training loop are identical to MNIST: just run LutLayer x 2 + GroupSum in ordinary PyTorch. What to watch is not the accuracy but that model.eval() at the end of training (= the discretized circuit) becomes the reference for every exit from here on.

IR and bundle: wrap the trained model into one file

Section titled “IR and bundle: wrap the trained model into one file”

The first step of the exit is the same as Export to HDL: export_ir fixes the trained model into the IR (a collection of truth tables). The IR depends on neither PyTorch nor C and is the source of truth shared by all targets.

validate(ir, target='hdl') checks that the IR holds together as a circuit (consistency of bit widths and wiring). If it fails here, fix it before generating C.

The input contract and the contents of the model JSON

Section titled “The input contract and the contents of the model JSON”

What goes into the bundle is the IR and the class names (labels). We fix the input as a 0/1 string of 400 bits (the 20x20 pixels in row-major order, 1 if pixel >= 128). There is also a way to put image preprocessing (thresholds, normalization) into the bundle, but it is available only for image models that start from a convolution (LutConv2d); for a fully connected circuit, the convention is to pass C the bit string itself. Turning the pixels into bits is the job of Python or of the C driver; here we let the latter do it in one line.

“A dict that has only {'ir': ...}” is the input (the model JSON) of griffith deploy bundle.

export_ir puts the time of export (created_at) into the IR metadata. Left as it is, the bytes of the bundle would change on every run (and the gzip size would fluctuate by +-1 B), so below we overwrite it with a fixed time (FIXED_TIME) so that the same training result gives the same bytes.

Build and write out the bundle

Section titled “Build and write out the bundle”

build_bundle combines the IR and the labels, and save_bundle writes them into a single file. With the CLI it is the same operation as griffith deploy bundle mnist_model.json -o mnist.bundle.json. The delivery size (compressed) is measured with gzip. gzip.compress writes the current time into its header by default, so we pin it with mtime=0 so that the same bundle always gives the same number of bytes.

C code generation and build: make model.c and hand it to cc

Section titled “C code generation and build: make model.c and hand it to cc”

We read the bundle back (the structure is validated on load) and create the C source with generate_c. The output is just two files, model.h (the public API and size constants) and model.c (the static const truth tables and the straight-line code that evaluates them in order), with zero heap allocation and zero floating point at run time. The public API is mdl_infer(input_bits, scores): pass 400 0/1 values and 10 integer scores come back.

The evaluation of the logic gates itself is done by the runtime (mdl_kernels.c, about 60 KB as source) with bit operations, 32 gates at a time. With the CLI, griffith deploy codegen-c does the same thing.

Write a host driver and build it

Section titled “Write a host driver and build it”

We prepare a small main that just calls the generated mdl_infer(bits, scores). It reads N u8 images from a file, compares each pixel with 128 to make 400 bits, and then infers. It repeats this for N images x reps times, measures the time of the whole loop (including the binarization), and writes the scores of the last pass to a file. The time is measured with clock() (standard C), so there is no extra dependency. Only the driver uses malloc, which is a convenience for the host; the model itself keeps its work area inside a context.

Infer in C and compare with PyTorch in integers

Section titled “Infer in C and compare with PyTorch in integers”

We write the first 1000 test images as u8 and feed them to the C executable (the binarization is done by the C driver). What comes back is a 1000 x 10 matrix of integer scores (the number of gates, out of the 200 assigned to each class, that output 1).

There are three things to compare against: PyTorch hard eval (the output of model.eval() multiplied back by tau), the IR reference implementation simulate (numpy integer bit operations), and C. We pin down with assert that the three do not differ in a single element — the proof that the trained circuit stays the same circuit through export, code generation and C compilation.

Pre-shipment gate: verify-c

Section titled “Pre-shipment gate: verify-c”

The above was a check against “the model we just trained”. verify_c_matches_simulate is more mechanical: it makes several random bit strings, generates and builds C from the bundle, and compares it with the IR reference implementation (the CLI’s griffith deploy verify-c). It is a gate that checks the circuit itself is reproduced correctly in C, independent of your model or images, and it can be built straight into CI or a pre-shipment script.

Delivery size and speed: how many bytes, and how many microseconds per image

Section titled “Delivery size and speed: how many bytes, and how many microseconds per image”

Now that we know it “runs correctly”, we count “how light it is”. There are three kinds of numbers: what you ship (the bytes of the bundle), what you build (the C source), and what you need to run it (the work RAM MDL_CTX_BYTES) plus the speed.

The speed (us/image) changes with the machine and from run to run, so it is not burned into this page’s output (it is measured above and written to out_examples/deploy_mnist/latency.json). On the author’s machine (Apple M1 Max, 1 core, cc -O2) the measured value is about 3 us/image (binarization included, about 330,000 images/s); if you rerun it yourself the order of magnitude is the same but the value changes a little. The byte counts, on the other hand, are the same every time for the same circuit.

Visualization: the digits C read, and the cost against the number of gates

Section titled “Visualization: the digits C read, and the cost against the number of gates”

The first figure overlays the predictions returned by the C executable on the test images. Green is correct and red is wrong; since it matches PyTorch exactly, the red ones are also exactly PyTorch hard eval’s mistakes.

Figure 1: C’s predictions overlaid on the test images

Section titled “Figure 1: C’s predictions overlaid on the test images”

We line up 24 images. The images are the 20x20 pixels (u8) that the circuit received, as they are.

Reading: the mistakes center on confusable digits such as 4 and 9, or 3 and 5, the same tendency as the misclassifications of MNIST. C creates no new mistake at all.

Figure 2: delivery size against the number of gates

Section titled “Figure 2: delivery size against the number of gates”

Since there is only one trained circuit, we make circuits with different widths K and line them up. Size and speed are decided only by the “shape” of the circuit and hardly depend on which logic functions were learned, so we may measure untrained (randomly initialized) circuits. To check this, we overlay the circuit with K=2000 that was really trained as a star — if it sits on the line of the random circuits, the assumption is correct.

Each point redoes “export_ir -> bundle -> C generation -> build -> timing over 1000 images” from scratch. The timing results (us/image) change with the machine, so they appear neither in the figure nor in the output but are written to latency.json. The figure is a deterministic one with sizes only.

Reading: all three size curves have slope 1 (twice the gates means about twice the size), and the star (trained) sits right on the line of the random circuits. The speed also grows in the same direction: on the author’s machine (Apple M1 Max, 1 core, cc -O2) it was about 0.4 us/image at 500 gates and about 6 us/image at 8,000 gates (the details of the slope change with the machine, so check latency.json yourself). Size and speed are decided by the shape of the circuit, so you can estimate them before shipping — even with 8,000 gates the delivery is about 110 KB, or about 37 KB gzipped.
