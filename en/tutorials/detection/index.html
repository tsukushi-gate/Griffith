Object detection with zero multipliers (CenterNet)

Object detection with zero multipliers. We follow a minimal CenterNet built only from LutConv2d and OrPooling2d as it finds digits in synthetic Multi-MNIST and draws bounding boxes. 784 gates in total, mAP@0.5 = 0.255 (measured on the minimal 500-step budget).

To fit within a few minutes of budget, this page is reduced to class-agnostic (1-class) detection (the 10-class version failed to take off on the same budget). Restoring the two lines that fold the GT heatmap with a max over the class axis gives you the 10-class version. For the production recipe, see experiments/train_detection.py (its measured numbers predate the per-image scoping fix in compute_map, so they are awaiting re-measurement).

What you’ll learn

  1. How to build a CenterNet-style detector from nothing but LutConv2d and OrPooling2d (784 gates in total)
  2. The post-processing that turns a heatmap plus size regression into bounding boxes
  3. How to shrink things to fit a few minutes of budget, and how to go back to the 10-class and production recipes

Prerequisites

  • U-Net (segmentation) — the basics of dense prediction heads
  • 5. Export a CNN to HDL

▶ Open in Colab (enabled once the repository is public)

An example of solving object detection (CenterNet-LUT) with a logic-gate circuit.

examples/06_mnist.py was classification: “one image → one class”. Object detection is two steps harder than that: you must answer where (coordinates) and for an unknown number of objects.

Here we put the idea of CenterNet (Zhou et al. 2019) straight onto logic gates. CenterNet uses neither anchors nor an NMS network; it detects with just three feature maps:

This structure — “the outputs are all conv feature maps” — suits logic-gate NNs well. The backbone can be built from just LutConv2d (a differentiable LUT tree that learns the truth table of a 3x3 window) and OrPooling2d (OR/max pooling), and numeric quantities like size/offset can be produced with SpatialGroupSum (count the firing gates and multiply by a constant). In other words it becomes a detector that completes even coordinate regression without a single multiplier.

The whole circuit (the actual sizes of this reduced recipe: k=8, 3 layers)

Where the concrete example shows up as a figure: the flow above can actually be seen in the figures on this page.

  1. “input (binarized)” = the output of TH above (bit planes at 64×64)
  2. “GT center heatmap” vs. “predicted heatmap (16x16)” = the output of HMS above. Training has worked once a peak rises at the center of each digit
  3. “predicted boxes” = BOX above: the result of applying size/offset at each peak and drawing a box

How it is done

  • The image is turned into bits at the entrance. The grayscale is cut at three thresholds, converting “darkness” into 3 bit planes (3ch). A logic circuit only accepts 0/1, so this is the rule
  • A convolution is a truth table over a 3×3 window. LutConv2d is a tree of LUTs (depth 3) that looks at the 3×3 = 9 pixels of a window and returns 0 or 1. Where a CNN filter is “an inner product of weights”, this is “a table lookup”, and only the contents of the table are learned
  • Pooling is OR. In the world of bits, max pooling coincides with “1 if any input is 1” = OR. No comparators and no adders are needed
  • Numbers (probability, width, height, coordinates) are made by counting wires. SpatialGroupSum is how a circuit without multipliers emits reals: it counts “how many of these 32 wires are 1” in groups of 16 and scales by 1/16 to land in 0–1. The resolution is therefore 1/16 — raise size_group if you need finer values. The heatmap is built the same way: logic-gate outputs are discretized to 0/1 at evaluation time, so a single channel would make the heatmap binary and leave every peak tied. Averaging 16 wires (hm_group=16) yields 17 levels of confidence: 0, 1/16, …, 1
  • No anchors and no NMS. CenterNet reduces detection to “make only the center cell 1”, so every output stays a feature map and decoding is just a local peak search

[About the imports] The model definition experiments/detection_model.py still lives outside the package (under experiments/), so this example loads it by extending sys.path. We plan to move it to the public API on the griffith_logic side in the future, at which point only the import lines change.

[About the scale] To fit within a few minutes on CPU, this example is a heavily reduced version:

  • 1-2 MNIST digits on a 64x64 canvas (the production recipe uses 96x96)
  • Backbone width k=8 (production 64), 3 layers (production 8)
  • 500 iterations
  • Class-agnostic (1-class) detection: only guess “is there a digit or not” The aim is not accuracy but seeing with your own eyes that “the boxes come out at plausible positions and sizes”. The serious 10-class recipe (which also identifies the digit) is in experiments/train_detection.py (see the model zoo). Note that the detection numbers listed there predate the per-image scoping fix in compute_map and are awaiting re-measurement.

Run: uv run python examples/21_detection.py Time: 2-4 minutes on CPU (depending on machine load) Expected result: class-agnostic mAP@0.5 around 0.20-0.30. The final figure shows the predicted boxes

Setup: imports and the reduced recipe

Section titled “Setup: imports and the reduced recipe”

All we need is PyTorch, matplotlib, and the detection parts that live under experiments/ (dataset, loss, decoding, mAP). The circuit building blocks themselves (LutConv2d / OrPooling2d / SpatialGroupSum) are used from inside those model definitions.

Adding experiments/ to the import path

Section titled “Adding experiments/ to the import path”

The model definition detection_model.py still lives outside the package (under experiments/), so we extend sys.path before importing it. It will move to the public griffith_logic API eventually, and at that point only the import lines change.

Hyperparameters (a reduced recipe that fits in a few CPU minutes)

Section titled “Hyperparameters (a reduced recipe that fits in a few CPU minutes)”

The output stride (STRIDE) says how many input pixels correspond to one cell of the detection grid. We look at a 64×64 image with stride 4, so the grid is 16×16. Coordinates are predicted on that grid and multiplied by STRIDE at the end to get back to image coordinates. SCORE_TH is the lowest score at which a heatmap peak is accepted as one detection: lower it and you over-detect, raise it and you miss objects.

Data: synthetic Multi-MNIST and CenterNet-style targets

Section titled “Data: synthetic Multi-MNIST and CenterNet-style targets”

We scatter MNIST digits over a 64×64 canvas (without overlap) and build CenterNet-style targets. The targets are three feature maps, matching the model’s three outputs one for one.

  • heatmap — the probability that an object centre lies in that cell. The centre cell is 1 and its neighbourhood is a smooth Gaussian (a bell-shaped weight), so a small miss is not punished hard
  • size (2ch) — the width and height of the object in that cell (normalised to 0–1 by image size)
  • offset (2ch) — the grid is coarse, so this is the sub-pixel shift from the cell centre to the true centre

The image itself is threshold-binarized into three bit planes, (3, 64, 64). The input wires of a logic circuit accept nothing but 0/1, so this binarization is the house rule at the door.

Model: a CenterNet made entirely of LutConv2d

Section titled “Model: a CenterNet made entirely of LutConv2d”

The first three lines materialize the data, and then we build the detector (both live in one cell). The backbone is three stages of Conv→Pool→Conv→Pool→Conv that take 64×64 down to 16×16, and three heads grow out of that same feature map (heatmap / size / offset).

Why a single centre point is enough to detect an object: instead of aiming directly at “the box around the object”, the problem is split into a per-cell classification (“which cell holds the centre”) and a numeric prediction (“the width, height and shift for that cell”). No anchors (pre-defined candidate boxes) and no NMS network (post-processing that removes duplicate boxes) are needed, and every output stays a plain conv feature map. That “everything is a feature map” property is exactly why this design suits a logic-gate circuit.

Why a circuit with no multipliers can emit numbers like width and height: the trick is SpatialGroupSum, which counts “how many of the 32 wires are 1” in groups of 16 and scales by 1/16. The resolution is therefore in steps of 1/16 — raise size_group if you need finer values.

Loss and evaluation: focal loss and mAP@0.5

Section titled “Loss and evaluation: focal loss and mAP@0.5”

Focal loss is a loss for classification where positives are extremely rare: it damps the contribution of the easy background cells and shifts the weight onto learning the centre cells. Out of the 16×16 = 256 cells at most two are centres, so without it the circuit settles into answering “everything is background”.

The metric mAP@0.5 is the standard measure for object detection. The overlap between a predicted box and a ground-truth box is measured by IoU (Intersection over Union = area of the overlap ÷ area of the union, 0–1); an IoU of 0.5 or more counts as a hit, and the misses and the over-detections are averaged into a single number.

Evaluation: decode → mAP

Section titled “Evaluation: decode → mAP”

Decoding detections is post-processing with no learned parameters: keep only the local peaks of the heatmap (cells that are the maximum within their own 3×3 window) and rebuild boxes there from size and offset. “Keeping the local peaks” already plays the role of NMS, so no dedicated post-processing network is required.

The training loop

Section titled “The training loop”

The body is ordinary PyTorch, and nowhere do you have to be aware that this is a logic-gate circuit. Every EVAL_EVERY steps we measure mAP and print the breakdown of the loss (hm / size / off) with it. The breakdown tells you directly which head is failing to make progress.

Reading the results: training curves and detections

Section titled “Reading the results: training curves and detections”

Figure 1: how the loss and mAP evolve

Section titled “Figure 1: how the loss and mAP evolve”

What to look for: the left axis (orange) is CenterNet’s total loss and the right axis (green) is mAP@0.5. The point is not just that the loss goes down, but that the detection metric climbs along with it.

What it says: the size loss falls to near zero almost immediately — MNIST digits are always 28×28, so width and height are effectively constants. The hard parts are the heatmap and the offset, and the shape of the two curves shows that mAP is decided almost entirely by the quality of the heatmap peaks.

Figure 2: the learned heatmap

Section titled “Figure 2: the learned heatmap”

What to look for: the input (after binarization) on the left, the target centre heatmap in the middle, and the circuit’s output on the right. The only thing that matters is whether a peak rises at the centre of each digit; once that is right, everything else is fine coordinate adjustment.

What it says: the target heatmap is a smooth hill, whereas the prediction looks like “a few points lighting up”. At evaluation time the LUT outputs are discretized to {0,1}, so confidence can only be expressed as a vote of 16 wires (17 levels of 1/16), and the skirt of the hill is never reproduced. Even so, as long as the peak position is right the decoder returns the correct box — which is why mAP takes off even in this reduced recipe. If you want the shape of the skirt as well, you need a larger width k and more layers.

Figure 3: drawing the predicted boxes on the images (the finale of this example)

Section titled “Figure 3: drawing the predicted boxes on the images (the finale of this example)”

What to look for: cyan dashed boxes are the ground truth, solid boxes the predictions (green = IoU 0.5 or more against the ground truth, red = a miss). If the positions and sizes overlap plausibly, you can see with your own eyes that coordinates can be regressed by a logic-gate circuit alone, without a single multiplier — that is what this closing figure is for.

This is the last figure, so here is how to read it, in advance. Among the eight images, the digits with a green box are right in both position and size, while a red box marks a case where “the peak rose in the wrong place” — which happens most often when two digits sit close together. The sizes of the boxes all look alike because MNIST digits are always 28×28, so the size head only has to memorise a constant. In other words, the figure says that what is hard in this reduced recipe is not the size but getting the centre right.
