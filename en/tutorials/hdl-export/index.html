3. Export to HDL

Extract a trained model into the IR (intermediate representation, the source of truth), generate Verilog, and check it against the golden model. This walks the whole exit path of the library: “train in PyTorch -> IR -> HDL”.

What you’ll learn

  1. The three steps of the exit path: trained model -> IR (intermediate representation, the source of truth) -> Verilog
  2. What kind of accidents validate(ir, target='hdl') catches for you before synthesis
  3. How to confirm the three-way equivalence PyTorch hard eval <=> IR simulate <=> HDL simulation

Prerequisites

  • Appendix: XOR Internals — the very circuit burned here
  • IR Guide — why the IR is the source of truth

About this page

Estimated time: about 10 minutes / Environment: CPU only (no GPU required) Source script: examples/04_export_hdl.py Try it locally: notebooks/04_export_hdl.ipynb (an unexecuted notebook with the same content as this page; open it with uv run --group docs jupyter lab notebooks/) Every code output below is the result of an actual run, embedded verbatim.

▶ Open in Colab (enabled once the repository is public)

An example of trained model -> IR -> Verilog export.

Train XOR and generate the IR (intermediate representation) JSON and Verilog. If iverilog is available, equivalence against the golden model is checked as well.

This is the shortest path through the library’s exit — “convert weights trained in PyTorch into a logic circuit that needs no GPU”. It has three stages: (1) training, (2) universal discretization into the IR, (3) Verilog generation from the IR. Since the IR is the source of truth and the simulator and the HDL both derive from it, “the PyTorch output = the IR output = the output of the actual circuit” can be checked mechanically.

Run: uv run python examples/04_export_hdl.py Expected result: out_examples/xor.json and xor.v are generated, and the check is ALLPASS

Setup: the four APIs used on the way out

Section titled “Setup: the four APIs used on the way out”

The path this page walks has four stages — train -> IR -> Verilog -> check — and the API for each one is imported up front. The terms are defined here on first use.

  • export_ir … converts a trained model into the IR (intermediate representation). The IR is JSON normalized as “a collection of truth tables”, and it is the source of truth on the hardware side
  • validate … checks that the IR satisfies the constraints HDL generation requires (bit widths, topological order, and so on)
  • write_verilog … writes synthesizable Verilog (RTL) out of the IR
  • simulate … a reference implementation that interprets the IR with numpy integer bit operations (the golden model)

Training: building the XOR circuit to be burned

Section titled “Training: building the XOR circuit to be burned”

Showing the export procedure is the point of this page, so the target is the smallest possible XOR (Appendix: XOR — exactly the same 32-gate setup). The training loop is plain PyTorch too, so here you can just run 500 steps and move on.

Looking at the circuit to be burned, before exporting

Section titled “Looking at the circuit to be burned, before exporting”

Figure 1: the network of resolved gates

Section titled “Figure 1: the network of resolved gates”

The moment model.eval() is called, each gate is no longer a mixture of 16 logic functions but a gate fixed to one of them. This draws that state as a circuit diagram. Green nodes are the resolved logic gates, orange is the GroupSum (everything from there on is real-valued).

What to read from it: every node carries a concrete logic function name such as XOR, NAND or A>=B. Those names come from the same path (export/discretize) as the truth tables export_ir uses when emitting Verilog, so the gates in this figure = the gates of the generated circuit.

Counting the circuit’s “bill of materials”

Section titled “Counting the circuit’s “bill of materials””

The same circuit seen from another angle. Each gate’s truth table (4 bits = 16 possibilities for a 2-input gate) is treated as a gate ID, and we count how many of each of the 16 logic functions were used. truth_tables_from_lut_layer is the same discretization path export_ir uses internally, so the breakdown counted here matches the breakdown of the contents of the generated Verilog.

Figure 2: how many gates of each logic function

Section titled “Figure 2: how many gates of each logic function”

All 16 kinds are laid out along the x axis (zero-count ones are kept as blanks, so you also see what was not used).

What to read from it: only some of the 16 kinds are used, heavily biased towards XOR / XNOR — nobody told the network to “use XOR”, yet gradients alone selected the logic functions the task needs. On the other hand constants (FALSE) and pass-throughs of an input (A / !B) remain. These are effectively wires or dead nodes, redundancy a human would not write. Training was never told to “use up all 32 gates”, so the leftover gates settled into a shape where they do nothing — which is also room for the synthesis tool downstream to remove them.

Extracting into the IR

Section titled “Extracting into the IR”

The IR being the source of truth is the keystone of this library’s design. Verilog, VHDL and the simulator all derive from it — which is exactly why “the PyTorch output = the IR output = the output of the actual circuit” can be checked mechanically.

Two things in the procedure are not optional.

  • Switch to eval() before extracting. Left in train(), you would be looking at the continuous-mixture state, which is not decided as a circuit
  • Run validate(ir, target='hdl'). Checking bit widths, topological order and the absence of unsupported nodes here prevents accidents you would otherwise only notice in the synthesis tool after having written out the Verilog

Generating Verilog

Section titled “Generating Verilog”

write_verilog writes synthesizable RTL (register transfer level description) out of the IR. The resulting .v can be thrown straight at vendor tools such as Vivado or Quartus. If you need VHDL instead, you only swap in write_vhdl — the downstream is interchangeable precisely because the upstream IR is a normalized source of truth.

Checking the three-way equivalence

Section titled “Checking the three-way equivalence”

The correctness of the exit is guaranteed by “three independent implementations producing the same answer”.

  1. PyTorch hard eval … the result of running the same truth tables through floating-point tensor operations
  2. IR simulate … a reference implementation using integer bit operations with no floating point at all (the golden model)
  3. HDL simulation … the result of actually running the generated Verilog under iverilog

If 1 and 2 agree, “nothing was dropped in the discretization”; if 3 agrees as well, you can assert that “the learned weights match the behavior of the actual hardware”.

Figure 3: the three-way equivalence as a single truth table

Section titled “Figure 3: the three-way equivalence as a single truth table”

Finally the answers from the three routes above are collected into one table. Rows are the 4 input patterns, columns are the routes to the answer (teacher label / PyTorch hard / IR simulate). The number in a cell is the output class; green = matches expected, red = mismatch.

What to read from it (written up front, since this is the last figure): all three columns are filled with the same values and the whole thing turns green. That is the confirmation that “the world of training (PyTorch)” and “the world of circuits (IR / HDL)” represent the same function; a single red cell would be a bug in the export. The figure title also carries the result of the HDL check under iverilog.
