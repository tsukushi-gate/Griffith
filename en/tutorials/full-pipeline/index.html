7. End-to-End Walkthrough: From Training to FPGA

An end-to-end walkthrough that runs training -> how to read the loss log -> HDL export -> the hand-off to an FPGA implementation, in one continuous flow. The subject is kept to the minimal XOR, so even without having read the individual pages (MNIST / Export to HDL) first, this page alone gives you the whole picture of “from training to becoming a circuit”.

What you’ll learn

  1. One unbroken flow from training -> the loss log -> IR -> Verilog -> the FPGA implementation
  2. Which API to call at each stage (this page alone runs all the way to the end)
  3. A map of which individual page to go back to when you want to dig deeper

Prerequisites

  • None — you can start reading from this page

About this page

Estimated time: about 15 minutes / Environment: CPU only (no GPU required) Source script: none (a composite of examples/01_xor.py and examples/04_export_hdl.py) Try it locally: notebooks/07_full_pipeline.ipynb (an unexecuted notebook with the same content as this page; open it with uv run --group docs jupyter lab notebooks/) Every code output below is the result of an actual run, embedded verbatim.

▶ Open in Colab (enabled once the repository is public)

1. Data and model

Section titled “1. Data and model”

XOR is “the smallest problem that cannot be linearly separated”, the standard task for measuring the expressive power of a logic gate circuit. griffith_logic.datasets.xor2() returns a dataset enumerating the 4 patterns in butterfly convention order. The model is the minimal setup of two LutLayers + GroupSum (which aggregates gate outputs per class).

2. Training and how to read the loss log

Section titled “2. Training and how to read the loss log”

Training is ordinary PyTorch (cross_entropy + Adam). What is specific here is that soft (during training) and hard (the discrete circuit) accuracy can be different things; watching the loss alone makes you miss the situation “it goes down in soft but breaks as a circuit”. So log hard accuracy (the accuracy under model.eval()) at the same interval alongside the loss.

Figure 1: how the loss and the soft/hard accuracy evolve

Section titled “Figure 1: how the loss and the soft/hard accuracy evolve”

The table alone makes it hard to see “when the circuit was decided”, so the same history is turned into a single figure. Left is the loss, right the accuracy, drawing soft (still under continuous relaxation) and hard (the circuit fixed by argmax) on top of each other. While these two lines are apart, the state is “the model under training solves it, but the burned circuit does not”.

Key points for reading it:

  • hard acc often reaches 1.00 before the loss has fully bottomed out. Correctness as a circuit is decided by the argmax after discretization, so the absolute value of the loss is not the goal.
  • If the loss falls but hard acc does not rise, it is a sign that the continuous relaxation is camped out in an “intermediate probability distribution” (it breaks under discretization). Suspect the temperature tau, the learning rate, or the layer width.
  • Conversely, if hard acc oscillates at 1.00, it has already learned enough and you may stop early.

3. The same code becomes this circuit

Section titled “3. The same code becomes this circuit”

All that was written so far is the three lines nn.Sequential(LutLayer(2, 16), LutLayer(16, 16), GroupSum(k=2)), but the reality is 16 gate nodes and the wires that connect them. plot_circuit() turns that circuit straight into a figure from the model.

Figure 2: the circuit before and after training

Section titled “Figure 2: the circuit before and after training”
  • Left (resolve=False) — before training. Each node is a mixture of the 16 logic functions (AND/OR/XOR/…), so it can only be called a LUT. The color intensity is the certainty of the gate distribution; the paler it is, the more “still undecided which function it is”.
  • Right (resolve=True) — after training. The name of the logic function fixed to one by argmax (AND / XOR / NAND / !A / A>=B …) goes into the node.

The claim that training is the work of picking one gate out of sixteen candidates, one at a time turns straight into a picture. The node names are derived from the truth tables the later export_ir() uses when emitting Verilog, so the gates in this figure are identical to the gates of the circuit actually burned.

For real models with more than a few hundred gates, drawing every node only turns into mush, so plot_circuit() automatically switches to an overview (layers = boxes, wiring = arrows labeled with counts) (you may also call plot_abstract() directly). For how to read it, see Wiring visualization.

4. Extract into the IR

Section titled “4. Extract into the IR”

export_ir() walks a trained nn.Module and, whichever parameterization it was trained with, turns it into an IR (JSON) universally discretized into truth tables. The IR is the source of truth on the hardware side; Verilog / VHDL / the simulator all derive from it. Use validate(ir, target='hdl') to check the constraints HDL generation requires (bit widths, topological order and so on) up front.

5. Generate Verilog and check it

Section titled “5. Generate Verilog and check it”

write_verilog() writes out synthesizable Verilog, which is then matched against simulate() (the bit-exact numpy golden model). If iverilog is installed, the generated Verilog itself is simulated and automatically verified to match the golden model on every pattern.

At this point the same XOR has gone through three separate implementations: PyTorch’s model.eval(), the numpy implementation simulate(), and the Verilog simulator. These three agreeing on every input pattern is the guarantee that “the trained model = the burned circuit”. With only 4 patterns, we can simply lay the three sets of predictions side by side and look at all of them.

Figure 3: the same XOR through three implementations

Section titled “Figure 3: the same XOR through three implementations”

The rows are “label / PyTorch eval / IR simulate” and the columns are the 4 input patterns. The number in each cell is the predicted class.

What to read from it: the three rows are filled with the same sequence 0 1 1 0 — the XOR exactly as labeled is reproduced identically by PyTorch’s discretization path and by numpy’s integer bit operations. If even a single cell disagreed, that would be a bug in the export.

6. From here to the FPGA

Section titled “6. From here to the FPGA”

The generated .v is synthesizable RTL you can throw straight at vendor tools (Vivado / Quartus etc.). For the hardware-side steps — pin assignment, clocking, bitstream generation — see the HDL equivalence verification guide.
