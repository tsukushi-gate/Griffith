5. Export a CNN to HDL

Train a CNN made of logic gate convolutions (LutConv2d) + OR pooling + a LUT fully connected layer, and convert the whole thing into Verilog / VHDL. When it becomes IR, the convolution is unrolled into per-tree-level lut_layers, and padding’s boundary handling is folded into specialized truth tables.

What you’ll learn

  1. How to assemble a logic gate CNN out of LutConv2d + OR pooling + a LUT fully connected layer
  2. How a convolution gets unrolled into per-tree-level lut_layers when it becomes IR
  3. That padding’s boundary handling is folded into specialized truth tables

Prerequisites

  • 3. Export to HDL — go through the whole pipeline on a fully connected circuit first
  • 1. Train on MNIST

About this page

Estimated time: about 10 minutes / Environment: CPU only (no GPU required) Source script: examples/05_cnn_export_hdl.py Try it locally: notebooks/05_cnn_export_hdl.ipynb (an unexecuted notebook with the same content as this page; open it with uv run --group docs jupyter lab notebooks/) Every code output below is the result of an actual run, embedded verbatim.

▶ Open in Colab (enabled once the repository is public)

An example of HDL export for a CNN (logic gate convolution).

Train a CNN classifier of LutConv2d (tree structured) + OR pooling + LUT fully connected + GroupSum on a small task and convert the whole thing into Verilog/VHDL. Padding’s boundary handling is folded in automatically by truth table specialization.

Where 04_export_hdl.py did the fully connected version, this one shows that the same procedure goes through unchanged for a model that includes convolutions. A convolution is a structure that “reuses the same weights at every position”, but a circuit has no notion of weight sharing, so it gets unrolled to every position when it becomes IR. Counting how much the gate count balloons is also a purpose of this script.

The shape of this model (with measured numbers)

Green is “the world of logic, where only bits (0 or 1) flow”, orange is “real numbers”. Real numbers appear only in the final GroupSum; everything before it is a mesh of gates.

Inside LutConv2d (the tree for one pixel)

The number of leaves is n_inputs ** tree_depth = 2 ** 2 = 4, and the number of internal gates is 3. This tree is held for each of the 4 channels and applied to all 64 pixels of the image, so it comes to 4ch x 64 px x 3 gates = 768 gates.

How it works (jargon explained as it comes up)

  • The images are 0/1 from the start — what enters a logic gate is only a High/Low voltage, so what the circuit can read is “bits” and nothing else. Real images too are binarized by thresholding or thermometer encoding (opening brightness into a few scale bits) before they go in
  • Convolution = sliding a small window over the image and applying the same circuit. Here a 3x3 window (the receptive field) is slid one pixel at a time, and the same tree is evaluated at every position
  • A tree = a small circuit of stacked gate stages. The first stage takes 4 bits to 2 bits, the second takes 2 bits to 1 bit. tree_depth is that number of stages, the knob for expressiveness
  • The leaf wiring is fixed at random — which 4 of the 9 bits are looked at is decided the moment the layer is created and never moves during training. What training changes is only “which of the 16 two-input logic functions each gate becomes”
  • Pooling = shrinking 4 nearby bits into 1 bit. Max pooling of a real-valued NN is, in the world of bits, exactly OR (1 if any one of them is 1), and one OR gate is enough
  • padding = filling the outside of the image with 0. At the border the window sticks out of the image, but what it sticks out into is the constant 0, so when it becomes a circuit that is folded straight into the truth tables and disappears
  • unroll = replicating the circuit once per position, because a circuit has no weight reuse. In PyTorch it is weights for 12 gates, but in hardware 768 gates line up
  • GroupSum = the exit that adds up the gate output bits per class into a score. This is where real numbers first appear, and argmax decides the class

The figures walk through, in order: an overview of the whole model as an architecture diagram with real data flowing through it, then the bit feature maps the circuit sees, the fully connected head as an actual circuit, which IR node the gate count balloons at after unrolling, the “bill of materials” of the baked circuit (the breakdown of the 16 two-input logic functions), and finally the fact that PyTorch’s hard eval and the IR simulate agree right down to the scores.

Run: uv run python examples/05_cnn_export_hdl.py Expected result: the IR simulate predictions match PyTorch and (if iverilog is present) the check is ALLPASS

Setup: the APIs the convolutional export needs

Section titled “Setup: the APIs the convolutional export needs”

On top of the fully connected version in 3. Export to HDL, parts for convolution join in.

  • LutConv2d … the logic gate version of convolution. A layer that picks a few bits out of a 3x3 window and emits one bit through a tree of 2-input gates
  • OrPooling2d … max pooling in the world of bits. It just takes the OR of 4 nearby bits
  • write_verilog / write_vhdl … write out two kinds of HDL from the same IR
  • truth_tables_from_conv / gate_id_from_tt_n2 … take the trained gates out as truth tables and map them onto one of the 16 two-input logic functions (used to print gate names inside the figures)

Dataset: guess which side is brighter

Section titled “Dataset: guess which side is brighter”

Make 8x8 binary images and label them by “number of ones in the left 4 columns > number of ones in the right 4 columns”.

Why this task ── it is a problem of gathering counts while sliding a local window over the whole image, so the structure of convolution + pooling applies directly. And because it is as small as 8x8, everything downstream — the IR conversion, the Verilog generation, the check — goes through in a few seconds.

The point is that the input is 0/1 from the start. What can be fed into a logic gate is only a High/Low voltage, so real images too are binarized by thresholding or thermometer encoding (opening brightness into a few scale bits) before they go in.

Model definition: a logic gate CNN

Section titled “Model definition: a logic gate CNN”

It is just four layers stacked, but everything about what each part of a real-valued CNN turns into in the world of bits shows up right here.

  • LutConv2d(1, 4, kernel_size=3, tree_depth=2, padding=1) … picks 4 bits out of the 9 bits of a 3x3 window (the receptive field) and emits 1 bit through a tree of two stacked stages of 2-input gates. tree_depth is the depth of the tree = the knob for expressiveness. Which 4 bits are looked at is decided at random the moment the layer is created, and never moves during training
  • OrPooling2d(kernel_size=2) … corresponds to max pooling of a real-valued CNN. In the world of bits, “1 if any one of them is 1” is exactly OR, so one OR gate is enough (average pooling needs adders, so it is not used)
  • LutLayer(64, 32) … a fully connected LUT layer that takes the flattened 64 bits
  • GroupSum(k=2, tau=4.0) … the exit that aggregates 32 gates into 2 classes. This is the only place real numbers appear

Training and hard evaluation

Section titled “Training and hard evaluation”

Training is just an ordinary PyTorch loop run for 300 steps. In train() mode each gate behaves continuously as a “weighted sum of the 16 logic functions”, which is why gradients flow.

It is fixed as a circuit only from eval() onward, and the accuracy measured there is the hard accuracy (= the accuracy as a baked circuit). If it drops there, the judgement is that the soft-to-hard gap is large.

Visualization: an architecture diagram with real data flowing

Section titled “Visualization: an architecture diagram with real data flowing”

What to read: hard accuracy is around 0.76. With a tiny recipe of fewer than 1000 gates in total and 300 training steps, a wide-area aggregation task — “which side is brighter” — is solved well above chance (0.5).

From here on is the heart of this page: first we make a single architecture diagram with real data pushed through it. The next few cells are the preparation for that figure (the palette, helper functions, and pulling out the intermediate bits).

Figure 1: bits flowing all the way to the last layer

Section titled “Figure 1: bits flowing all the way to the last layer”

The top row is the actual bits of one image going through the layers (input 8x8 → conv 4ch → pooling → flatten → fully connected → finally the real-valued GroupSum scores). Bottom left is which positions of the receptive field the tree’s leaves L0–L3 look at, bottom center is the inside of the tree for one pixel (with the gate names actually settled by training), and bottom right is the breakdown of the gate count after unrolling.

unroll means replicating the convolution for every output position, because a circuit has no weight reuse. On the PyTorch side it is weights for 12 gates, but in hardware 768 gates line up ── and that arithmetic is written out at the bottom right of the figure.

What to read: following the top row from left to right shows that the values stay 0/1 all the way to the end (only the GroupSum scores at the far right, drawn in orange, are real numbers). In the breakdown at the bottom right, the 12 shared gates balloon into 768 gates through unrolling, and adding pooling and the fully connected layer brings the whole thing to 864 gates. It is this post-unroll gate count, not PyTorch’s parameter count, that is the FPGA area.

Figure 2: what the circuit sees as input, and the bits the convolution layer emitted

Section titled “Figure 2: what the circuit sees as input, and the bits the convolution layer emitted”

The top row is the input 8x8 binary images (= the circuit’s 64 input wires), the bottom row is the 4-channel output of LutConv2d. The feature maps of a real-valued CNN are real numbers, but here, because of eval(), they are pure 0/1.

What to read: the four channels each emit a different pattern, showing that trees of different logic functions are at work on the same input. Since both the inputs and the outputs are bits, they connect straight on as wires into the next layer (the OR pooling).

Figure 3: look at the fully connected head as an actual circuit diagram

Section titled “Figure 3: look at the fully connected head as an actual circuit diagram”

Pull out only the fully connected head of the second half of the model (LutLayer(64→32) + GroupSum(k=2)) and draw it as an actual circuit diagram. The 64 grey boxes are the bits after pooling, the 32 green boxes are the settled gates, and orange is the real-valued scores of the 2 classes.

What to read: the nodes carry the names of concrete logic functions such as XOR and NAND. These gate names come from export/discretize (the one and only discretization path that the IR and Verilog use), so the gates drawn in this figure become exactly the gates of the generated Verilog.

Into the IR and HDL generation

Section titled “Into the IR and HDL generation”

The procedure is the same as the fully connected version; the only difference is passing input_shape=(1, 8, 8) to export_ir (because the expansion needs the image size — for a fully connected model input_width is enough).

This is where the convolution is unrolled into a lut_layer per tree level. The boundary handling of padding=1 too is folded in as a specialization of the truth tables and disappears from the circuit, using the fact that what the window sticks out into is the constant 0. VHDL can be generated from the same IR ── pick whichever matches your toolchain.

Figure 4: where unrolling makes the gate count balloon

Section titled “Figure 4: where unrolling makes the gate count balloon”

Line up the gate count (out_width) of each IR node as horizontal bars. A lut_layer node lines up per tree stage (tree_depth), so which stage dominates the area is obvious at a glance. This is exactly the estimate of FPGA implementation area.

What to read: level 0 of the convolution (2 gates per pixel × 4ch × 64 pixels = 512) is the largest, and the 32 gates of the fully connected head are within the noise. What determines the area is not the “width” of a layer but how many pixels the convolution is expanded over.

Figure 5: what gates is the baked circuit made of?

Section titled “Figure 5: what gates is the baked circuit made of?”

Every gate in the IR carries a truth table. For 2 inputs it is one of the 16 logic functions, so naming and counting them gives you the circuit’s bill of materials. It is the information that corresponds one-to-one with lines like 4'h8 >> {a, b} in the generated Verilog (OR pooling is a 4-input LUT, so it is excluded from this tally).

What to read: of the 16 kinds, AND stands out, followed by A>B (= A and not B) ── functions in the direction of “is the bit at this position set” are the ones being chosen. On the other hand, the constant FALSE and pass-throughs remain at around 10%. These are effectively dead nodes or wires, so they are room for the downstream logic synthesis tool to strip away, and the gate count that actually lands will be smaller than this tally.

Checking against the golden model

Section titled “Checking against the golden model”

Just as in the fully connected version, we match PyTorch’s hard eval against the IR simulate. The one thing that needs care in the convolutional version is matching the scale: GroupSum returns logits divided by tau, whereas the IR scores are the raw sums, so multiply tau=4.0 back before comparing.

The requirement is not “roughly matching” but that the scores agree bit for bit. A mismatch here is a bug in the IR conversion, so the threshold must never be loosened.

Figure 6: PyTorch (hard eval) and the IR simulate are the same circuit

Section titled “Figure 6: PyTorch (hard eval) and the IR simulate are the same circuit”

The same agreement is confirmed in two ways. The left is a scatter plot of 64 samples × 2 class scores (PyTorch on the horizontal axis, IR on the vertical), the right is a line of the class-0 scores in sample order.

What to read (written first, since this is the last figure): on the left every point sits on the dashed y=xy=xy=x (the values are integers, so points overlap), and on the right the dashed line of the IR simulate lands exactly on top of PyTorch’s thick line. This is the first and second rung of the three-way equivalence ── a single stray point means a bug in the IR conversion. The final cell also prints the result of the third rung, the check by iverilog.
