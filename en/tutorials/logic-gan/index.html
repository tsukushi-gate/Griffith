Making images from a random bit string — and breaking it (LogicGAN)

Make images by pushing a random bit string — the kind a physical RNG or an LFSR can supply directly — through a logic circuit. And then break it. We train a stabilized configuration (STABLE) and an untuned one (NAIVE) from the same initial circuit, put them side by side, and show by measurement how adversarial training falls apart.

The difference is just four knobs (G:D=3:1 / bit-flip noise on D’s input / label smoothing / lower learning rate for D). In the untuned version the G loss diverges to 7.22 and D accuracy pins at 1.000 — the Generator has been wiped out. We also do not hide the fact that with this reduced recipe mode collapse (1/4) occurs in both conditions.

What you’ll learn

  1. How to make images with a logic circuit driven by a random bit string — the kind a physical RNG or an LFSR can supply
  2. The four knobs that stabilize adversarial training (update ratio / input noise / label smoothing / D’s learning rate)
  3. How to spot a broken GAN — a diverging G loss, D accuracy pinned at 1.000, and mode collapse

Prerequisites

  • Folding an image into 96 bits — a binary-latent VAE — generation without adversarial training
  • Running Training

LogicGAN — an example of making images from a random bit string with logic circuits alone (and of how it breaks).

Generation in 18_logic_vae.py was “latent bits → decoder circuit → image”. A GAN adds a Discriminator and pits it adversarially against the Generator. LogicGAN builds both out of LutLayer stacks, and the Generator’s input is not continuous Gaussian noise but a random bit string z ~ Bernoulli(0.5) — the most natural noise source for a logic circuit, suppliable straight from a physical entropy source or an LFSR.

Green is the logic circuit, where everything stays in bits, orange is where real numbers appear (only the final sum in the discriminator), and blue is the random bit source. From the entrance to the exit of generation, not a single multiplication appears.

How it actually works (in four lines)

Section titled “How it actually works (in four lines)”
  1. The noise source is a coin flip. z is not a continuous Gaussian but 64 bits of Bernoulli(0.5). A comparator against u < 0.5 produces it, so a physical RNG or an LFSR (a small circuit that makes pseudo-random numbers) can be wired straight in.
  2. The Generator is a LutLayer stack. z is already bits, so no preprocessing (thermometer coding or anything else) is needed. The output of the last LutLayer is the pixel: soft (a continuous pixel probability) while training, hard (a pure Boolean circuit) at inference, emitting exactly 0/1.
  3. The Discriminator is a logic circuit too. Pixels go through LutLayers, and GroupSum counts “how many gates fired” to make a single real/fake logit.
  4. Gradients flow back through the soft phase. Only during training is each gate a weighted sum over 16 logic functions (continuous), which is what lets the gradient travel from D to G. The circuit that gets baked is discrete, but a smooth shadow runs alongside it while it learns — a two-layer structure.

Differences from an ordinary GAN

Section titled “Differences from an ordinary GAN”
What to look atOrdinary GANLogicGAN

The four stabilizing knobs and how much they help are exactly the STABLE / NAIVE comparison below. At the end of this page you will find an architecture figure with real data flowing through it and the real circuit of the trained Generator (one gate per pixel, drawn down to the logic function each gate resolved to under argmax).

The other subject of this example is “how it breaks”: A GAN carries a double instability: “adversarial min-max” × “discrete output”. With an untuned configuration the Discriminator overwhelms the Generator, the G loss diverges and the Generator is wiped out — this is a failure mode measured in this repository, and tests/test_logic_gan.py::test_training_dynamics_smoke guards the healthy region. This script runs both the stabilized and the untuned version and puts them side by side, making it visible which setting does what.

The reduced recipe used in this example: The full run (experiments/train_logic_gan.py) trains 30 epochs on 28x28 binary MNIST, but here we use a minimal task, “four 8x8 binary patterns”, so it fits in under 3 minutes on CPU. What you get is the level where “the shape of the pattern starts to appear”, and moreover with the reduced recipe mode collapse (all samples come out looking alike) occurs. That too is part of the lesson.

Run: uv run python examples/19_logic_gan.py Expected result (seed=0, about 90 seconds on CPU): stabilized late G loss 0.9-1.0 / late D accuracy 0.8-0.9 / untuned late G loss in the 7s / late D accuracy 1.00 (collapsed). Mode coverage is 1/4 in both. GAN trajectories diverge on tiny floating-point differences, so the numbers shift a little between CPUs (Apple Silicon and x86). The stabilized recipe was chosen so that D accuracy stays < 0.99 for seeds 0-2 on both CPUs (the earlier D learning rate 0.003 / smoothing 0.1 let D win completely on x86)

Setup: imports and the random seed

Section titled “Setup: imports and the random seed”

All we need is PyTorch, matplotlib, this library’s LogicGAN (the model itself), and the circuit-drawing utilities. No special GAN framework is required.

GAN (generative adversarial network / adversarial training) — a training framework that trains one network by pitting two networks against each other: one that draws pictures, and one that guesses whether a picture is real or fake. The one that draws is the Generator, the one that guesses is the Discriminator; from here on we write them G and D. The goal is for G to produce pictures so convincing that D cannot see through them.

LogicGAN builds both G and D out of stacks of logic gates (LutLayer), so from entrance to exit not a single multiplication appears.

Hyperparameters

Section titled “Hyperparameters”

The image is squeezed down to a minimal 8x8 = 64 pixels, so the whole thing runs to the end in a few minutes even on CPU. NOISE_BITS is how many bits of the random bit string z go into G (defined in the next section). DISC_HIDDEN is kept far smaller than the Generator’s HIDDEN as the very first move toward not letting D win too easily — the reason shows up in the “Training” section.

Data: a four-pattern toy distribution where collapse can be counted

Section titled “Data: a four-pattern toy distribution where collapse can be counted”

The training distribution is just four 8x8 binary patterns: “only the top half / bottom half / left half / right half is black”. There is a reason for picking such a simple distribution instead of handwritten digits.

Mode collapse — the phenomenon where the generator stops producing more than a slice of the distribution, so no matter how often you sample you get back the same kind of picture. It is the best-known failure mode of GANs.

If the distribution has only four points in it, then simply assigning each generated image to its nearest training pattern and counting tells you “how many of the four kinds it can produce” — it is mechanically measurable. With MNIST you can only eyeball whether it “collapsed”, but with this toy distribution collapse becomes a number — which is exactly what Figure 3 shows.

The model: the Generator and the Discriminator

Section titled “The model: the Generator and the Discriminator”

Before we get into the code, let us pin down the symbols that recur throughout this page.

  • z — the random bit string that is the Generator’s input (NOISE_BITS=64 zeros and ones in a row). It plays exactly the role of the latent vector an ordinary GAN uses — the “seed of the picture”, randomness supplied from outside — except that here it is bits, not real-valued Gaussian noise. That means it can be supplied directly from a physical entropy source or from an LFSR (a linear-feedback shift register: a tiny circuit that emits pseudo-random bits using nothing but a few flip-flops and an XOR). The upshot is that LogicGAN has the shape of “feed 64 zeros and ones in from outside the circuit and an image comes out”.
  • G (the Generator) — the logic circuit that takes z and returns the bits of an image (8x8 = 64 bits).
  • D (the Discriminator) — the logic circuit that takes the bits of an image and returns exactly one logit.
  • Logit — a real-valued score meaning “the larger, the more real it looks”. Push it through a sigmoid and you get a probability; its sign is itself the boundary (0) between “judged real” and “judged fake”. In LogicGAN, real numbers appear only from D’s final GroupSum, which counts bits, onward.
  • D accuracy — the fraction of real/fake calls D gets right. Around 0.5 means the two are evenly matched and healthy; pinned at 1.0 means D is winning too hard, and the gradient returning to G dries up (= the sign of collapse).

The training loop itself: only four knobs as arguments

Section titled “The training loop itself: only four knobs as arguments”

A GAN makes progress only while G and D are in balance. If either one wins, the gradient dries up and the other can no longer learn anything. That is why a GAN needs “knobs for keeping the balance”. This function takes exactly four of them as arguments, and the difference between the stabilized version (STABLE) and the untuned version (NAIVE) that we compare later is closed under those four.

  • Update ratio g_steps — how many times G is updated for each single update of D (the D:G update-count ratio). D learns faster, so we run G more often to let it catch up.
  • Input noise flip_prob — flip bits with the same probability for real and fake alike before showing them to D. This prevents D from reaching a state where it can separate the two perfectly.
  • Label smoothing label_smoothing — the knob that “makes the real label 0.9 instead of 1.0”. A standard GAN remedy for stopping D from asserting “this is definitely real”.
  • D’s learning rate disc_lr — simply shorten D’s stride to keep it from winning too hard.

When training is done, gan.generate(...) samples 128 images. That runs the hard eval path (each gate resolved by argmax to a single logic function, executed as a pure Boolean circuit), so the pixels that come back are strictly 0/1, not approximations from the continuous relaxation.

Training: running the stabilized and the untuned version side by side

Section titled “Training: running the stabilized and the untuned version side by side”

This is the centrepiece of the page. We run two training runs from the same initial circuit, with only the knobs changed.

  • STABLE — update ratio G:D=3:1 / input noise p=0.1 / label smoothing 0.2 / D learning rate 0.001 (1/10 of G’s)
  • NAIVE — a GAN written straightforwardly, with all four stabilizers removed

There are two numbers to watch in the output. late G loss (the average over the last 200 iterations) says whether G is still alive; late D accuracy is the thermometer of the adversarial balance, where 1.0 means collapse. Instead of merely saying “GANs are unstable” in words, this example lays the ways it breaks side by side, measured.

The numbers above are claims we want reproduced on every run, so we write them as asserts rather than prose. All three are minimum conditions for this example not being broken (the same healthy region is guarded by tests/test_logic_gan.py::test_training_dynamics_smoke).

Figure 1: generated samples (stabilized / untuned)

Section titled “Figure 1: generated samples (stabilized / untuned)”

The top row is eight generated images from STABLE, the bottom row eight from NAIVE. There is exactly one thing to look for: “do they take the shape of the four training patterns (squares with only one half blacked out)?”

What is being drawn is the output of hard eval (the pure Boolean circuit resolved by argmax), so each black-or-white cell is literally a bit the circuit output, not an approximation from the continuous relaxation.

How to read it: on this tiny 8x8 task both rows are only at the stage where “the pattern’s shape starts to show”, and the Hamming distance to the nearest pattern is around 20 of 64 pixels (the exact values for this run are in the output above). The difference to look at is not how pretty the pictures are but whether learning is still alive, and that shows in Figure 2 next. Same circuit, same initial values; the only difference is the four knobs. In both rows the eight images look alike — that is mode collapse, and Figure 3 is where it becomes a number.

Figure 2: how the adversarial balance evolves (this is how you spot collapse)

Section titled “Figure 2: how the adversarial balance evolves (this is how you spot collapse)”

We look at the balance of power between G and D over time: G loss on top, D accuracy on the bottom. The bottom panel is the one to watch: wandering around 0.5 means the two are evenly matched and healthy, while pinned at 1.0 means D is winning too hard. The G loss on top rising monotonically as a consequence is the classic footprint of collapse.

How to read it: with NAIVE (red) the D accuracy pins at 1.0 early on and the G loss keeps climbing into the 7s — D has won outright and the gradient returning to G has dried up. With STABLE (green) the D accuracy settles at 0.8-0.9 (it does not stick at 1.0) and the G loss stays below the dashed line (2.0). The four knobs work not by “making G stronger” but by “not letting D win too hard”.

Figure 3: mode coverage (collapsing is normal with the reduced recipe)

Section titled “Figure 3: mode coverage (collapsing is normal with the reduced recipe)”

We assign the 128 generated images to their nearest training pattern and count them into four bars. The dashed line is the training distribution (0.25 each, since the four are uniform), so four bars lined up around the dashed line means the distribution is covered; a single bar sticking out means mode collapse.

How to read it: in both conditions only one bar stands up, and the number of covered modes is 1/4 — meaning even the stabilized version has mode-collapsed. This is as far as an 8x8, 4000-iteration reduced recipe gets, and that is the honest limit of this example. It also says that “keeping the adversarial balance (Figure 2)” and “covering the distribution (Figure 3)” are two different difficulties — the full run (experiments/train_logic_gan.py) goes further by training 30 epochs on 28x28 binary MNIST.

Figure 4: the architecture (one real sample pushed through the stabilized run)

Section titled “Figure 4: the architecture (one real sample pushed through the stabilized run)”

We push exactly one real sample through the trained stabilized model and paste the intermediate states into the figure. The top row is G (64 random bits z → logic circuit → image bits), the bottom row is D (image bits → logic circuit → a single real-valued logit). The numbers inside the boxes are the real gate counts, and the dots on the far right are where D placed the logits for the real and the fake sample (the dashed line is the decision boundary).

The box to pay attention to is readout — the output stage, where the correspondence is one LUT per pixel. The colour legend is the project-wide one: green = logic gates / orange = where real numbers appear / blue = the random bit source / grey = data.

How to read it: orange (real numbers) exists only at the tail of D, from the GroupSum that counts bits onward. From z to the image, and from the image to just before the verdict, what flows is nothing but 0/1 bits and not one multiplication appears. The logits come out higher on the real side than on the fake side (the gap is in the output above), so the breakdown behind Figure 2’s “D accuracy does not stick at 1.0” is visible in this single picture.

Figure 5: the real circuit (the trained Generator itself)

Section titled “Figure 5: the real circuit (the trained Generator itself)”

To close, a picture of the circuit that is itself the result of training. This figure is not a schematic of the code; it is the real thing, raised from the trained parameters.

  • Left — the whole Generator (320 gates). It is large enough that plot_circuit automatically switches to the overview (layers = boxes, arrows = the number of wires).
  • Right — the output stage generator.readout spread out in the layout of the image. One cell = one pixel = one LUT, and what is written in the cell is the name of the logic function it resolved to under argmax (XOR / NAND / A>=B, and so on). How dark a cell is reflects how often that pixel came out as 1 in the generated samples.

How to read it: which gate emits which square of the generated image can be read off directly, by name. These names are identical to the gate names baked into the IR (the JSON representation this library holds as the source of truth for a circuit) and into the Verilog (the hardware description you push into an FPGA or ASIC) emitted from it. As the last print shows, the 64 gates of the output stage concentrate into a handful of logic functions — we really do have, in hand, “a small circuit that turns random bits into a picture”.
