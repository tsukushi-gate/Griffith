3. Replace an MLP with a DLGN

Keep the same data and the same training loop as the previous page, and change only the inside of the model into logic gates. nn.Linear + ReLU → LutLayer, and the output nn.Linear (+softmax) → GroupSum: this page shows that one-to-one replacement in real code and overlays both training curves on a single graph.

Measured: MLP 0.9535 versus DLGN soft 0.8745 / hard 0.8660 (discretization gap +0.0085). A circuit that performs not a single multiplication gets 90% of the way to the real-valued NN. We look side by side at the difference between “weights (real numbers you multiply by)” and “truth tables (which logic function it is)”, and at the two phases, soft and hard, that appear for the first time with a DLGN — then close with a replacement checklist.

Replacing an MLP with a DLGN — solving the same problem with logic gates (beginner course 3/3).

Take the MNIST 20x20 MLP built on the previous page and, keeping the same data and the same training loop, change only the inside of the model into logic gates. In practice only two lines are rewritten.

The point of this page is to line up, with measurements, what actually changes when you replace them.

  • The way you write training does not change — cross_entropy, backward() and Adam all stay the same
  • What gets learned changes — instead of real-valued weights (numbers used for multiplication), it is the truth table of each gate (the choice of logic function: is it AND, or XOR?)
  • You now have two accuracies — always report both the continuous relaxation used during training (soft) and the circuit fixed to a single logic function by argmax (hard). That difference is the discretization gap, the one and only biggest gotcha specific to DLGNs

We close with a “checklist for porting an MLP to a DLGN”.

Run: uv run python examples/26_mlp_to_dlgn.py Expected result: MLP test acc around 0.95 / DLGN hard acc around 0.87 (about a minute on CPU)

Setup: bring in the tools for both the real-valued and the logic side

Section titled “Setup: bring in the tools for both the real-valued and the logic side”

On top of the PyTorch set used up to the previous page, we add three things from this library.

  • LutLayer … a layer that learns a LUT (lookup table = truth table). It drops straight into the place of nn.Linear + activation
  • GroupSum … the exit from the world of logic to classification scores. It counts the output bits per class
  • gate_labels … returns, by name, which of the 16 logic functions each gate settled on after training

Drop the inputs to bits for hard evaluation

Section titled “Drop the inputs to bits for hard evaluation”

There is exactly one preprocessing step that only the DLGN needs. In hard evaluation (= evaluation as the burned circuit itself) the input must be 0/1 bits as well. What enters an actual FPGA are the High/Low levels of signal wires, not real numbers like “0.37”. We build test_bits by binarizing with round().

Model B: a DLGN solving the same problem

Section titled “Model B: a DLGN solving the same problem”

Model B is the main topic. There are only two replacement rules.

  • nn.Linear + activation → LutLayer(in, out, n_inputs=2). No activation function is attached — the non-linearity is held by the gates (AND / XOR …) themselves
  • The output nn.Linear(h, 10) → GroupSum(k=10, tau=10.0). A layer that merely splits the final-layer bits into 10 classes x 200 wires and counts “how many 1s stand”, holding not a single weight (a single adder on the hardware side)

Why does the width grow from 128 to 2000? — one gate with n_inputs=2 looks at only 2 wires of the previous layer. Its information content is orders of magnitude below that of an nn.Linear neuron which sees all 400 inputs, so you have to compensate with sheer numbers. “Take a width one or two orders of magnitude larger” becomes the basic DLGN practice.

Training: run both models in the same loop

Section titled “Training: run both models in the same loop”

We update A and B side by side inside the same for. Not one character of the training loop code changes — cross_entropy, backward() and Adam can all be used as they are. This is the demonstration of this library’s claim that “you can bring your PyTorch assets over untouched”.

There are only two differences. (1) The learning rate on the DLGN side is 10x larger (the reason is in the comment below). (2) The DLGN measures two accuracies, soft and hard. Soft is the continuous relaxation in train() mode; hard is the accuracy of “the burnable circuit itself”, with every gate fixed to a single logic function in eval() mode.

Figure 1: training curves on the same task with the same training loop

Section titled “Figure 1: training curves on the same task with the same training loop”

Three lines are overlaid on one figure. Blue = the real-valued MLP, orange = the DLGN’s soft, green = the DLGN’s hard. What to look at is green, since that is the true score as “a circuit that holds not a single multiplier”.

What to read here: the MLP (blue) plateaus around 0.95, while the DLGN’s hard (green) climbs to about 0.87. The difference is roughly 0.08 — a circuit performing not a single multiplication reaches 90% of the way to the real-valued NN. The space between orange (soft) and green (hard) is the discretization gap, and in this run it is only about +0.01 — meaning that the model being trained and the burned circuit are almost the same thing. When this gap opens wide, the gates have not made up their minds about “which logic function” they are.

Figure 2: the learned “real-valued weights” and “chosen gates”

Section titled “Figure 2: the learned “real-valued weights” and “chosen gates””

We put the shape of “what got learned” side by side. On the left, a histogram of the MLP’s first-layer weights; on the right, the breakdown of which logic function each of the 2000 gates in the DLGN’s first layer settled on. The point is to see that even under the same phrase “we learned parameters”, what you end up with is completely different.

What to read here: the left is a continuous distribution spreading smoothly around 0 — every value is a “half-hearted real number”, and every inference needs a multiplication. The right is a discrete breakdown with only 16 bars (or fewer), where each gate has landed on a logic function with a name such as OR / NOR / pass-through (passing A or B straight on); the top five are printed in the output right below. The point of this one figure is that the product of training has changed from “a vector of real numbers” into “a bill of materials for a circuit”.

Figure 3: soft and hard are “different models”

Section titled “Figure 3: soft and hard are “different models””

We line up the 10-class scores for one and the same test image under soft (left) and hard (right). In ordinary PyTorch, eval() only changes the behaviour of BatchNorm or Dropout, but in a DLGN, eval() swaps out the mathematics of the model itself. This figure is there to make that difference tangible.

What to read here: the two bar charts are similar in shape but their values do not match. Soft is a continuous value produced by the mixture of 16 logic functions, while hard is “how many of the 200 wires stood at 1” divided by tau — they are simply different computations. Even so, the highest class agrees: the output right below shows soft, hard and the ground truth all lining up.
