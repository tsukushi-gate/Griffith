Growing "n-gram detectors" with a logic-gate TextCNN

We set up a problem that counting words alone can never solve, and show in an irrefutable form that convolution works as an n-gram detector. In bigram-XOR classification, where the label is decided by the XNOR of affirmative × good word / negative × bad word, every word appears equally often in both classes — that is, unigrams carry zero information (the ceiling for any rule based on word frequency is 0.535 = essentially chance).

The logic-gate TextCNN solves it at 1.000 in both soft and hard. And peeking at the filters after training, filter 6 is “really good” and filter 4 is “never awful” — they have grown into detectors for specific pairs of words. A natural sequel to Appendix: XOR.

What you’ll learn

  1. How to build a task that word frequency cannot solve in principle (bigram-XOR classification), and what that means
  2. How the logic-gate TextCNN is put together, and that it solves the task at 1.000 in both soft and hard
  3. How to peek at the filters after training and confirm they have grown into “detectors for specific pairs of words”

  • Appendix: peeking at the mechanism with a minimal XOR — the minimal version of the same XOR structure

▶ Open in Colab (enabled once the repository is public)

An example of training text classification with a TextCNN (logic-gate version) and visualizing how convolution works as an n-gram detector.

TextCNN (Kim 2014) is a model that “convolves a width-k window over a sequence of embeddings and, with Global Max Pool, picks up only the position that responded most strongly”, so each filter is effectively a circuit that detects whether a specific n-gram appeared anywhere in the sentence. This example replaces that convolution with LutConv2d (a tree of differentiable logic gates), and the embeddings too are dropped to {0,1} bit vectors by LogicEmbedding. In other words the whole sentence is classified by a logic circuit that uses not a single multiplication.

The model lives in experiments/train_textcnn.py, not inside the package

TextCNNModel is placed on the experiment-script side (outside the package), so you cannot get it via from griffith_logic import .... Here we add experiments/ to sys.path and import it the same way tests/test_textcnn.py does. (Loading the experiment script triggers reading .env and importing the wandb utilities, but no logs are sent unless init_wandb is called.)

The subject: bigram XOR

Upstream uses the Japanese sentiment dataset WRIME, but downloading and training take time. Here, so it runs in a few minutes, we set up a synthetic task that is impossible to solve with unigrams alone:

The label is decided by the XOR of two words: an affirmative modifier (really / truly) or a negative one (not / never), combined with a good word (good / nice) or a bad word (bad / awful). Every word appears equally often in both classes, so no amount of counting word occurrences (= unigrams) gets you above 50%. The only way to solve it is to look at two adjacent words as a set, which is exactly the shape a width-2 convolution is good at. Think of it as the XOR of example 01 having moved into the world of words.

The whole circuit (actual sizes: 12 words per sentence, 32-bit embeddings)

Where the concrete example shows up as a figure: the EX flow above can be seen for real in the second figure on this page, “k=2 conv activations before Global Max Pool”. The horizontal axis is the window position and the vertical axis is the filter index, and only the column at the position of the decisive bigram lights up. The third figure averages that over every test sentence, showing that different filters respond to different combinations such as “really good” and “not bad”.

How it is done

  • The embedding is made of bits too. LogicEmbedding assigns 32 bit lines to each word. During training they are reals in [0,1], but a regularizer pushes them to the extremes, so in the end a word is literally “a 32-bit code”
  • The window covers the entire embedding dimension. With kernel=(k, 32) matching the embedding width, the horizontal output width becomes 1, so a 2D convolution turns into a 1D n-gram sweep
  • One filter = one n-gram detection circuit. For k=2 it is a LUT tree that looks at 2 words × 32 bits = 64 wires and returns 0 or 1. Logic such as “1 if the code of really and the code of good” is learned as a table
  • Global Max Pool is OR. In the world of bits max = OR, so “did this n-gram appear anywhere in the sentence?” can be folded into a single bit, discarding position. This is also why TextCNN is strong on word order but insensitive to location
  • Unigrams cap out at 50%. Every word appears equally often in both classes, so a circuit that merely counts word occurrences cannot solve this in principle. Needing to look at two adjacent words as a set — a width-2 window — is the essence of this task

Run: uv run python examples/23_textcnn.py Expected result: hard accuracy 1.00 (about 1 minute on CPU)

Setup: imports and the random seed

Section titled “Setup: imports and the random seed”

The model itself, TextCNNModel, lives in experiments/train_textcnn.py, which is outside the package, so we extend sys.path before importing it. Both the gates’ initial wiring and the embeddings are randomly initialised, so we fix both PyTorch’s and Python’s own RNG for reproducibility.

Hyperparameters

Section titled “Hyperparameters”

An n-gram is a run of n consecutive words (two words make a bigram). KERNELS = [2, 3] means “run a width-2 window and a width-3 window side by side”; since the answer to this task lives in a bigram, the k=2 branch is the protagonist. D_EMB is how many bit lines represent one word — here a word becomes a 32-bit code.

Data: building a task unigrams can never solve

Section titled “Data: building a task unigrams can never solve”

The label is the XOR of “modifier × meaning word”: really good and not bad are positive, not good and really bad are negative. Every word appears equally often in both classes by construction, so no amount of counting word frequencies (unigrams, features that look at one word at a time) can push accuracy past 50%.

Why this task: by artificially creating a situation where no solution exists other than “looking at two adjacent words together”, any accuracy gained after training becomes evidence that the convolution really captured an n-gram. Think of it as the XOR of example 01 moving into the world of words.

Vocabulary and IDs

Section titled “Vocabulary and IDs”

We build the dictionary that maps words to integer IDs. The embedding layer looks these IDs up and returns bit strings, so this is the boundary between “the world of strings” and “the world of circuits”.

Measuring the unigram ceiling up front

Section titled “Measuring the unigram ceiling up front”

We actually run the best unigram rule — “positive if it contains a good word” — and record its accuracy. Later we draw that value as a dashed line on the learning curve, so that whatever rises above it can be read as the contribution of the n-gram. Measuring the claim first keeps the result from being confused with “it just happened to go up”.

Model: a logic-gate TextCNN

Section titled “Model: a logic-gate TextCNN”

The structure is LogicEmbedding → a LutConv2d branch per k → Global Max Pool → concatenate → a LutLayer stack → GroupSum. There are three points to it.

  • The embeddings are bits too. LogicEmbedding assigns 32 bit lines to each word. During training they are real values in [0,1], but a regularizer pushes them towards both ends, so in the end a word literally becomes a 32-bit code
  • The window covers the whole embedding dimension. With kernel_size=(k, d_emb) the width matches the embedding dimension, so the horizontal output width is 1 and the 2D convolution becomes a 1D scan over n-grams. One filter is “a LUT tree that looks at 2 words × 32 bits = 64 wires and returns 0/1” = one n-gram detector circuit
  • Global Max Pool is OR. In the world of bits, max is “1 if any of them is 1” = OR. This is where why max pooling is OR starts to matter: it lets us discard position and fold “did this n-gram appear anywhere in the sentence” into a single bit. No comparators and no adders needed

Training: cross entropy plus a binarization regularizer on the embeddings

Section titled “Training: cross entropy plus a binarization regularizer on the embeddings”

The loss is cross entropy with a little emb_reg (a regularizer that pushes the embeddings towards 0/1) mixed in. Why it is needed: at inference LogicEmbedding is binarized with a Heaviside step (a step function that cuts at a threshold), so if the values stay half-way during training the codes flip the moment they are discretized and hard accuracy alone collapses. Pushing them to the ends in advance keeps soft and hard in agreement. Accuracy is likewise measured both ways: soft (the continuous relaxation) and hard (the discretized circuit).

Peeking inside the convolution

Section titled “Peeking inside the convolution”

From here we do not stop at “it solved the task” but check what the circuit looked at in order to solve it. TextCNNModel.forward only returns values that have already gone through Global Max Pool, so we extract the pre-pool activations (the 0/1 per window position) ourselves. What we do is the same as the first half of forward.

Visualization: learning curves and what the filters learned

Section titled “Visualization: learning curves and what the filters learned”

Figure 1: learning curves

Section titled “Figure 1: learning curves”

What to look for: orange is soft (the continuous relaxation), green is hard (the discretized logic circuit) and the grey dashed line is the unigram ceiling we measured earlier. The thing to watch is green clearly overtaking the grey dashed line; whatever it gains above that line is the contribution of the n-gram.

What it says: soft and hard rise together, almost on top of each other, and go well past the unigram ceiling (the grey dashed line). The circuit reached territory that counting words cannot touch, and it did so while staying intact under discretization. If soft were high and hard were left behind, that would be a sign of the embeddings or the gates lingering in an intermediate state (which is not what happens here).

Figure 2: where in the sentence the filters fire

Section titled “Figure 2: where in the sentence the filters fire”

What to look for: the vertical axis is the filter index and the horizontal axis is the window position (labelled with the two words that window covers). The pre-pool activations for one positive and one negative sentence are laid out as they are. The thing to watch is that only the column at the position of the decisive bigram lights up — that is the evidence that the convolution captured those two words as a detector. Note that Global Max Pool passes only the maximum of each row downstream, so what matters for classification is not “where it lit up” but “whether it lit up somewhere”.

What it says: check that the lit column matches the position of that sentence’s decisive bigram (the key bigram in the title). If the same filter responds in two sentences where the position differs, that filter is looking at the combination of words, not the position. Rows that never light are normal too; the next figure counts them as “dead filters”.

Figure 3: which filter responds to which bigram

Section titled “Figure 3: which filter responds to which bigram”

What to look for: for each decisive combination (the really good / not good / really bad / not bad families) we average the activation at the position where that bigram was placed, over the whole test set. The vertical axis is the filter and the horizontal axis the bigram. The thing to watch is that each row lights a different column; if they separate, each filter has grown into a detector for a specific n-gram. Conversely, a row where every column is equally bright is a “dead filter” that distinguishes nothing.

What it says: reading the table above row by row puts into words which bigram each filter became a detector for. The larger the “max − min” spread, the more selective the filter; a row whose spread is nearly 0 returns the same value for every bigram and is a dead filter. It is perfectly normal for some of the redundantly provided filters to end up that way, because the stage after Global Max Pool only needs to use the filters that are alive.
