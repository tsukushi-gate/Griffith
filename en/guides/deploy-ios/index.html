Run on iPhone

The C that the deploy kit generates can be called from Swift directly through C interop. No Objective-C wrapper or JNI-style bridging layer is needed; you only expose the C header through a bridging header. The aarch64 NEON path is enabled automatically at compile time. This page collects the procedure for iPhone and the measured results on a real device and on the simulator.

Five models matched as integers on a real iPhone 17

On a real iPhone 17 (iPhone18,3, iOS 26.6.2), all five models ran and their output scores matched the host’s ir/simulate.py as integers. The real-device times are in “Measurement table (real iPhone 17)” below. The simulator times are native execution times on the Apple Silicon Mac (host CPU), not iPhone values (the “Measurement table (simulator)” says so explicitly). You can check the verification status in Platform support.

Prerequisites

Section titled “Prerequisites”
  • macOS with Xcode (including the iOS SDK)
  • To run on a real device: an Apple ID (a free account works) registered in Xcode, and the iPhone in developer mode
  • This repository cloned and uv sync --extra dev --extra cpu done (used to generate the model)

Project layout

Section titled “Project layout”

The SwiftUI demo app is in examples/31_deploy_ios/.

FileRole
gen_model.pyFrom a bundle and samples, creates the files for one model under Models/<name>/
gen_xcodeproj.pyGenerates GriffithDemo.xcodeproj (gen_model.py calls it at the end)
GriffithDemo/The app itself (SwiftUI views, the inference calls, the bridging header)
Models/Generated C and samples per model (generated artifacts; one directory per model)

The C runtime (runtime/c/src/mdl_kernels.c) is referenced by relative path from inside the repository rather than copied. Only the single copy common to all models is linked.

Procedure

Section titled “Procedure”

1. Bring in a model

Section titled “1. Bring in a model”

Run gen_model.py once per model. You can run it any number of times, and it does not touch the other models’ files.

<name> (har_dlgn_k600 in the example above) is lowercase alphanumerics and _ only, and becomes the prefix of the C symbols. For setting up bundles and samples, see Prepare demo models. Every model you bring in is scanned from Models/*/ and automatically bundled into the app. To put in only XOR, bash examples/31_deploy_ios/setup_xor.sh does everything from training to bringing it in.

To put in the three demo models, loop like this.

gen_model.py also takes --dense-flat {auto,on,off} (default auto). It is passed straight through to the same option of codegen-c and decides whether the dense 2-input lut_layer chains become the flat netlist lut_flat. auto adopts it only when the effective-gate reduction is 25% or more, on always does, and off never flattens. The decision and the executed-gate count after flattening are printed to stdout. Flattening grows the work memory (MDL_CTX_BYTES) by the signal table, so use --dense-flat off when memory is the priority. For the same option on ESP32, see Run on ESP32.

2. Call the generated C through a bridging header

Section titled “2. Call the generated C through a bridging header”

To call C from Swift, put the C header in a bridging header (specified with Xcode’s SWIFT_OBJC_BRIDGING_HEADER). In this demo, the model-specific model.h is not put in the bridging header; only the common descriptor gd_model (GdModel.h) is exposed.

gd_model holds the model name, input and output widths, MDL_CTX_BYTES, the gate count, and function pointers for context initialization and inference. On the Swift side you enumerate models with gd_model_count() and gd_model_at(i) and call inference through the descriptor. The caller allocates the work area (MDL_CTX_BYTES worth) and passes it to ctx_init, so no heap allocation happens in C during inference.

The image-model path (face detection)

Section titled “The image-model path (face detection)”

For a model whose input is a u8 image, such as face detection, samples.json carries image (u8 NCHW = 3×128×128 = 49,152 bytes as hex) instead of bits. If the generated model.h has mdl_infer_image_ctx, gen_model.py treats it as an image model and changes the following.

  • It sets input_kind of the descriptor gd_model to 1 (image) and input_bytes to C×H×W
  • The function the unity wrapper calls becomes mdl_infer_image_ctx (preprocessing included; it takes the u8 image as is)
  • The app decodes image into bytes and passes it. The expansion to bits is done by the C side in integers, so Swift needs no floating point

For a model with no label (label: null), the screen shows accuracy as ”—” and instead shows the integer match with the host ir/simulate.py expected scores, n / N, and the latency. The image model’s work RAM (MDL_CTX_BYTES) is a large 1.5 MB, but it is allocated only once at run time. mdl_threads.c is not bundled for image models (single-threaded execution).

3. Avoiding symbol collisions when bundling several models

Section titled “3. Avoiding symbol collisions when bundling several models”

A generated model.c has functions with the same names for every model (such as mdl_infer_ctx and mdl_ctx_init), plus a type definition (mdl_ctx). Linking several models as is collides symbols at link time.

This demo resolves it with a per-model “unity wrapper” <name>_unit.c.

  1. Inside the wrapper, the symbols model.c exposes externally are replaced with model-name-prefixed ones, as in #define mdl_infer_ctx <name>_mdl_infer_ctx
  2. With that in place, model.c is #included and the replacement is reverted with #undef
  3. Each model exposes exactly one const gd_model gd_model_<name>

The runtime (mdl_kernels.c) is linked as a single copy common to all models, so it is not subject to the replacement. Keeping model.h out of the bridging header is for the same reason: to avoid types overlapping between models. gen_model.py generates all of this automatically, so all you need to think about is “bring a model in under a name.”

4. Build and run

Section titled “4. Build and run”

Open examples/31_deploy_ios/GriffithDemo.xcodeproj in Xcode, pick a destination, and Run. From the command line, use xcodebuild. Check the scheme name and destinations with xcodebuild -list and xcrun simctl list devices.

Simulator

Section titled “Simulator”

The simulator needs no code signing, so confirm that things work here first. On an Apple Silicon Mac the simulator also runs as aarch64. Use a device name shown by xcrun simctl list devices available for <simulator name> (a device name that does not exist on the latest OS fails to resolve). The measurements used an iPhone 17 (iOS 26.5), and the C is built with -O3 even in the Debug configuration.

Auto-run with launch arguments and collect the result

Section titled “Auto-run with launch arguments and collect the result”

With the launch arguments -gd_autorun 1 -gd_model <name>, the app runs the given model automatically right after launch (for screenshots and CI). The result goes to standard output as one RESULT {json} line and also to os_log (subsystem com.example.griffithdemo).

Streaming standard output to the terminal with --console-pty lets you collect the RESULT line. simctl launch can time out after 30 seconds right after the simulator boots (a rerun gets through). The measurement table below is for the Release configuration. Add -configuration Release to xcodebuild to build it, and the install path becomes Build/Products/Release-iphonesimulator/GriffithDemo.app.

Real device (signing)

Section titled “Real device (signing)”

A real device needs code signing. In Xcode’s Signing & Capabilities, choose a Team (a personal Team is available even with a free Apple ID). From the command line, pass the Team ID and allow automatic provisioning updates.

Put -- before the app’s arguments

With devicectl device process launch, place -- before the arguments you pass to the app. Without it, devicectl parses -gd_autorun as one of its own options and fails with an error such as Please specify a 'timeout' value between 5 and ....

The generated .xcodeproj is created with the bundle ID (com.example.griffithdemo) and DEVELOPMENT_TEAM empty. To run it in your own environment, change the bundle ID to a value nobody else uses (BUNDLE_ID in gen_xcodeproj.py, or in Xcode). The first time, you need to trust the developer on the iPhone via Settings → General → VPN & Device Management, and turn on Developer Mode under Settings → Privacy & Security. The app does not exit after printing RESULT, so stop it with Ctrl-C once the line appears.

Streaming the app’s standard output to the terminal with devicectl --console is confirmed on a real iPhone 17 (the RESULT JSON line was collected in the terminal). For the Release build, even a free personal Team had its provisioning profile created automatically just by passing -allowProvisioningUpdates. If RESULT does not appear, you can substitute any of these: send it from the on-screen “share result JSON” via AirDrop or Notes, look at os_log in Console.app, or take a screenshot. When measuring, use airplane mode, Low Power Mode OFF, a charging cable connected, and the screen on (heat costs a few percent).

To check only that it compiles for a real device without signing, do this (this procedure is confirmed).

What to check

Section titled “What to check”

For each model, the app infers the bundled samples and shows whether the output scores match the expected values and the time per inference on screen. The reference is the output of the generated C that matched ir/simulate.py integer-exactly on the host (a Mac). So if the iPhone’s result differs from the expected scores, you can isolate it as a problem with the device-side build or environment.

On the models measured this time, the C on the iPhone 17 was 1.7 to 2.0 times faster than the simulator on the Apple Silicon Mac (host CPU). However, the host CPU model, the simulator figure being a median of 12 runs against one run on the device, and differences in load and power state were not controlled. Effect of gate reduction (simulator)

Section titled “Effect of gate reduction (simulator)”

Times here are also host-CPU values

The times in this section are also run times on the iPhone 17 simulator, executed on the Apple Silicon Mac (host CPU), not iPhone values.

We also measured the lossless gate reductions described in Prepare demo models (--sweep, --sweep --dense-flat, and --resynth lossless) in the iOS demo app. We put raw, sweep, and flat in the same binary (15 models bundled), ran them with the order rotated for 6 runs × 2 sets = 12 runs, and took the median of each run’s median (the host was heavily loaded during measurement, and 6 runs alone swung between fast and slow, so we used 12). score_mismatch is 0 in all 144 runs, and the accuracy (50 windows) is identical across raw, sweep, and flat (k6000 80%, k2400 76%, k600 76%, MNIST 84%).

ModelRawsweepflatGates executed raw / sweep / flatctx raw / sweep / flatraw ÷ flat
Activity recognition k600029.81 µs23.46 µs15.42 µs36,000 / 28,636 / 15,12412,000 / 13,872 / 25,736 B1.93x
Activity recognition k24007.67 µs6.93 µs5.35 µs9,600 / 8,681 / 4,8864,800 / 6,284 / 11,896 B1.43x
Activity recognition k6001.98 µs1.65 µs1.25 µs2,400 / 1,989 / 9711,200 / 1,396 / 6,180 B1.58x
MNIST3.22 µs2.92 µs2.98 µs4,000 / 3,615 / 2,2104,000 / 3,616 / 4,612 B1.08x
  • sweep gives 1.1 to 1.3x (raw ÷ sweep is 1.27x for k6000, 1.20x for k600, 1.11x for k2400, 1.10x for MNIST), roughly in line with the gate reduction.
  • flat is 1.4 to 1.9x over raw on the three HAR models, and 1.3 to 1.5x over sweep, largest for k6000 where the gates roughly halve. For MNIST, flat is on par with sweep (0.98 over sweep, very slightly slower): even though the gates drop from 3,615 to 2,210, the time did not drop. We have not isolated the cause (it looks like the table-driven cost per gate is higher than sweep’s dedicated loop, but we have not confirmed it). Together with the fact that the same MNIST halves with flat on the real ESP32, this means the host’s trend must not be applied as is to a real device
  • flat grows ctx (12,000 B to 25,736 B for k6000). In exchange for time, the work memory becomes 2 to 5 times larger
  • Moving from k6000 to k2400: the speed ratio is 3.89x for raw, 3.39x for sweep, and 2.88x for flat. The gate count is 3.75 times smaller, and the accuracy over all 2,947 windows with the host ir/simulate.py drops by 1.0 point, from 0.9009 to 0.8911
  • Face detection --resynth lossless: the gates fall from 2,686 to 2,319 (-13.7%, 253.5 seconds of resynthesis), but the time per inference is 1,584 µs against 1,577 µs, with no difference (1.004x). MDL_CTX_BYTES also stays at 1,544,000 B. The time looks dominated by preprocessing and the image convolutions and does not depend on the gate count (not isolated)

An unsigned Release build for a real device with 15 models bundled (raw, sweep, and flat included) also succeeded. The total of files inside .app is 4,034,511 B (main binary 1,214,432 B, unsigned zip 987,636 B). The number of bundled models differs from “App size” above (5 models). The aggregate is in comparisons_flat_12runs of results/deploy/devices/ios_summary_20261007.json.

Troubleshooting

Section titled “Troubleshooting”
SymptomCause and fix
duplicate symbol at link timeSeveral models’ model.c are linked directly without the unity wrapper. Bring them in again with gen_model.py so they go through <name>_unit.c
No account for team or a signing errorChoose a Team under Xcode’s Signing. Add -allowProvisioningUpdates and pass the correct Team ID as DEVELOPMENT_TEAM
Untrusted Developer on the device and it will not launchTrust the developer under the iPhone’s Settings → General → VPN & Device Management
Added a model but it does not appear in the appCheck that you ran gen_model.py to update gd_registry.c and the .xcodeproj (reopen the project in Xcode)
mdl_kernels.c not foundThe runtime is referenced by relative path to runtime/c/. Check that you have not moved only examples/31_deploy_ios/ out of the repository
