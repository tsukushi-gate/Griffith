Run on ESP32

The C that the deploy kit generates is C99 with zero dependencies, zero heap allocation, and zero floating point. That is why even a small microcontroller like the ESP32 can run inference just by adding model.c and mdl_kernels.c to an ESP-IDF project. This page collects the on-device procedure and the measured results.

Measured on real hardware

On an ESP32-D0WDQ6 (Xtensa LX6, 240 MHz, 4MB flash, no PSRAM), all three activity-recognition models and MNIST run, and the output scores of all 50 samples match the host’s ir/simulate.py as integers. With the default circuit compression in effect, activity recognition k6000 takes 12.7 ms per inference (26.60 ms uncompressed). On the other hand, face detection (a convolutional model) does not fit in static DRAM and cannot be built. The numbers are in the measurement table. You can check the overall verification status in Platform support.

Prerequisites

Section titled “Prerequisites”
  • ESP-IDF v5.x installed, with the environment activatable in your shell
  • An ESP32 development board and a USB cable (flashing and log capture go through the UART bridge)
  • This repository cloned and uv sync --extra dev --extra cpu done (used to generate the model)
  • If you use scripts/esp32_capture.py to capture device logs, run uv sync --extra fpga (it brings in pyserial)

Activate the ESP-IDF environment each time you open a shell.

Project layout

Section titled “Project layout”

The ESP-IDF project is in examples/30_deploy_esp32/.

FileRole
gen_model.pyBuilds main/model/ (generated C + runtime + sample inputs) from a bundle
main/main.cDriver that infers on the bundled samples and prints accuracy and latency to the UART
CMakeLists.txt / main/CMakeLists.txtWire model.c and mdl_kernels.c into the build
sdkconfig.defaultsDefault settings (CPU frequency, optimization, flash size, and so on)

main/model/ is a generated artifact and is not committed. To swap the model, just run gen_model.py once and rebuild with idf.py build.

Procedure

Section titled “Procedure”

1. Generate the model

Section titled “1. Generate the model”

With no arguments it generates XOR (built-in 4 patterns). To load a demo model, pass a bundle and samples. For setting up bundles and samples, see Prepare demo models.

Internally gen_model.py calls griffith deploy codegen-c and writes model.c / model.h / mdl_kernels.c / mdl_kernels.h / mdl_simd.h plus a header of sample inputs (samples.h) into main/model/. If the samples take too much flash, trim them with --max-samples N.

gen_model.py also takes --dense-flat {auto,on,off} (default auto), which is passed straight through to the same option of codegen-c. auto adopts lut_flat (a flat netlist run through a signal table) for the dense 2-input lut_layer chains when the effective-gate reduction is 25% or more, and otherwise keeps the layer-by-layer execution. on always flattens, and off never does. Flattening grows the work RAM (MDL_CTX_BYTES) by the signal table (measured in Effect of gate reduction), so use --dense-flat off when RAM is the priority. The decision and the final executed-gate count are printed to stdout and written to model_info.json.

The sample JSON has the shape {"input_width": N, "samples": [{"bits": "<hex>", "label": int|null, "expected_scores": [...]|null}]}, where bits is a hex byte string (input i is bit i%8 of byte i/8, LSB-first). If expected_scores is present, the device checks the output scores of every sample as integers. Image-input models (face detection) carry image (u8 NCHW) instead of bits; gen_model.py recognizes this automatically and sets SAMPLE_INPUT_IS_IMAGE 1 in samples.h. In that case main.c does not expand to 0/1 but hands the u8 image straight to mdl_infer_image_ctx.

2. Build and flash

Section titled “2. Build and flash”

<port> depends on your environment (/dev/cu.usbserial-* on macOS, /dev/ttyUSB0 and the like on Linux). set-target is only needed the first time and when you change the target. The first build took 43 to 44 seconds on an Apple Silicon Mac (measured with the activity-recognition models).

Building several models side by side

Section titled “Building several models side by side”

Without rewriting main/model/, you can build side by side by separating the output directory and the build directory per model. Pass --out to gen_model.py, and -B and -DMODEL_DIR to idf.py.

3. Capture the log

Section titled “3. Capture the log”

Once flashing is done, capture the UART output. scripts/esp32_capture.py resets the board via DTR/RTS, picks up the boot log, and reads non-interactively until the end.

idf.py -p <port> monitor needs an interactive terminal. To collect non-interactively, use esp32_capture.py (it also turns the RESULT line into a .json). The output has two kinds of lines, and it prints DONE at the end and stops.

OutputContents
SAMPLE i pred=.. exp=.. ns=.. h=XXXXXXXXPer sample: the prediction, the expected label, the time per inference (ns), and a hash of the output scores
RESULT {...}A machine-readable summary (one line of JSON): accuracy, latency statistics, and so on

The h= hash is an FNV-1a over the whole output scores, and it can also be used to check whether the output matches the host run. The same main.c can be built on the host, so generated C that has matched ir/simulate.py integer-exactly can serve directly as the reference for the device’s results. It passes when, on the device and the host, the SAMPLE fields other than ns= and reps= (pred / exp / h / scores) and the score_hash in RESULT match exactly.

Memory design

Section titled “Memory design”

The key to running on a microcontroller is being aware of what lands in RAM and what lands in flash.

RegionWhat goes thereNotes
Flash (.rodata)Weights, instruction lists, truth tables (all static const)Does not eat RAM however large the model is. Shared by all contexts
RAM (.bss)The work area static uint32_t work[MDL_CTX_BYTES / 4]The region rewritten during inference. Its size is MDL_CTX_BYTES in model.h

This project’s policy is to place the work area yourself as a static, and it uses two tricks for that.

  • Place MDL_CTX_BYTES as a static: pass it with mdl_ctx_init(&ctx, work, sizeof(work)). The caller provides the memory, so no heap allocation ever happens (work needs 4-byte alignment)
  • -DMDL_NO_DEFAULT_CTX: removes the default context (the static the generated code holds internally). Without it, a region of the same size would land in .bss twice. In CMake it is specified with target_compile_definitions(${COMPONENT_LIB} PRIVATE MDL_NO_DEFAULT_CTX)

Reading idf.py size

Section titled “Reading idf.py size”

Running idf.py size after the build prints a breakdown of the image. These are the three places to look.

ItemHow to read it
DRAM (.data + .bss)Statically allocated RAM. The MDL_CTX_BYTES portion goes into .bss
Flash Code (.text)Executable code. Most of it is ESP-IDF itself, and the increase from the model is small (measured: XOR 79,048 B → 36,000 gates 79,284 B)
Flash Data (.rodata)The model’s weights and instruction lists. The size of the model shows up here

idf.py size-components also gives a per-component breakdown (the model placed in main versus everything else).

Measurement table

Section titled “Measurement table”

Measured on real hardware. The board is an ESP32-D0WDQ6 rev v1.0 (Xtensa LX6 dual-core 240 MHz, 4MB flash, no PSRAM), with ESP-IDF v5.4-dev-2194 (xtensa-esp-elf 13.2.0, COMPILER_OPTIMIZATION_PERF, equivalent to -O2). The models are the trained production bundles fetched from wandb (har_dlgn_k600 / har_dlgn_k2400 / har_dlgn_k6000), and the samples are 50 UCI-HAR test windows (for MNIST, 50 test images of 20×20 binary; all with labels and expected scores from the host ir/simulate.py). Times are per inference (averaged, repeating each sample until the total reaches 5 ms or more), using only one of the two cores.

  • Integer match: for all three activity-recognition models (k600, k2400, k6000), the SAMPLE lines and score_hash of all 50 windows match exactly between the device and the host (cc -O2). The accuracies 38/50 and 40/50 are the same values as the host ir/simulate.py. The 50 windows are a subset of the whole, so they differ from the accuracy over all 2,947 windows (k600 80.5%, k6000 90.1%)
  • Throughput: uncompressed, about 2,430 windows/s for k600, about 37.6 windows/s for k6000, and about 1,380 images/s for MNIST (1 ÷ mean time). With the default (compressed) circuit it is about 3,440 windows/s for k600, about 78.8 windows/s for k6000, and about 3,080 images/s for MNIST

The build’s wall time was 111.9 seconds, but other jobs were running in parallel, and the user time was comparable to the other models
  • Stress: a test feeding a 36,000-gate IR with 8 random-input samples also gave 26.59 ms, with scores matching 8/8
  • XOR timing: esp_timer has µs resolution, so a short XOR-class inference shows up as discrete values of 5.84 to 5.93 µs

Excerpt of idf.py size (activity recognition k6000, uncompressed)

Section titled “Excerpt of idf.py size (activity recognition k6000, uncompressed)”

IRAM is 48,287 B for all three models (the kernels run from flash, and IRAM is used by ESP-IDF itself). The .bss consists of MDL_CTX_BYTES (12,000 B), the input expansion buffer (4,608 B), and so on, and weights do not eat DRAM; they sit in flash (.rodata). The .rodata is 77,256 B for k600 and 228,488 B for k6000.

Comparison with the host

Section titled “Comparison with the host”

Compared with the same main.c run on an Apple Silicon host (cc -O2, scalar); both sides are the uncompressed circuit.

ModelESP32 (mean)HostRatio
Activity recognition k600410.9 µs1.85 µs (mean)about 220x
Activity recognition k600026.60 ms27.5 µs (median)about 970x
MNIST725.2 µs (mean)3.36 µs (median)about 216x

The host mean for k6000 is 39.1 µs, but there is one outlier of up to 229.6 µs, so we used the median. On the ESP32 the mean and median nearly coincide (MNIST: mean 725.248 µs, median 725.200 µs), so we show the mean. We have not isolated the cause, but the ESP32 side has no SIMD implementation for Xtensa and runs only the scalar path, and clock and cache differences probably also contribute. Only one of the two cores is used (mdl_run_pool is the pthread version and cannot be used as is on FreeRTOS; running on both cores would need a rewrite with two tasks each holding its own context).

Effect of gate reduction

Section titled “Effect of gate reduction”

We measured on the device the lossless gate-reducing optimizations described in Prepare demo models. The bundles used in the measurement are made with griffith deploy bundle --sweep (sweep) and --sweep --dense-flat (flat), and flashed with the same procedure (gen_model.py → idf.py -B / -DMODEL_DIR → flash → capture).

The old flags in this measurement build the same circuit as today’s defaults

The measurement predates the default compression and used the explicit --sweep --dense-flat. The same compression is now applied automatically by default.

  • griffith deploy bundle (default --compress fast) applies sweep to dense models (resynthesis for conv2d) (the old --sweep)
  • griffith deploy codegen-c (default --dense-flat auto) flattens to lut_flat when the effective-gate reduction is 25% or more (the old --dense-flat)

Both use the same transform (flatten_dense), so the circuit is the same. However, we have not re-measured on the device through today’s default path. The “default values” above refer to the flat measurement made with the old flags.

The samples are the same 50 as before, with the same expected scores. The board, ESP-IDF, and optimization are as above.

Today, plain griffith deploy bundle <model.json> plus gen_model.py (default --dense-flat auto) gives the same flat circuit.

In every case score_mismatch is 0, score_hash is identical across raw, sweep, and flat, and the SAMPLE lines match the host cc -O2 run on 50/50. So “the output does not change (lossless)” is confirmed on the device too. All the numbers are in results/deploy/devices/esp32_summary_20261007.json.

  • The 7.4x of k2400 flat cannot be explained by the gate reduction (-49.1%) alone. Something that helped in raw or sweep may have gone away in flat, but we have not investigated the cause. Only this value departs from the other models, so read it with that in mind
  • For memory, flash shrinks and DRAM grows: .rodata is smaller than raw in both sweep and flat, going from 228,488 B to 154,056 B (flat) for k6000. On the other hand, flat grows MDL_CTX_BYTES by the signal table (12,000 B to 25,736 B for k6000), and the DRAM used reaches 41,640 B for k6000. Even so, about 139 KB of static DRAM stays free. Sweep also grows ctx a little (+1,872 B for k6000)
  • The host’s trend does not carry straight over to the ESP32: for MNIST, on the host (cc -O2, median) it gets slower from 2.70 µs for sweep to 2.98 µs for flat, yet on the device it halves from 638.1 µs to 324.7 µs. We did not isolate this

Why face detection does not fit

Section titled “Why face detection does not fit”

Face detection (det_face_lut_k256, a 128px convolutional model) matches the expected scores as integers on all 10 samples on the host, and runs at 1.76 ms per image. The logic itself is correct, but it does not fit on a plain ESP32. The build stops with this link error.

The cause is the size of the work RAM.

ItemSize
MDL_CTX_BYTES (static work[])1,544,000 B
Score output scores[5120] (int32)20,480 B
Total static DRAM (dram0_0_seg)180,736 B
Total .bss1,566,784 B

Moving it to the heap (malloc) does not help either. The free heap right after boot is 283,696 to 300,648 B, less than a fifth of the 1,544,000 B needed. On a board without PSRAM, there is nowhere to put this work RAM.

With a PSRAM board (speculation, unverified)

On a board with PSRAM, such as the ESP32-WROVER (4MB PSRAM) or an ESP32-S3 (variants with 8MB PSRAM), passing a region allocated with heap_caps_malloc(..., MALLOC_CAP_SPIRAM) to mdl_ctx_init(&ctx, buf, bytes) may fit in terms of capacity. This is speculation, and we have not confirmed it on real hardware. Speed through PSRAM is also unmeasured.

Because the generated main.c hands the work area to mdl_ctx_init, the swap only needs a change to main.c. The detailed build log is in results/deploy/devices/esp32_det_face_build_20261006.log.

Troubleshooting

Section titled “Troubleshooting”
SymptomCause and fix
CMake stops with main/model/ が無いgen_model.py has not been run yet. Do step 1 above
The build fails with a dram0_0_seg overflowMDL_CTX_BYTES plus the input expansion buffer does not fit in static DRAM (180,736 B). If flattening (--dense-flat) grew the work RAM past the limit, try --dense-flat off. Check that -DMDL_NO_DEFAULT_CTX is in effect (that you are not double-allocating); if it is still too big, use a smaller model, or place it in the PSRAM of a PSRAM board (see “Why face detection does not fit” above)
It does not fit in flashMatch CONFIG_ESPTOOLPY_FLASHSIZE_* in sdkconfig.defaults and the partition table to the board’s real flash size (a large model’s model.c lands in .rodata)
Failed to connect when flashingSome boards need you to hold the BOOT button as flashing starts. Also check that the cable carries data
No log, or garbled charactersCheck the baud rate (sdkconfig.defaults uses 115200). esp32_capture.py resets the board right after opening, so check you have not passed --no-reset
Reset in the middle of a long inferenceThe task watchdog is running. Check that CONFIG_ESP_TASK_WDT_EN=n (already set in sdkconfig.defaults) is in effect
A warning in the generated code fails the buildIt comes from -Werror. The project specifies -Wno-error. Add the same setting when embedding into your own project
The build broke after changing targetsRun idf.py set-target again (after idf.py fullclean if needed)
