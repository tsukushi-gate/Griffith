A Mapping Table for PyTorch Users

This library is plain PyTorch. It subclasses nn.Module, loss.backward() works, and torch.optim can be used as-is. Migration is therefore fast.

At the same time, a few things share a name but not a meaning, and that is where accidents happen. The worst offender is model.eval(): in PyTorch it only changes how Dropout and BatchNorm behave, but here it changes the mathematics of the model itself (a real-valued mixture becomes a Boolean circuit).

This page is a translation table from PyTorch vocabulary to the vocabulary of this library.

New to PyTorch as well?

This page is a translation table for people who already write PyTorch. If neural networks themselves are new to you, the fastest route is the Intro Course (three pages) — PyTorch basics → an MLP on MNIST → replacing the same model with a DLGN, all with executed output. For the ideas alone, read From NN to DLGN.

What you will learn here

  1. The mapping table — what replaces nn.Linear / nn.Conv2d / the output layer / optimization / export
  2. How model.eval() differs — the switch from soft to hard, and the discretization gap
  3. Where PyTorch intuition breaks down — floating-point-centric techniques, and the absence of pretrained assets

The minimal mapping — the same network written two ways

Section titled “The minimal mapping — the same network written two ways”

The two look almost identical, and neither loss.backward() nor optimizer.step() changes. What differs is what lives inside a single neuron. One output of nn.Linear is a weighted sum over every input, whereas one output of LutLayer is a single LUT (truth table) that sparsely picks up just N of the input lines, and what is learned is not a weight but which logic function it becomes.

model.eval() means something different

Section titled “model.eval() means something different”

In PyTorch, eval() only changes the behavior of Dropout and BatchNorm, and you get an approximation of the same function. Not so here.

soft (train())hard (eval())
Inputreals in [0,1][0,1][0,1]0/1 bits via round()
LUT weightssoftmax(W) (spread over all 2N2^N2N entries)one_hot(argmax(W)) (a single entry)
Outputreal valuesbits
Meaninghow well the continuous relaxation fitstrue performance as a logic circuit

The accuracy difference between the two is called the discretization gap.

GapInterpretationAction
0–0.5ptHealthy. Gates have converged well onto specific entriesLeave it as is
1pt or moreIt helps the continuous approximation but falls apart as a circuitMore epochs / revisit the parameterization
soft is low tooIt simply is not learningSuspect lr, τ, or capacity (k, number of layers)

Always look at hard eval before you bake

If continuous truth tables stay clustered around 0.5 and are then rounded, accuracy collapses. In one real case, a model with eval acc 0.803 dropped to 0.211 the moment its entries were rounded (recalibrating BatchNorm statistics only got it back to 0.632). A soft score is not a circuit’s score.

There are also options that drive the gap structurally to zero: selection='hard_st' (the CAGE approach, where the forward pass uses argmax and only the backward pass approximates with softmax gradients), the warp parameterization (measured at −0.06pp), and DWN (train/eval logit difference of 0.0).

Where PyTorch intuition breaks down

Section titled “Where PyTorch intuition breaks down”

Here is the honest list. Starting without knowing these guarantees you get stuck.

1. The metric to watch is hard, not soft

Section titled “1. The metric to watch is hard, not soft”

Training only progresses in soft, but the score that means something is the hard one. test_acc is hard, test_acc_soft is soft. It is easy to read them backwards until you are used to it.

2. Pretrained assets are unavailable

Section titled “2. Pretrained assets are unavailable”

There is no pretrained ecosystem like timm / torchvision / HuggingFace. Nor does “just convert a strong real-valued model” hold up: distillation, transfer initialization, and layerwise binary distillation were all measured, and none of the three beat training from scratch (transfer initialization degraded badly). The strength of a native DLGN is that it can learn free Boolean logic, and transferring arithmetic structure constrains that freedom (→ Taxonomy and Lineage of DLGN).

The practical answers are training from scratch, or keeping the parts that should stay real-valued via hybridization (e.g. replacing only a Transformer’s MLP with LUTs).

3. Floating-point-centric techniques lose their meaning

Section titled “3. Floating-point-centric techniques lose their meaning”

The final artifact is a Boolean circuit with no multiplication. Therefore:

  • Tuning precision (FP16/BF16/quantization) is meaningless on the inference side — the output is nothing but 0/1 bits
  • The magnitude of a weight carries no meaning by itself. All that matters is which entry is the largest
  • The main battleground of regularization is managing the discretization gap, not weight norms
  • Correctness is measured by bit-level agreement, not numerical error (three-stage equivalence)

4. The learning-rate scale is different

Section titled “4. The learning-rate scale is different”

Your sense that Adam sits around 1e-3 does not apply. 0.01 is the default, and with independent or deep serial configurations you go up to 0.1–0.3. The first suspect for “the loss will not move off its initial value” is always the learning rate.

5. “Layer width” means something different

Section titled “5. “Layer width” means something different”

The out in LutLayer(in, out) is the number of gates, and it maps directly to circuit area. For MNIST you work in the range of 2,000 (smoke test) to 64,000 (paper reproduction). Numbers 1–2 orders of magnitude larger than an nn.Linear hidden dimension are normal here, which is visually surprising.

6. Only inference is GPU-free

Section titled “6. Only inference is GPU-free”

Training is real-valued computation in PyTorch, so a GPU helps during training. “No GPU needed” refers to the circuit after baking (CUDA is not required; CPU / MPS work too).

7. There are three axes beyond architecture

Section titled “7. There are three axes beyond architecture”

In PyTorch, “which layer to use” is nearly the whole design, but here you also get three orthogonal axes: parameterization / selection / learning rule. What to pick is summarized in What Should I Use? (Selection Guide).

8. Replacing nn.Linear is not 1:1

Section titled “8. Replacing nn.Linear is not 1:1”

Swapping nn.Linear(784, 256) for LutLayer(784, 256) does not give you an equivalent. A single gate sees only N inputs, so you need many more gates and more layers to get the same expressive power. This is why the hybridization API (LogicSpec(n_inputs=2, depth=2, neurons_per_output=8)) exposes depth and neurons_per_output as knobs.

Migration steps

Section titled “Migration steps”
  1. Get one run working with the Quickstart
  2. Decide architecture, N, parameterization, and learning rule in What Should I Use?
  3. Match the usual ranges for lr, τ, and k in Running Training
  4. Learn to read soft vs. hard in Reading Training Curves
  5. Turn it into a circuit with Working with IR → HDL Export
