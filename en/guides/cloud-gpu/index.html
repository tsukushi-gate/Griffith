Cloud GPUs

Logic-gate networks do not need a GPU for inference (that is the whole selling point), but a GPU does help for training. Reproduction experiments at the 60k-gate, 200-epoch scale in particular will not finish in any reasonable time on a local CPU. This page is a guide for deciding where to run.

What you will learn here

  1. Choosing a device — at what scale to pick CPU / MPS (Apple Silicon) / CUDA
  2. How to send jobs to the cloud — running the same script with the same arguments on a cloud GPU
  3. Etiquette for long jobs — detached execution, retrieving artifacts, and how to think about monitoring

Start locally

Section titled “Start locally”

This library does not require CUDA. The CUDA kernels are an optional acceleration; in environments where they are unavailable, it automatically falls back to the Python implementation.

If you do not specify a device, it is auto-detected in the order cuda → mps → cpu. To be explicit, set run.device in the config.

Rules of thumb for device selection

Section titled “Rules of thumb for device selection”
DeviceWhat it’s forRough scaleNotes
CPUSanity-checking the implementation, training logic functions such as XOR and parity, CIup to a few thousand gates / minutesRuns deterministically, so it suits regression tests. The logic_xor recipe takes seconds
MPS (Apple Silicon)Local MNIST smoke tests, checking the UI and editorup to ~10k gates / ten-odd minutesCUDA kernels are not used; it runs on the Python implementation
CUDA (local GPU)The main arena for everyday experiments10k–60k gates / tens of minutesThe LUT kernels are JIT-compiled, making this the fastest
Cloud GPUPaper reproduction, long runs, hyperparameter sweeps60k+ gates / hoursKeeps running after you close your laptop

Inference needs no GPU

Once training is done and the model is lowered from IR to HDL, the circuit runs on an FPGA or as bit operations on a CPU. A GPU is only needed while the continuous relaxation of training is running (→ “no performance difference at inference time” in Choosing a Parameterization).

Running on a cloud GPU

Section titled “Running on a cloud GPU”

A wrapper for the serverless GPU execution platform Modal is bundled in. Existing training scripts run unmodified, with the same arguments as locally.

Etiquette for long jobs

Section titled “Etiquette for long jobs”

For jobs that run for hours, sticking to these three points prevents most accidents.

1. Launch detached

Section titled “1. Launch detached”

Avoid synchronous calls

If you call a cloud function synchronously (polling for the result and waiting), the whole job can be cancelled the moment the client stops polling. Launch via the asynchronous path (spawn), and go fetch the result explicitly only when you want to wait. The bundled entry points and griffith launch --modal / griffith sweep --modal are already built this way.

2. Set up monitoring

Section titled “2. Set up monitoring”

Do not launch and walk away: follow the logs, or run stall detection alongside.

Quiet does not mean healthy. If the heartbeat (epoch / step / loss) shows the same value for several cycles, go look at the logs directly.

3. Retrieve artifacts

Section titled “3. Retrieve artifacts”

Training results must not disappear along with the container, so the design keeps them in both a persistent volume and the experiment tracker.

Set the volume name through the MD_MODAL_VOLUME environment variable (a default name is used when it is unset). griffith collect reads the same variable, so exporting it once from your shell profile or .env is enough.

Checkpoints can also be uploaded to the experiment tracker (wandb Artifacts). How much gets uploaded is controlled by an environment variable.

WANDB_ARTIFACTSBehavior
offDo not upload
best (default)Upload only the best checkpoint, once, at the end of training
allUpload periodic saves as well

Common stumbling blocks

Section titled “Common stumbling blocks”
SymptomCauseFix
The job vanished when I closed my laptopLaunched without detachingPass --detach and --background together
Cold starts are 2–3 minutes slower every timeJIT compilation of the CUDA kernels (the cache is container-local)Expected. Run one job first before launching many in parallel
It was launched but never startsThe concurrent GPU limit was hit and it is queuedDetect the overage with the pre-launch check (scripts/modal_preflight.py)
It works locally but crashes in the cloudData or checkpoints are referenced by absolute pathFollow the relative-path convention (scripts are expected to run unmodified)
It should be using the GPU but it’s slowIt fell back to CPUCheck the “device: …” line in the startup log
