Running Training

Training a differentiable logic-gate network follows one arc: optimize a continuously relaxed circuit by gradient descent, then discretize it into a pure Boolean circuit at the end. This page covers the operational side — how to actually run it.

What you’ll learn here

  1. Two entry points — when to use griffith train (CLI) with a config YAML versus TrainConfig + run_training() (Python API)
  2. Typical hyperparameter ranges — measured guidelines for learning rate, temperature τ, neuron count k, depth, and epochs
  3. Soft vs. hard accuracy — why both are reported and what the gap between them (the discretization gap) means

The overall training flow

Section titled “The overall training flow”

The training loop itself is no different from an ordinary neural network. What is distinctive is the dual nature of the weights: during training they are a probability distribution; at evaluation they are a truth table with a single entry set.

The top row (yellow) is soft = training mode; the bottom row (green) is hard = inference mode. Learning only progresses in soft mode, but the score that actually matters is the hard one.

Path A: run it from the CLI (griffith train)

Section titled “Path A: run it from the CLI (griffith train)”

Use this when you need reproducibility, when you are running sweeps, or when you are submitting jobs to the cloud. Write the config in YAML and override individual fields on the command line with dot notation.

The recipe YAML maps directly onto the structure of TrainConfig.

FlagPurpose
config (positional)Path to the config YAML. If omitted, training starts from the defaults
overrides (variadic)Dot-notation overrides such as model.k=8000
--from-run DIRReload an existing run’s config.yaml and re-execute it
--out-dir DIROutput directory (defaults to outputs/<timestamp>_<run name>)
--strictExit non-zero when expected_metrics are not met

Re-running is just pointing at a directory

At launch, the runner saves the fully resolved config to outputs/<run>/config.yaml. It uses the same schema, so uv run griffith train outputs/<run>/config.yaml reproduces the run exactly.

Keys for wiring, GroupSum and conv-DLGN

Section titled “Keys for wiring, GroupSum and conv-DLGN”

With the defaults you get the usual fully connected DLGN with fixed random wiring. The keys that change the structure are:

KeyValuesMeaning
model.connectionsrandom / unique / {kind: ...}Wiring. kind is rot (per-layer lists s_a / s_b and the stride step) / perm / random_seeded / random_uniform / butterfly (strides / order) / local1d (strides) / local2d (grid / bits_per_cell / layer0_offsets / assign) / per_layer (each layer takes rot / stretched_rot / perm / random_* / rot_n / butterfly / local1d / local2d). Structured wirings accept dedupe: true to remove duplicate pins
model.group_assigncontig / strideClass assignment of GroupSum (neuron i → class i // m or i mod k). In the IR, stride becomes a transpose plus group_sum
model.estimatorsigmoid / sinEstimator of the entry probabilities for parameterization: independent (sin is the paper IWP; with residual_init: true the residual init is done in Ω space)
model.kind: conv_dlgn + model.convin_shape / channels / sampler (random / random8 / cross5 / dilated8 / checker13) / downsample (orpool / stride) / head_dims / head_wiring (rot2 / random / unique)Weight-shared logic-gate-tree convolutions + OR pooling + a fully connected head (cdlgn style). Images are consumed as tensors; the IR comes from export_ir(..., input_shape=in_shape, native_conv=True)

Recipe examples: configs/recipes/conv_dlgn_cifar10_s.yaml (CIFAR-10, calibration anchor) and configs/recipes/conv_dlgn_mnist_quick.yaml (a one-epoch local smoke run).

Unknown keys fail immediately

Section titled “Unknown keys fail immediately”

Configs are validated by pydantic with extra='forbid'. A typo such as model.kk=2000 raises a validation error before training starts, so you never lose three hours only to discover a misconfigured run.

Path B: run it from the Python API (run_training)

Section titled “Path B: run it from the Python API (run_training)”

Use this when you want to call training from a notebook, build your own sweep logic, or feed the result dictionary straight into downstream processing.

run_training() returns a dictionary that contains at least the following.

KeyMeaning
hard_accDiscretized accuracy at the final epoch (performance as a circuit)
best_hard_accBest hard accuracy seen over the whole run
final_lossLoss at the final step
stepsTotal number of steps
out_dir / checkpoint_latest / checkpoint_bestPaths to the artifacts
expected_metricsResult of checking the expected metrics ({'ok': bool, 'checks': [...]})

griffith train (CLI)run_training() (API)

The CLI is a thin wrapper around the API, so training itself is identical either way.

Typical ranges

Section titled “Typical ranges”

Measured guidelines based on MNIST-style tasks (28×28, 10 classes).

τ (the GroupSum temperature) directly affects accuracy

Section titled “τ (the GroupSum temperature) directly affects accuracy”

GroupSum merely sums neuron outputs per class and divides by τ, yet the choice of τ alone can move accuracy by a full point.

logitc=1τ∑i∈groupcyi\text{logit}_c = \frac{1}{\tau}\sum_{i \in \text{group}_c} y_ilogitc​=τ1​i∈groupc​∑​yi​

On MNIST with 6 layers and k=8000, a fixed τ=10 measured about 1.0pt higher than the rule-of-thumb τ=k/C≈28.3\tau=\sqrt{k/C}\approx 28.3τ=k/C​≈28.3. Start around 10 and only change it if the loss refuses to drop or the logits saturate.

Soft and hard — reading the two accuracies

Section titled “Soft and hard — reading the two accuracies”

Training scripts always report two accuracies. Treat them as scores for two different models.

Displaymodel.trainingInputsLUT weightsMeaning
test_acc(soft)TrueContinuous values in [0,1]softmax(W) (spread across all 2N2^N2N entries)How well the continuous relaxation fits
test_acc (hard)False{0,1} via round()one_hot(argmax(W)) (a single entry)True performance as a logic circuit

Laid out side by side, here is what happens internally.

Normally soft > hard, and the difference is called the discretization gap.

GapInterpretationWhat to do
0–0.5ptHealthy. Gates have converged well onto specific entriesNothing
1pt or moreThe continuous relaxation works, but the circuit falls apartTrain longer / revisit the parameterization
soft is low tooTraining is not working at allSuspect lr, τ, or capacity (k, depth)

Measured example (MNIST, 6 layers, 50ep): softmax N=2 gives soft 98.30% / hard 97.74% (a 0.56pt gap). More training drives gates toward a single entry, so the gap tends to close on its own.

Running hard eval on a trained checkpoint

Section titled “Running hard eval on a trained checkpoint”

The model structure is restored from the config stored inside the checkpoint, so there is no need to re-specify the architecture at evaluation time. Pass --dataset to evaluate on different data.

Common pitfalls

Section titled “Common pitfalls”
SymptomCauseFix
Loss never moves from its initial valueLearning rate too low — especially common in deep serial configurationsRaise optim.lr to 0.1–0.3 to isolate the issue
soft is high but hard drops sharplyThe discretization gap. Either not enough training or a mismatched parameterizationTrain longer / Choosing a Parameterization
Accuracy falls short of published numbersUsually a mismatch in τ, the wiring scheme, or how many evaluation samples were usedSet τ to the official recipe value and evaluate on the full test set
Config changes seem to have no effectYou edited one YAML but the run is reading another fileCheck outputs/<run>/config.yaml (the resolved config)
Training works but the model won’t lower to HDLNon-logic layers (ones returning real values) are mixed in→ HDL Export
