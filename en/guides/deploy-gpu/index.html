Run on GPU (CUDA / Metal)

The deploy kit also generates CUDA (NVIDIA GPU) and Metal (Apple GPU) sources from the same bundle. This page covers how to use the generation commands, how to call the result from host code, how optimizations are selected automatically, and how to verify before shipping. Up to making the bundle, it is the same as the Quickstart.

Know this first

At batch=1, a GPU is not necessarily faster than C. Feeding a small model one sample at a time is dominated by GPU launch overhead. A GPU pays off when you push a lot through at once (large batch). If speed is the goal, measure on your own model first.

Generation commands

Section titled “Generation commands”

The two take almost the same flags (all of them are in the griffith CLI). The commonly used ones:

FlagMeaning
-o, --output DIROutput directory (required)
--batch NThe maximum number of samples in flight (default 1). The number you run at call time can be anything from 1 to N. Device memory scales with this
--no-autoTurn off automatic optimization selection (below)
--dense-flat auto|on|offWhether to generate dense as a flattened netlist (lut_flat) (default off = do not flatten; auto = flatten when the reduction is 25% or more; see “Flattening (opt-in)” below)
--dense-fuse / --dense-packedExplicitly enable a dense-model optimization (no flattening when given)
--conv-engine split|combinedExplicitly choose how conv2d is executed
--n-streams NStream pipelining (opt-in, below)
--conv-codegenPer-conv2d model-specialized kernels (opt-in, below)
--no-runtimeDo not copy the runtime

Calling it from host code

Section titled “Calling it from host code”

The generated model_metal.mm / model_cuda.cu exposes these C functions to the host (extern "C"). Internal initialization (allocating the device and buffers; compiling shaders on Metal) runs on the first inference call, so you do not call init yourself.

MetalCUDA
Inference (up to N samples at once)mdl_metal_infer_batch(bits, scores, n)mdl_cuda_infer_batch(bits, scores, n)
One samplemdl_metal_infer(bits, scores)mdl_cuda_infer(bits, scores)
Input width / output width / max batchmdl_metal_input_width() / _output_width() / _max_batch()mdl_cuda_input_width() / _output_width() / _max_batch()
Image models (preprocessing included)mdl_metal_infer_image_batch(image, scores, n)mdl_cuda_infer_image_batch(image, scores, n)
Cleanupmdl_model_shutdown()mdl_cuda_shutdown()

The arguments have the same shape for both.

  • bits is a host unsigned char array of n x input_width values, each 0 or 1 (samples laid out back to back)
  • scores is a host int array of n x output_width values (for classification, one score per class; the largest is the prediction)
  • The return value is 0 on success, and -1 if n exceeds the maximum you set with --batch

Optimizations are chosen automatically

Section titled “Optimizations are chosen automatically”

Whether a GPU optimization helps depends on the model’s shape and the batch size. The same optimization can make some models slower. So codegen-cuda / codegen-metal turn an optimization on automatically only under conditions where it is measured to win (the default). The result and its reasons are left in two places: one line on standard output at generation time, and a /* auto-config ... */ comment at the top of the generated source.

The auto-config ... line in the output above is exactly that. For the XOR above, CUDA at --batch 256 picks dense_fuse=True automatically (batch is 32 or more and there is a chain of dense layers that can be fused). If you flatten it with --dense-flat auto (22 → 3 gates), the same --batch 256 gets dense_fuse=False (no lut_layer chain is left to fuse). For Metal at --batch 1, dense_fuse=False, and the reason (batch is below 32) is written in the comment at the top of the source.

Decision table

Section titled “Decision table”
OptimizationDefaultTurned on automatically whenBasis
conv_engine split to combinedsplitIf any conv2d node has max_slots_per_oc above 8, the whole model switches to combinedOn a 1.6M-gate detection model, generating with split fails with 9 > 8; combined works
dense_fuseOFFWhen not flattened (the default --dense-flat off, or a reduction under 25% with auto), batch >= 32 and a fusable chain exists (consecutive dense layers plus a final group_sum fit in shared memory)On 4 models on Apple M3: 1.11-1.34x at batch=1, 1.20-2.01x at batch 32 and above, stably faster. On CUDA, 1.57-1.58x at batch 128
dense_packedOFFWhen not flattened, dense_fuse is not turned on automatically, the model is eligible (non-image input, main path is only dense and group_sum), and batch >= 128At batch=32 several models get slower on both CUDA and Metal (0.878-0.891x on CUDA, 0.887x on Metal). At 128 the slowdown mostly disappears
decode megakernel (RDDLGN generation)ONAlways on when the model fits. If it does not fit, it falls back to the older path automaticallyEvery measurement was positive (Metal 1.61-2.10x, CUDA 1.71-2.34x) with no slowdown case, so it is on by default with no batch condition
n_streamsOFF (opt-in)Never turned on automatically0.66x slowdown on some Metal models. On CUDA, 0.878x at batch=1 and at most 1.058x
conv_codegenOFF (opt-in)Never turned on automaticallyEnd-to-end speed barely changes (1.00-1.04x) while the generated code grows 1.78-6.65x

The numbers come from docs/guides/deploy-optimization.md in the repository and the measurement files it lists (under results/deploy/).

dense_fuse and dense_packed cannot be combined. When both conditions hold, dense_fuse wins because it came out ahead in the measurements (on 4 HAR-style models at batch=256 on Apple M3, dense_fuse was ahead on all four). For models where dense_fuse cannot be used (for example a layer width over the shared-memory limit), dense_packed is the fallback.

When picking a GPU at batch=1 makes things slower

Section titled “When picking a GPU at batch=1 makes things slower”
  • dense_fuse is not turned on automatically at batch=1. In the Metal measurement (har_dlgn_k6000_gumbel, Apple M3), batch=1 was 0.81x, a slowdown; batch=32 was 1.91x and batch=128 was 2.51x (from the --dense-fuse help text).
  • dense_packed cannot amortize its cost at small batch. Packing 32 samples into one word does not pay back when there are few samples, and some models get slower even at batch=32.
  • n_streams is 0.878x on CUDA at batch=1. The duplicated buffers for pipelining weigh on a small model.

In short, if you want low latency one sample at a time, measure C (CPU) first. Choose a GPU for pushing batches through.

Overriding the automatic selection

Section titled “Overriding the automatic selection”
  • --no-auto: do not use the decision table. Anything you did not set explicitly keeps the value from before automatic selection existed (conv_engine=split, dense_fuse / dense_packed OFF). Use it when you want the generated output pinned (comparison experiments, reproducibility).
  • An explicit setting always wins: with --dense-fuse, it is on even if the batch does not meet the condition. Without it, the automatic selection decides. To turn dense_fuse off, use --no-auto.
  • --n-streams and --conv-codegen are never turned on automatically. As the table says, the conditions where they help could not be pinned down (or they are not worth it). Measure first, then add them yourself.

Relation to circuit compression

Section titled “Relation to circuit compression”

Now, griffith deploy bundle automatically applies a lossless sweep that reduces the gate count of dense models (default --compress fast). This is baked into the bundle, so it helps every target: CUDA, Metal, C, and Web (the XOR above goes from 32 to 22 gates).

Flattening (--dense-flat, opt-in)

Section titled “Flattening (--dense-flat, opt-in)”

--dense-flat (lut_flat, a flattened netlist with pass-throughs, constants and duplicates folded away) also runs on CUDA / Metal. The GPU side reorders the gates into levels (by dependency depth) at generation time and evaluates the gates of a level in parallel. If the signal table fits in shared memory (Metal 32KB / CUDA 48KB), it becomes a single launch with one sample per threadgroup (fused).

However, the default of codegen-cuda / codegen-metal / verify-metal is --dense-flat off (no flattening): unlike C and Web, they do not flatten automatically, because there are conditions under which flattening makes the GPU slower (see the caution below). To use it, pass --dense-flat auto (try flattening right before generation and adopt it if the effective gate reduction is 25% or more) or --dense-flat on (always adopt it). Neither changes the bundle. If you pass --dense-fuse / --dense-packed explicitly, they do not flatten, because those assume a lut_layer chain. A bundle with lut_flat baked in by bundle --dense-flat runs as a flattened netlist on the GPU too, regardless of this default.

When flattening makes the GPU slower

On Metal on an Apple M3, measuring HAR k600 / k2400 / k6000 at batch 32-4096, the gates roughly halve, yet against the best without flattening (dense_fuse / dense_packed) it reached 1.02-1.10x on k600, 0.85-1.15x on k2400 and 0.47-0.71x on k6000 at batch 128 and above (1.02x at batch 32) (on the GPU, the fixed cost of launches and transfers dominates over the gate count). In other words, a large model (tens of thousands of gates) run at batch 128 or more can drop to about half the speed when flattened. Small models or batches around 32 are about the same or slightly faster. Flattening means the automatically selected dense_fuse / dense_packed are no longer used, so when you try it, compare the default (off) against --dense-flat auto with scripts/bench_dense_gpu.py before choosing. The CUDA lut_flat path has not been run or measured on real NVIDIA hardware (only a syntax check of the generated code; to check it, use scripts/verify_cuda_remote.py --dense-flat on). The figures of how levels are formed and of the measurements are in “Flattening on the GPU” of Compression and Optimizations.

Verifying before you ship

Section titled “Verifying before you ship”

For every target, the reference is the integer output of ir/simulate.py (a plain numpy implementation). Ship only after confirming that the generated code does not differ by a single bit.

Here --dense-flat auto is passed to check the flattened path (with the default off, it does not flatten and verifies the same conventional path as the codegen-metal default). About larger models

Only XOR was run here. The MNIST image model needs a data download to train, so it was not run when this page was written. For real models, confirm integer match with verify-metal, then measure your own model and batch with scripts/bench_deploy.py.

CUDA: verify on a remote NVIDIA machine

Section titled “CUDA: verify on a remote NVIDIA machine”

codegen-cuda only generates code; there is no subcommand equivalent to verify-cuda. For when you have no NVIDIA GPU locally, scripts/verify_cuda_remote.py builds and runs on a GPU machine over ssh and compares against simulate.

The script generates the bundle and CUDA source from the model, rsyncs it together with the runtime, builds with nvcc remotely, runs on random inputs (both the bit-vector and raw-image paths), and compares against simulate as exact integers.

  • It needs a machine with an NVIDIA GPU and nvcc that you can ssh into. It cannot be run on a Mac without one.
  • Pass --models names from tools/webbench/public/models/. Set --arch to your GPU’s compute capability (default sm_89).
  • Add --bench to also measure performance. --batch sets the maximum number of samples at generation time.
  • Add --dense-flat on (or auto) to verify the flattened CUDA path (lut_flat). The default is off, the same as codegen-cuda.
  • The stream version (--n-streams) is verified by scripts/verify_cuda_stream_remote.py.

The verified GPUs and CUDA versions are in Platform support.
