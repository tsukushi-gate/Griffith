Run in the Web browser

The deploy kit’s Web target, unlike C or CUDA, does not generate source code. The executor (a TypeScript engine plus WASM kernels) already exists as a runtime, so codegen-web only writes the bundle itself out as a distribution JSON and copies the runtime next to it. The server only needs to serve static files. Inference finishes entirely inside the browser, so the input never leaves the device. This page collects the procedure, how to embed it in your own page, and numbers measured on one machine.

What you get

Section titled “What you get”

The output directory of codegen-web can be dropped straight onto static hosting.

FileRole
model.bundle.jsonThe bundle itself (rename with --name)
mdl_web.jsThe public API (loadBundle etc.). ESM, works in both the browser and Node
lib-*.js / release-*.js / assets/Shared chunks referenced by the above. File names carry a hash and change on every build
release.wasm / release-simd.wasmWASM kernels (scalar / v128 SIMD). auto and wasm use the SIMD one
verify.mjsNode verification CLI (called by verify-web)
demo.js / index.htmlThe default single-page demo (?model=<url> changes what it loads)

The chunk file names are not fixed, so copy the contents of dist/ as a whole (this is what codegen-web does).

Prerequisites

Section titled “Prerequisites”
  • This repository cloned, with uv sync --extra dev --extra cpu done
  • node and npm (used to build the WASM kernels and the JS runtime; the serving host does not need them)
  • A browser with WebAssembly (without SIMD, auto falls back to the JS engine, as described below)

Steps

Section titled “Steps”

1. Build the runtime (first time only)

Section titled “1. Build the runtime (first time only)”

This produces runtime/web/dist/. It is a build artifact, so it is not tracked by git. If runtime/web/dist is missing, codegen-web fails and tells you to run this first (so a stale runtime is never shipped silently).

2. Build the distribution from a bundle

Section titled “2. Build the distribution from a bundle”

This example uses the XOR model, which needs no network. One command runs training, bundling, codegen-web, placing the custom page, and verify-web.

Underneath are these three commands (for your own model, prepare a bundle and start from the second line).

For how to make a bundle, see the Deploy Kit Quickstart; for real-data models, see Prepare the demo models. gen.py also works with another bundle via --bundle <x.bundle.json> --samples <samples.json>.

3. Serve statically and open in a browser

Section titled “3. Serve statically and open in a browser”

The page fetches ./model.bundle.json and ./samples.json, then shows each sample’s predicted class, the accuracy, and µs per inference. The engine selector (auto / js / wasm) switches engines. Opening the page directly via file:// makes fetch fail, so always serve it over HTTP.

Public API

Section titled “Public API”

mdl_web.js exposes loadBundle (spec: runtime/web/README.md).

  • bundleJson is the parsed bundle. A .mdlb binary can be passed as an ArrayBuffer / Uint8Array as it is.
  • bundle.scores(bits, batch) takes an array of 0/1 of length batch × input bit width and returns integer scores (Int32Array). For classification, the argmax is the predicted class.
  • For image-input models (kind of seg / detection / classify-image), pass model-resolution RGBA (ImageData.data) to scoresRgba / segLabels / detect. The runtime does the encoding according to the bundle’s preprocessing definition.
  • detect for detection models returns the boxes, including peak extraction.

The main.js in this example is the minimal use: it runs a dense bundle one sample at a time with scores(bits, 1).

Choosing an engine, and the fallback

Section titled “Choosing an engine, and the fallback”
engineImplementationOn failure
'auto' (default)Tries to initialize WASM first, else falls back to JSRuns on 'js' and records the reason in bundle.notes
'wasm'AssemblyScript kernels (bitplane-wasm)Throws
'js'Pure TypeScript (bitplane)—

The engine actually used is in bundle.engine (even with auto, it holds the resolved 'js' or 'wasm'). The integer outputs match exactly between the two engines, so a fallback changes only the speed, not the result. To avoid shipping a fallback unnoticed, show bundle.notes on screen or in a log (this example shows it on the page).

threads defaults to 1 and does not use SharedArrayBuffer. So no COOP / COEP headers are needed, and it works as is on plain static hosting such as python -m http.server.

Run verify-web before shipping

Section titled “Run verify-web before shipping”

verify-web is the shipping gate: it actually runs the Web runtime on Node and requires the output to match the ir/simulate reference as integers, exactly. A single difference fails it on the spot. In verification, a broken programs section is an error rather than silently rebuilt (so stale or tampered programs cannot slip through). -n changes the sample count (default 3) and --seed the random seed. Pass both js and wasm before shipping.

Embedding in your own app

Section titled “Embedding in your own app”
  1. Put the output directory of codegen-web (mdl_web.js and chunks, *.wasm, model.bundle.json) on your site as static files. mdl_web.js loads the release-simd.wasm next to it relative to import.meta.url, so do not break the relative layout. If you place it elsewhere, pass a URL with loadBundle(doc, { wasmUrl }).
  2. From your page (or a bundler-built module), import { loadBundle } from './mdl_web.js'.
  3. Call loadBundle once per model and reuse the result. Do not call it again on every inference.
  4. The input to inference is an array of 0/1 (dense) or RGBA (images). The output is integer scores; no floating point appears.

The minimal page is index.html (about 1.2KB) and main.js (about 3.8KB) in examples/32_deploy_web/, small enough to copy and adapt.

The delivery estimate is “bundle size + about 290–300KB of runtime” (an earlier record says about 279KB, see the Bundle specification; it varies with the runtime build). Bundle sizes of real models are in the measurement table of the Bundle specification.

Measured (XOR, in a browser)

Section titled “Measured (XOR, in a browser)”

Conditions for these numbers

Measured on an Apple M3 / macOS 26.6.2, in the Claude desktop app’s built-in browser (Chromium 152 series). Served with python -m http.server; the page of examples/32_deploy_web/ shows the average over “4 samples × 2,000 rounds = 8,000 inferences”. The model is XOR (2 input bits, 22 gates after sweep), which is very small. This is not the speed of a real model.

Conditionµs/inference
First page load (engine=auto → wasm)15.55
Switching the engine js ↔ wasm and measuring (js, wasm, js, wasm in that order)3.84 / 3.24 / 3.00 / 3.86

What can be read from this:

  • All four predictions matched the labels (accuracy 4/4). The output scores are integers such as [8, 1] / [0, 8].
  • At XOR’s tiny size, js and wasm showed no meaningful difference (the values scattered within 3–4µs across switches). WASM is expected to help on models with many gates, but this example did not measure that.
  • The first 15.55µs includes JIT warm-up. The very first number after opening the page reads higher than the steady state.

Do not infer a real model’s speed from this XOR figure; measure your own bundle with the same page.

Relation to circuit compression

Section titled “Relation to circuit compression”

griffith deploy bundle bakes circuit compression (--compress fast, a sweep) in at bundle time by default. In this example, XOR went from 32 gates to 22 (31.2% fewer). The browser does not redo the reduction; it runs the baked-in circuit as it is.

In addition, codegen-web, like C, flattens dense right before shipping (lut_flat). Flattening is a reduced netlist in which pass-through, NOT, constant and duplicate gates are folded into wires; it is lossless (scores match as integers). On the Web there is no threshold: whenever there is a chain of 2-input lut_layers, it is used (default --dense-flat auto). The Web’s legacy path (lut_layer) costs more per gate than the flattened one, so unlike C there is no region where flattening makes it slower. --dense-flat off ships the legacy lut_layer chain. verify-web uses the same decision, and its golden is ir/simulate of the original bundle.

On the real HAR models, the time per inference in the built-in browser (Chrome 152, Apple M3) was as follows (µs; the integer scores matched in all four).

ModelCountlut_layer (legacy)lut_flat jslut_flat wasm
HAR k2400180.819.411.1
HAR k24003276.07.53.8
HAR k60001248.346.427.6
HAR k600032243.111.36.0

If you pass 3 or more samples at once to scores(bits, n), it switches automatically to a path that packs 32 samples into one word. Flattening also shrinks the delivery size (the HAR k6000 bundle goes from 428KB to 262KB). Bar charts for all three models are in “Measured on the Web” of Compression and Optimizations. For the C side, see the Deploy Kit Quickstart.
