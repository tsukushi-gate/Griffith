Platform Support

A reference that gathers, on one page, “how far each target has been verified” for the targets generated by griffith deploy codegen-c / codegen-cuda / codegen-metal / codegen-web. For how to use the deploy kit as a whole, see the Deploy Kit Quickstart, and for the bundle format see the Deploy bundle spec.

Verification levels

Section titled “Verification levels”

The “verification” columns on this page use three levels. They exist so that we never write “it works” for something we have not verified.

LevelMeaning
Measured and verifiedBuilt and run on real hardware, with integer-exact agreement with ir/simulate.py (the golden model) confirmed by a test or a verify command
Build confirmed onlyCross-compilation is confirmed to succeed, but nothing was run in that environment (integer agreement is unverified)
Theoretically possible by standards conformance (unverified)The code handles it through branches or macros, but there is no build or run record

Where the ESP32 and iOS stand

The ESP32 (Xtensa) was run on real hardware, and the outputs of all 50 samples of the three activity-recognition models (k600, k2400, k6000) and MNIST matched ir/simulate.py as integers, so it is “measured and verified”. However, a convolutional model (face detection, 128px) does not fit in DRAM on a plain ESP32 without PSRAM, and cannot be built.

iOS is measured and verified both on the simulator (native execution on an Apple Silicon host) and on a real iPhone 17 (iOS 26.6.2). On the device, the outputs of five models matched ir/simulate.py as integers (activity recognition k6000 at 8.07 µs, face detection at 0.803 ms). The simulator times are host-CPU values, not real-device values.

The procedures and measured values are in Run on ESP32 and Run on iPhone.

The C runtime’s dependencies are just two C99 standard headers (<stdint.h> / <stddef.h>), and the only libc functions are memcpy / memset (-DMDL_NO_LIBC switches to our own implementations, so libc is not needed at all).

The range of compilers available for verification is also limited. The clang at hand (Apple clang 21.0.0) has cross backends only for the ARM / AArch64 family and the x86 family, with no backend for RISC-V / MIPS / WASM / Xtensa / MSP430. These are “unverified” not because of any constraint in the code but because there was no verification environment.

Supported CPU architectures: the portability contract

Section titled “Supported CPU architectures: the portability contract”

The conclusion first. Any target that has a C99 (cross) compiler should work, in principle. The “supported architectures” are not a list of separate implementations prepared per instruction set; they are merely a list of the verification record of whether the same single C99 source goes through as is. The grounds are as follows.

  • The core is strict C99. The only headers it depends on are <stdint.h> / <stddef.h>, both of which the C standard obliges even freestanding implementations to provide. -DMDL_NO_LIBC also removes the need for libc (it builds without host headers under -ffreestanding)
  • Architecture-specific code (NEON / SSE2 / AVX2 intrinsics and detection macros) is isolated in the single file mdl_simd.h. On unsupported architectures, or with -DMDL_NO_SIMD, it automatically falls back to a bit-identical scalar implementation
  • No endianness or alignment assumptions are introduced. Bit-plane word operations are all defined by bit position (x>>5, x&31), and the core contains not a single pointer cast that reinterprets a byte sequence in memory as another integer width
  • SIMD only makes it faster and does not affect correctness. That the SIMD path and a scalar-forced build agree bit for bit on real models is pinned by a test
  • It is pinned likewise that the generated code (model.c / model.h) contains no architecture-specific code

There is one condition we cannot state flatly

The horizontal shift of the tap plane (mdl_kernels.c) treats a signed right shift of a negative value as an “arithmetic shift” (floor division in two’s complement). In strict C99 this is implementation-defined, and the standard does not guarantee it unconditionally. It does hold on every practical C99 compiler that uses two’s complement (gcc / clang / MSVC / the major embedded toolchains), no known counterexample exists, and C23 spells this behavior out as standard semantics. So “works on C99” is most accurately understood as meaning “works on any practical C99 compiler with two’s complement and arithmetic right shift.”

The contract is enforced mechanically by the following checks.

What is checkedCorresponding test
Architecture detection macros and inline asm do not exist outside mdl_simd.hTestSIMDContract
The core has no byte-reinterpreting castsTestSIMDContract
The SIMD path and the scalar path agree bit for bit on real modelsTestSIMDContract
The generated code also has no architecture-specific codeTestSIMDContract
Only two dependency headersTestFreestanding
No heap allocation, floating point, or I/OTestFreestanding
A libc-free build (-DMDL_NO_LIBC -ffreestanding) goes throughTestFreestanding

The tests are in tests/deploy/test_c_portability.py.

About the Windows parallel helper: mdl_threads.c (mdl_run_pool and others) is pthread-only and not supported on Windows. The core (mdl_kernels.c + the generated model) cross-builds on Windows too, but to use multiple cores you call mdl_infer_ctx (re-entrant when the contexts differ) directly from the caller’s own threads (CreateThread and the like).

SIMD paths (by detection macro)

Section titled “SIMD paths (by detection macro)”

The SIMD path is selected automatically by macros at compile time, and falls back to scalar where disabled (mdl_simd.h). The integer output is exactly identical on every path, which is pinned by a test as part of the portability contract above.

PathDetection macroVerification levelBasis
NEON__ARM_NEON / __ARM_NEON__Measured and verifiedRun on an Apple M3. Integer-output agreement with the scalar path is pinned by a test (this Mac’s default build is NEON)
SSE2__SSE2__, or _M_IX86_FP >= 2 (MSVC dialect)Build confirmed onlyThe x86_64 cross-compile goes through, but there is no record of running the SSE2 path itself on real hardware
Scalar (fallback)When neither of the above is present, or -DMDL_NO_SIMDMeasured and verifiedThe baseline path for all measurements. Also the comparison target for the SIMD path
AVX2__AVX2__ (MSVC unsupported)Measured and verifiedReal Xeon W-1270P (Comet Lake, 8C16T), gcc 9.4.0. For dense and conv models alike, the AVX2 build and the scalar / SSE2 builds produce byte-identical output. This verification is a manual A/B and is not a standing test. You can go back to SSE2 with -DMDL_NO_AVX2 / -mno-avx2
AVX-512—Not implementedThe verification machine has no AVX-512 and cannot run it, so implementation was put off

HDL (FPGA / ASIC)

Section titled “HDL (FPGA / ASIC)”

Output to Verilog / VHDL is a separate path from the deploy kit’s C / GPU / Web (griffith export-hdl), but it starts from the same IR. It is verified by three-way equivalence (PyTorch hard eval, ir/simulate.py, HDL simulation).

ItemContentsVerification level
VerilogChecks the generated output with iverilog (can run locally)Measured and verified
VHDLChecks the generated output with ghdl (ghdl is officially verified in CI / cloud containers)Measured and verified
Real FPGATang Nano 20K / DE0-CV and othersSee the supported-boards table in Deploy to FPGA

The procedure and the details of the check are in HDL Export.

Supported node kinds and unsupported features

Section titled “Supported node kinds and unsupported features”

The IR node kinds the C runtime supports are conv2d / or_pool2d / upsample2d / permute / concat / group_sum / lut_layer (n_inputs<=5) / flatten. Shapes outside the range raise at generation time (UnsupportedNode), and nothing silently falls back to another path (so that unverified code is not shipped).

NodeSupported range
conv2dGeneral (any stride / padding; stride=1 with equal width takes the shared-shift-plane fast path)
or_pool2dkernel=2, stride=2, padding=0 only
upsample2dscale=2 (nearest neighbor) only
permuteChannel axis only / the SpatialGroupSum form ([0,2,3,1] + group_sum fusion)
concatChannel axis (bit planes) / score vectors (a detection model’s multi-head output)
group_sumPlain sum / SpatialGroupSum fusion
lut_layern_inputs <= 5
lut_flatThe flat dense netlist. griffith deploy codegen-c builds it at C-generation time with the default --dense-flat auto when the effective-gate reduction is at or above the threshold (bundle --dense-flat can also bake it into the bundle). Now it also runs on the Web (codegen-web flattens by default) and on CUDA / Metal (executing level by level in parallel; codegen-cuda / codegen-metal default to off, opt in with --dense-flat auto / on). It does not appear with --dense-flat off
flattenPass-through

The unsupported features that deserve particular attention are as follows.

  • Box decoding for detection models (CenterNet peak extraction plus NMS) is not included. What the runtime returns is up to the score map, and everything after that is post-processing on the application side (see Prepare demo models for the procedure)
  • add / binarize / constant / generic pool / generic upsample are not implemented (they do not appear in real models)
